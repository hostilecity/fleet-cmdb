# Health, logs, failed jobs, and retention

For the server owner. Hostnames below are examples (`vm-01.example.lan`, `agent.fleet.example.lan`).

## `GET /health`

Served on the agent hostname and on localhost, never the dashboard hostname. No sign-in. It answers `200 {"status":"ok"}` or `503 {"status":"unhealthy"}` with each check as `ok`, `warning`, or `failing` and nothing else (no versions, counts, or error text; the server log has the detail). A `warning` keeps the status `ok` and the answer 200: it is something to fix that has not stopped anything yet. An uptime monitor that watches the status code does not see one, so: signed-in operators see a **Database maintenance needs attention** banner on every dashboard page naming each problem the last hourly run or nightly check found (the audit guard's only in production; it goes once a run no longer finds it); the hourly maintenance logs `[partitions] needs attention: …` once when a problem appears and `[partitions] resolved: …` when it clears; and a monitor that can match a keyword can alert on `"warning"` in the body of `/health`. Point the uptime monitor at it. `/up` stays the container's liveness check.

| Check | Fails when |
|---|---|
| `database` | a query does not succeed |
| `releases` | the binary of the newest release, or of a running rollout's target, is missing or has the wrong size |
| `backup` | the last complete backup is missing or older than `FLEET_BACKUP_MAX_AGE_HOURS` ([backup-and-restore.md](backup-and-restore.md)) |
| `failed_jobs` | a background job failed all its retries in the last 24 hours |
| `job_liveness` | the recurring liveness evaluation has not succeeded in the last 5 minutes: the scheduler, a worker, or the queue database is down, or the evaluation keeps raising (an attempt that raised and was retried does not count) |
| `partitions` | **failing:** the audit log has fewer than 2 months of partitions created ahead. It has no default partition that takes rows, so audited actions would start failing when they run out. **warning:** a history table's default partition has rows, or rows set aside from it are still being moved back, fewer than 2 partitions are created ahead, a partition has been due for retirement, or missing ahead, for 3 days, maintenance has been skipped for over 3 hours, or the nightly check found rows whose host or rule does not exist. See [Partitions](#partitions) |
| `audit_guard` | **warning** only: the audit log's guard does not hold. Its event triggers are not installed or are disabled, the guard function is not owned by the PostgreSQL superuser, a partition is not among what it protects (made while it was off), a month it protects is no longer attached, an audit table has an index, statistics object, constraint, default, or column type using code other than PostgreSQL's own (which would run as the superuser when it next runs the step; the line says what to do: the app's role drops an index or statistics object, and the superuser runs `ops/postgres/audit-guard-recover.sql` for a default or constraint, install-server.md "Recovery"), an audit table has an invalid index (a refused `CREATE INDEX CONCURRENTLY`; the app's role drops it), an event trigger other than the guard's exists (the line gives the quoted `DROP` to run, connected as install-server.md says; one of `cmdb`'s, or a login trigger of `cmdb`'s, means `cmdb` was a superuser and the cluster is rebuilt), `pg_catalog` holds something the bootstrap superuser did not put there, or the app's role is the bootstrap superuser (rebuild: install-server.md, "If cmdb is or was a superuser"), the id sequence is unlogged, or the app's role, or the owner of `audit_entries`, is a superuser or a member of one (then no guard can hold). The superuser runs `ops/postgres/audit-guard.sql` once ([install-server.md](install-server.md), "The audit log's guard"), and again after a restore |
| `live_updates` | this process's Solid Cable listener has stopped, so it delivers no live update to any open page until the server restarts, while the pages still look connected (#194). The log says `[health] Solid Cable's listener thread has stopped`. Restart the app container. A PostgreSQL restart is survived: the listener retries its connection for about 28 s (`reconnect_attempts` in `config/cable.yml`), so only a longer outage stops it. With several Puma processes, each answers for itself |

## Job queues

The app's jobs use three queues (`cmdb/config/queue.yml`), each with a worker of its own. `realtime` holds the jobs that run every minute (liveness, task leases and expiry, rollout timeouts, report request expiry) and the dashboard's live refreshes, so a long advisory refresh, upload import, or matching run never delays them. `default` holds everything else; its worker also takes realtime jobs when it has a free thread. `evaluation` holds the batches of fleet-wide CIS evaluation and advisory re-matching (#197), so a fleet-wide run never holds the threads per-host work and imports need. The failed-jobs page shows each job's queue. Sizing the workers: [scaling.md](scaling.md).

## Failed jobs

Every job is retried 5 times with a growing delay (about 3 s, 18 s, 83 s, 4 min). After the last failure the job is kept as failed. Signed in, the dashboard shows a red banner with the count of jobs that failed in the last 24 hours, linking to **Failed jobs** (`/jobs/failed`): the time, job, queue, and error of each, newest first (the newest 100). The page is read-only. Retrying or discarding a failed job is done from the server console for now.

## Fleet-wide evaluation

A rule change and an advisory import re-evaluate the fleet in the background (#197). Each is a run of batches of at most 1,000 hosts on the `evaluation` queue, which has its own worker, so liveness, leases, and live updates never wait behind it. While a run is unfinished, the rule's page (for a rule change) or **Data sources** (for an import) says how many hosts are done. Only that line refreshes, first after 3 s and then less often, up to once a minute; it does not keep a signed-in session from timing out. If the run has not moved for 10 minutes, the line says so and stops refreshing: check that the job workers are running. A failed batch is retried on its own like any job; after its last attempt it appears under **Failed jobs** and the run **stops**: the line says "Stopped", how many hosts were done, and offers a button. For a run that had been split into batches it is **Check the remaining hosts** (or **Re-match the remaining hosts**, **Re-triage the remaining hosts**), which carries on from the batches it had left; for one stopped before that, **Check every host again** (or **Re-match again**, **Re-triage again**), which starts it over. A second press changes nothing. If a worker is killed instead (a deploy's restart that goes past the 5 s shutdown timeout, or the OOM killer), Solid Queue fails its job without a retry. `EvaluationRunWatchJob` (every 10 minutes) then resumes any run, of any kind, untouched for 10 minutes whose jobs are gone (a job waiting for its retry counts as live): its fan-out is queued again, which prepares a run not yet split again, or queues its remaining batches; a run with no batches left is finished. Only resumes with no progress since the last one count: after 3 in a row the run stops with "Its work was stopped 4 times, with no progress after the first", and the button, which starts the count again. Check the job workers' memory and restarts before you press it: the same batch on the same worker most likely stops again (#278). Preparation (before a run's hosts are found, when its line says "starting") has no checkpoint and is not progress: a resume prepares again from the start. An import's preparation matches every chunk holding its sources again, which for a widely used source (a kernel) at a million hosts takes long enough that 4 deploys during it fail the run; it then says "Stopped: before its hosts were found", and its button starts it over. A run that failed by raising every retry is never resumed. A later change to all the same rules, or an import of all the same sources, replaces a stopped run too. A rule change costs well under a millisecond a host, so it finishes in seconds on one thread; re-matching after an import costs about 10 ms a host, and that is where more `EVALUATION_THREADS` help.

## Logs

In production the server writes one JSON object per line to standard output:

```json
{"time":"2026-11-02T13:44:51.432Z","level":"INFO","message":"request completed","request_id":"…","host_id":12,"report_id":"…","event":"request","method":"POST","controller":"Api::V1::InventoryReportsController","action":"create","status":200,"duration_ms":28.6}
```

`request_id` is the `X-Request-Id` response header and the `request_id` in every API error body. To trace an agent report, search the log for its `report_id` or the request id the agent logged. Query strings, headers (including `Authorization`), and request bodies are never logged; secret-like parameters are filtered.

## Retention

History older than the retention window is removed: inventory, config, and package snapshots, host status events, CIS result changes, report ids, report requests, advisory refresh attempts, and vulnerability findings resolved before the window. Each host's newest snapshot of each type and newest status event are always kept, and so are current CIS results, open and reopened findings, the newest refresh attempt, advisory and triage data, and their imports. Recent report ids, which only recognise a retried report, are kept 7 days whatever the window. Audit entries are never deleted.

- **The history tables are partitioned by time** ([ADR 0027](../decisions/0027-time-partitioned-history.md), #195): report ids by day; snapshots, status events, and CIS result changes by week (30 days when the window is over 180 days); the audit log by month. Every hour (minute 23), `PartitionMaintenanceJob` creates partitions ahead (3 days, 3 weeks, 3 months) and drops whole every partition whose range is all past the window: one catalog operation, not a delete per row. A host's newest snapshot or status event in a partition being dropped is first moved forward to the current partition (its id is kept). So rows are kept for **at least** the window, and up to one partition longer.
- **The rest is deleted in batches** once a day (03:17 server time, `RetentionPruneJob`): report requests, refresh attempts, resolved findings, and, after the upgrade that partitioned the tables, the rows from before it, which sit in each table's `_legacy` partition until that partition is past the window and dropped whole too.
- **The audit log** is partitioned by month too, but no partition of it is ever detached or dropped. It fails closed: before the superuser's guard step it has no default partition, and after it a default that refuses every row (see "Partitions").

```sh
bin/rails settings:show                  # shows retention.days (default 90)
bin/rails settings:retention DAYS=120    # 7 to 3650; audited
```

A dry run (counts only) from the Rails console: `RetentionPruneJob.perform_now(dry_run: true)` for the row deletes, `PartitionMaintenanceJob.perform_now(dry_run: true)` for the partitions it would drop. The log lines `[retention] deleted … older than …` and `[retention] retired partitions …` state the counts of every run.

After pruning, the same job collects the package sets and chunks no host and no kept snapshot uses any more (a package snapshot the default repair set aside still counts, see Partitions below), once unused for two days (ADR 0028; log line `[package store] collected package_sets=… package_chunks=…`). Hosts with the same packages share one stored set, so there is nothing to clean by hand. `bin/rails packages:check_snapshots` checks the store's references (a dpkg snapshot or host with no set, or an id that names nothing) and exits non-zero if it finds any; that would be a bug worth reporting. `bin/rails vulnerabilities:match` matches every package chunk and every host against the advisory data again.

## Partitions

The history tables' time partitions ([ADR 0027](../decisions/0027-time-partitioned-history.md), #195). The dashboard's **Database maintenance needs attention** banner and `/health`'s `partitions` check point here.

Each table except the audit log has a `_default` partition, normally empty, so a write never fails because a partition is missing. When it has rows that a partition about to be created would cover, the next hourly run sets it aside (detached and renamed `<table>_default_moving`, with an empty default in its place, in one short transaction), creates the partitions, then moves the rows back 1,000 at a time, each batch its own short transaction, and drops it: no lock on the table is held while rows are copied, and until a row is moved back it is not seen. A run that stops part-way carries on at the next one. Each DDL statement waits at most 150 ms for its lock (3 tries a run), and nothing is done while `pg_dump` is dumping the database; whatever waits is done the next hour, and `/health` warns after 3 days. Only one maintenance run works at a time (a PostgreSQL advisory lock): a boot-time `partitions:ensure`, the hourly job, and a manual run that would overlap skip and say so. A partition the job retires is detached, renamed `<partition>_retired`, and dropped; if the drop fails, the next run drops it. A partition an operator detached by hand keeps its name and is never dropped by the job. `bin/rails partitions:status` lists each table's partitions and any problem; `bin/rails partitions:ensure` creates the ones ahead now. These tables have no foreign keys (with them, every partition operation would lock `hosts`), so `PartitionCheckJob` checks every night (04:41) that recent rows name a host and rule that exist. If not, it logs `[partitions] rows with no matching host or rule` as an error, and for two days `/health`'s `partitions` check is a warning and the dashboard banner names the table and column (`bin/rails partitions:check` runs it now). There is nothing to install in PostgreSQL; `pg_partman` is not used.


**What a problem means, and what to do:**

- **The default partition has rows**, or **rows set aside from the default partition are still being moved back**: rows arrived for a time with no partition, usually because maintenance did not run. The next hourly run moves them; if the line stays, check that the jobs run (`job_liveness`, Failed jobs) and run `bin/rails partitions:ensure`. While rows are set aside, a retried report is still recognised and CIS evaluation still reads each host's latest config snapshot; the history pages do not show the set-aside rows until they are moved back.
- **Fewer than 2 partitions created ahead**, or **a partition ahead has been missing for 3 days**: maintenance has not been creating partitions. For the audit log this is **failing**: audited actions (operator changes, enrolments, task steps) fail once its months run out. Run `bin/rails partitions:ensure` now, then find why the hourly job does not run.
- **A partition has been due for retirement for 3 days**: retention has not dropped old history. Usually a lock that was never granted in 150 ms (a long query or a backup running at every attempt); `bin/rails partitions:status` and the log's `[retention]` lines say which table.
- **Partition maintenance has been skipped since …**: every hourly run for over 3 hours found a backup running or another run holding the maintenance lock. A stuck backup, or a run that never ended: check `pg_stat_activity` for a `pg_dump` or a long-running session.
- **Recent rows name a host or rule that does not exist**: the nightly orphan check found rows a foreign key would have refused. It should not happen; report it with the log's `[partitions] rows with no matching host or rule` line.
- **The audit log's guard does not hold** (production only, and `/health`'s `audit_guard`): see [install-server.md](install-server.md), "The audit log's guard". The line says why: not installed yet, a role that is or can become a superuser (a member of a superuser role included), a search path other than `public`, a month no longer attached, code of the app's role on an audit table, or another change that got past it. Do not query the audit tables as the superuser to look (install-server.md says why); connect as `cmdb`.

## Advisory data

The server downloads OSV advisory data every 6 hours (`FLEET_ADVISORY_FEED_URL`, outbound HTTPS to `storage.googleapis.com` by default; `cmdb/README.md`, "Advisory data"). The fleet page says when each ecosystem's data was last updated, and shows a warning when it is older than `FLEET_ADVISORY_MAX_AGE_HOURS` (48 by default) or has never been refreshed. Until then, vulnerability findings may be missing.

- **A failed refresh** is retried 5 times with backoff, then appears on the failed-jobs banner and page as `AdvisoryFeedRefreshJob`, in `/health` as `failed_jobs`, and in the audit log as "Advisory import failed" with the reason.
- **A refresh held back** ("The last advisory refresh was held back"): the feed's archive would have marked more than 10% of an ecosystem's advisories withdrawn (`FLEET_ADVISORY_WITHDRAW_SHARE`), so nothing was imported and the data may be going stale. It is not a failed job and is not retried. Check the feed (a truncated or wrong archive does this); if the withdrawals are right, confirm the counts on the refusal's page on the Data sources page, or run `ALLOW_WITHDRAWALS=<ecosystem>:<count> bin/rails advisories:refresh` with the counts it prints. `bin/rails advisories:import FULL=1` refuses the same way and takes the same `ALLOW_WITHDRAWALS`.
- **To refresh now:** `bin/rails advisories:refresh`. To see freshness and the last import: `bin/rails advisories:status`.
- **A failed upload import** (Data sources page) is retried 5 times with backoff unless the file cannot be read, then appears on the failed-jobs page as `AdvisoryUploadImportJob`, with the import failed and its reason on the page and in the audit log. An upload whose job never finished is failed and its stored file deleted after an hour by `AdvisoryUploadPruneJob`.
- **A server without internet access:** set `FLEET_ADVISORY_FEED_URL=` (empty). Download `all.zip` elsewhere, copy it over, and run `bin/rails advisories:import FILE=all.zip FULL=1`, not by upload: uploads are for small files (up to 64 MiB), and the Debian archive is about 80 MB and growing. `FULL=1` says it is the complete data set, so it counts as a refresh. A single advisory file adds data but does not.
- **Signed kernel images and shim** (#270). Debian's advisories name the source package that builds the code (`linux`, `shim`), but the running kernel's signed image (`linux-image-6.12.48+deb13-amd64`) and its metapackage `linux-image-amd64` come from `linux-signed-amd64` (`linux-signed-arm64` on arm64), and `shim-signed` from `shim-signed`. The server matches those as `linux` and `shim` too, from the table in `cmdb/config/signed_sources.yml`, and still under their reported source, so a mapping only adds findings. A finding on them shows source `linux` or `shim`, the installed version as dpkg reports it, and Debian's triage for that source. A kernel image's version is `linux`'s own; `shim-signed`'s is `<shim-signed version>+<shim version>`, and when the shim part cannot be read the package is listed as not evaluated with that reason. shim's advisories also open on `shim-unsigned` (pulled in through `shim-helpers-<arch>-signed`), but only `shim-signed` says whether the shim that boots is fixed: `shim-unsigned` may be newer.
  - **Left out on purpose:** `grub-efi-<arch>-signed` (it depends on `grub-common` at its exact `grub2` version, so `grub2`'s findings are on `grub-common` and move with it), `shim-signed-common` (scripts, not shim), `shim-helpers-<arch>-signed` (its version cannot be turned back into shim's; shim's findings are on `shim-unsigned` and `shim-signed`), and `fwupd-<arch>-signed` (built from `fwupd-efi`, for which Debian lists no CVE yet; a future one needs a row or #271).
  - **Adding a row** (another architecture or kernel series) is a change to the file, checked when the server starts. Chunk verdicts are kept until an import changes their sources' advisories, so then queue a re-match of the row's source: `bin/rails vulnerabilities:rematch SOURCES=linux`. It runs in the background like an import's, and its progress line on **Data sources** says it re-matches after a change to how packages are matched.
  - **Kernel advisory imports reach the whole fleet.** Every amd64 and arm64 host has a signed image, so an import that changes any `linux` advisory, which Debian does most days, re-matches every such host, not only the ones with headers or `linux-libc-dev`. See [upgrades.md](upgrades.md#signed-kernel-images-get-their-findings-270) for what it costs; #273 tracks reducing it.
- **Backports** (#274, `Ecosystems::BACKPORTS`, [ADR 0011](../decisions/0011-vulnerability-data.md)). A package from trixie-backports (`linux-image-7.3.4+deb13-amd64` 7.3.4-1~bpo13+1) is built from forky's version, and trixie's advisories follow trixie's own series (6.12 for the kernel). So a package whose version has `~bpo13+` is also matched against `Debian:14` (forky) advisories, which the import keeps for this, and still against trixie's. The host's **Vulnerabilities** tab lists its backports and says how they are matched.
  - **Only once forky's data is complete**: a full import (the scheduled refresh, or `advisories:import FULL=1`) has kept `Debian:14`. A malformed `Debian:14` entry is skipped and counted on its own, never the record's `Debian:13` data. **Data sources** says whether it is complete, since which import, and how many entries and records that import skipped as malformed; the tab says so too. Until then backports are matched on trixie's data alone, as before #274.
  - **Only adds.** An advisory that affects the backport under either release's data opens a finding, so a CVE trixie has not fixed still shows on a backports kernel even when forky has.
  - **Forky's fix is not "Fix available".** A finding forky's data fixes shows "Fixed in 7.1.3-1 in the release this backport is built from; no backport of it known yet". It is not counted as fixable, on the Compliance page or the fleet list, because this server cannot tell whether trixie-backports has such a build. A backports kernel's finding moves to K1 ("reboot into it") only when a backport at or above the fix is installed. dpkg sorts 7.1.3-1~bpo13+1 just below 7.1.3-1, as OSV does, so the backport of the fixing version itself does not resolve it.
  - **Resolution.** Fixed when forky's advisory names the source and the version is outside its ranges. Not affected when forky's data names the source but not in this advisory (OSV leaves out releases that are not affected), or neither release names it.
  - **Kept open.** When only trixie's data says a backport's finding is fixed and forky's data has nothing for its source at all, the finding stays open ("Kept open" in its Fixed in column, and a count on the tab). It is still triaged: KEV, EPSS, listeners, controls, and the installed version reach it. It never opens on another host. A finding trixie's fix had resolved as fixed (before the upgrade, or before forky's data was complete) is reopened, since that was no evidence for a backport. It resolves when the package is removed, the advisory is withdrawn, or forky's data names the source.
  - **Debian's triage for trixie** is not shown beside a backport's finding and is not counted in the "Debian: no security update planned" chip. It does not make a backport's finding Ignorable or Low risk (I3, I4, I5, L4, F2, and L2 by the tracker's local scope); a remote scope and an end-of-life urgency still escalate it.
  - **Cost.** A change to an advisory that names only forky (a CVE in code only newer series have) re-matches only the hosts holding a backport of its source, through a small partial index on backports. One that names trixie too re-matches as before. `bin/rails vulnerabilities:rematch_backports` re-matches every backport, and only those.
  - **Known limits** (#304): trixie-backports-sloppy builds after forky's release are matched as forky's, and `Debian:14`'s freshness is not shown.
- **Debian triage** has its own section below.

## Debian triage

Debian's own triage of each CVE (status, urgency, and no-DSA, postponed, or ignored notes) is shown beside findings on each host's Vulnerabilities tab and package pages. It comes from the Debian Security Tracker, a second data source beside OSV ([ADR 0022](../decisions/0022-distribution-triage.md), P2-S16; details in `cmdb/README.md`, "Debian triage"). The **Debian Security Tracker** panel on the Data sources page shows its status, problems, and latest imports; this section explains them.

- **Triage only.** It never changes a finding's state, its severity, or any count; those come from the OSV data. A failed or held-back tracker refresh never stops the OSV refresh or matching.
- **Releases.** `cmdb/config/triage_releases.yml` maps a host's OS to the tracker's release name (`debian` `13` is `trixie`). Only releases an active host reports are imported, and the others in the file are skipped. A release appears on the panel when an active host uses it and is imported at the next refresh. When no active host uses a listed release, the refresh downloads nothing, and its import says so.
- **Out of date.** A release's data is stale when its last successful import is older than `FLEET_ADVISORY_MAX_AGE_HOURS` (48 by default, the same limit as the OSV data), or it was never imported. Stale triage is not shown beside findings; they say Debian's triage is not available, with the last import date. The panel's notice names the release and counts the failed refreshes since the last good import.
- **Schedule.** `DebianTriageRefreshJob` runs every 6 hours, 15 minutes after the OSV refresh (`cmdb/config/recurring.yml`). **Refresh now** on the advisory feed refreshes OSV and then the tracker, under the same cool-down; there is no separate button. Without the advisory feed, run `bin/rails advisories:triage_refresh` on the server.
- **Download.** One JSON document per refresh from `FLEET_DEBIAN_TRACKER_URL` (outbound HTTPS to `security-tracker.debian.org`), as a conditional request (ETag or Last-Modified), so an unchanged document is not downloaded again ("Not modified" on the panel). Limits: `FLEET_DEBIAN_TRACKER_MAX_DOWNLOAD_MB` (512 MiB by default) and 15 minutes for the whole exchange. Only the source's host and path are shown on the panel; the URL is set in the server's configuration ([configuration.md](configuration.md)), not in the dashboard.
- **A failed refresh** is retried 5 times with backoff, then appears on the failed-jobs page as `DebianTriageRefreshJob` and in the audit log as "Debian triage import failed", with the reason.
- **A refresh held back.** An import that would remove more than `FLEET_ADVISORY_WITHDRAW_SHARE` (10%) of a release's stored entries keeps that release's previous data, is audited as "Debian triage import held back" with the counts per release, and is not a failed job. The kept data is still shown beside findings until it goes stale. There is no button to accept it: the next refresh tries again. If the drop is right, run `bin/rails advisories:triage_refresh` with the `ALLOW_DROPS=<release>:<count>` it prints.
- **No upload.** The tracker has no upload form. A server without internet access sets `FLEET_DEBIAN_TRACKER_URL=` (empty, which turns the refresh off; the panel says "Turned off on this server"), downloads the document elsewhere, and runs `bin/rails advisories:triage_import FILE=json` on the server.
- **History.** The panel lists the latest 10 imports with a short summary. Every import, with its full counts per release, is in the audit log.

## Exploitation signals

Two exploitation signals feed the triage buckets ([ADR 0032](../decisions/0032-vulnerability-triage-buckets.md), VT-SIGNALS): **CISA's Known Exploited Vulnerabilities catalog** (KEV, rule N1) and **FIRST's EPSS scores** (rule N2). The server fetches both; agents never contact them. Each has a panel on the Data sources page with its freshness, entries, problems, and latest imports.

- **Signals only.** Neither ever opens, resolves, or reopens a finding, or changes its severity or the open count. A failed or held-back refresh never stops the advisory refresh, Debian triage, or matching. What changed (CVEs added to or removed from KEV, CVEs whose EPSS band changed, advisories whose CVSS vector or severity changed) is queued for the triage run in `triage_signal_changes`; the triage run processes it ("Triage buckets", below).
- **Stale data is still used.** Data is out of date when its last successful import is older than `FLEET_SIGNAL_MAX_AGE_HOURS` (168, shown as 7 days), or, for EPSS, when the score date in the file is. Out of date, the last stored data keeps being used and nothing is rewritten; the panel and the freshness line on the fleet, Compliance, and host pages say "out of date" and "still used". Turning a source off (its URL setting empty) keeps its last data too. Never imported, nothing is checked against it.
- **Schedule.** `KevRefreshJob` every 6 hours, 30 minutes after the OSV refresh; `EpssRefreshJob` daily at 14:30 UTC, an hour after FIRST publishes (`cmdb/config/recurring.yml`). **Refresh now** on the advisory feed refreshes both after the OSV data, under the same cool-down; there is no separate button. Without the advisory feed, run `bin/rails signals:kev_refresh` or `bin/rails signals:epss_refresh`.
- **Download.** Through the same fetcher as the advisory data: HTTPS with the certificate verified, a conditional request, 15 minutes for the whole exchange, and retries. KEV: `FLEET_KEV_URL` (CISA's GitHub mirror by default), at most `FLEET_KEV_MAX_DOWNLOAD_MB` (16), and no redirect to another host. EPSS: `FLEET_EPSS_URL`, at most 64 MiB compressed, 512 MiB uncompressed, and 2 million rows; its redirects are followed only to `FLEET_EPSS_REDIRECT_HOSTS` (a refused redirect fails the refresh and names the host it was sent to). Only each source's host and path are shown.
- **What is kept.** KEV: each CVE's date added, due date, known ransomware use, vendor, and product. EPSS: only the CVEs stored advisories name (about 40,000 of 300,000 rows), with the score, percentile, and band: high from 10% (`FLEET_EPSS_ENTER`) until it falls below 7% (`FLEET_EPSS_LEAVE`). An EPSS file older than the stored scores is refused, recorded as a failed import, and not retried; so is one dated more than a day ahead of the server's clock. Malformed rows are skipped and counted. Reading an EPSS file stops after 10 minutes, and the import's transaction is limited (5 minutes a statement, 1 minute idle).
- **How many match open findings** on each panel is counted by `SignalMatchCountJob`, queued after each import commits, and shown with when it was counted. While it runs the panel says "being counted". If a statement passes 5 minutes (a very large fleet), it says "too large to count" with the time; any other error is retried 3 times and then shown as "count failed" with the time, and logged. Neither ever marks the import failed. `bin/rails signals:recount` queues the count again for the latest imports.
- **A lost database connection** during an import (for example its 60-second idle limit inside the transaction) rolls the import back; the refresh job and the rake tasks record it as a failed import that says so.
- **A failed refresh** is retried 5 times with backoff, then appears on the failed-jobs page as `KevRefreshJob` or `EpssRefreshJob` and in the audit log as an import failure, with the reason.
- **A refresh held back.** An import that would remove more than `FLEET_ADVISORY_WITHDRAW_SHARE` (10%) of the stored entries stores nothing, is audited as held back with its counts, and is not a failed job. If the drop is right, run the refresh or import again with the `ALLOW_DROPS=<count>` it prints (a ceiling, not a bypass).
- **A server without internet access** sets `FLEET_KEV_URL=` and `FLEET_EPSS_URL=` (empty), downloads the files elsewhere, and runs `bin/rails signals:kev_import FILE=known_exploited_vulnerabilities.json` and `bin/rails signals:epss_import FILE=epss_scores-current.csv.gz` (a `.csv` works too).
- **A wrong EPSS score date.** If a bad file stored a date the real files cannot pass ("older than the stored scores of ..." on every refresh), run `bin/rails signals:epss_reset CONFIRM=1` (audited): it deletes the stored scores, rule N2 stops applying until the next import, and the next file imports whatever its date.
- **Clearing KEV data.** Stored KEV entries are deleted only by `bin/rails signals:kev_clear CONFIRM=1`, which is audited: rules N1 (known exploited) and I5 (Debian "unimportant" is ignorable once KEV data exists) stop applying until KEV is imported again.

## Triage buckets

Every open finding is in one of four buckets (Fix available, Needs attention, Low risk, Ignorable) by the first of 19 rules that matches ([ADR 0032](../decisions/0032-vulnerability-triage-buckets.md), [VT-BUCKETS](../backlog/specs/vt-buckets.md)). The bucket never changes a finding's state, severity, or the open count; the four bucket counts on each host's summary add up to its open count, also on a host that is not evaluated now (its kept findings keep current bases and KEV flags), once the upgrade's background re-triage has reached it.

- **Where it is decided.** The rules that do not depend on the host are computed for each chunk verdict when it is matched. The host's own rules (its running kernel: I1, K1, K2) are applied in its matching transitions. A new running kernel (`kernel_version` in an inventory report) re-matches that host.
- **A stopped re-triage run is resumed.** A run records what it changed as it goes. If its job fails every retry, the run is failed and its button on Data sources re-runs it: a run that had been split into batches (**Re-triage the remaining hosts**) carries on from the batches it had left, so a failed full run does not start again from scratch. If its worker is killed (a deploy's restart, the OOM killer), Solid Queue fails the job without a retry; `EvaluationRunWatchJob` (every 10 minutes, for runs of every kind: [Fleet-wide evaluation](#fleet-wide-evaluation)) resumes a triage run untouched for 10 minutes whose jobs are gone (a fan-out job waiting for its retry counts as live): its fan-out is queued again, which prepares it again or queues its remaining batches, and a run with no batches left is finished. Only resumes with no progress since the last one count: after 3 in a row it is failed instead, with its button (whose run starts the count again), while a long full run that makes progress between deploys is resumed every time once it has been split into batches. Its preparation (tens of minutes at a million hosts) starts again on a resume and is not counted as progress, so avoid four deploys in a row during it. A run waits, before it reads which chunks hold its advisories, for chunk matches that read the signals before they changed (a short lock wait), so none keeps an outdated bucket. A day naming more than 20,000 advisories (a first tracker import) re-runs each affected host's whole matching, about 80 ms a host instead of about 1 ms.
- **Re-triage runs.** When a signal or Debian's triage changes, a run on the `evaluation` queue (an `EvaluationRun` of kind `triage`) recomputes the chunk verdicts concerned, then re-matches only the hosts on sets holding a chunk whose bucket or KEV flag changed. A KEV import that changes the catalog starts one at once. EPSS band changes and Debian tracker changes wait for `TriageDailyJob` (daily at 15:37 UTC, an hour after the EPSS refresh), which starts one run for all of them if any is pending. The run shows on **Data sources** as "Re-triaging ..." with its progress. If it stops, **Re-triage again** there runs the same hosts again; `bin/rails vulnerabilities:triage` re-triages every host.
- **Stale or turned-off data changes nothing.** The rules use the stored KEV entries, EPSS bands, and tracker entries whatever their age. Only an import that changes stored data starts a re-triage. Clearing KEV (`signals:kev_clear`) re-triages every host, since rules N1 and I5 stop applying.
- **Tracker churn.** Each Debian triage import records, per release, how many entries the document added (`added`) and how many changed what the rules read (`changed`: status, urgency, fixed version, no-DSA, scope), in the import's counts in the audit log. The CVEs concerned are handed to the daily run.
- **Kernels.** `cmdb/config/triage_applicability.yml` says which packages are versioned kernel images (and which kernel release each boots) and which hold no runtime code (headers, `linux-libc-dev`, the flavour metapackages: Ignorable). It is checked when the server starts; a mistake stops it. An installed image that is not running is Ignorable; the running image's fix is "reboot" (K1) when a newer image at or above the fix is installed, else "install the new kernel package, then reboot" (K2). When no installed image is the running kernel (it was removed, or is not a Debian package), no kernel rule applies and the images' findings are triaged like any package's.
- **Work events.** A host's matching appends what its reports show done to `vulnerability_work_events` (an upgrade that resolved Fix available findings, a new kernel image that turned K2 into K1, a reboot that moved K1 to I1), weekly partitions kept 90 days ("Retention" and "Partitions", above). An advisory correction writes none.
- **Listening processes only escalate** (owner decision 2026-11-21). Once VT-APPLICABILITY (#258) supplies the evidence, a package that a process holding a listening socket loads cannot be Low risk (rule N5, Needs attention, naming the listener's package and whether it listens on the network). Nothing is ever lowered for a package not seen running. Evidence is used while the host's scan is at most 24 hours old: `TriageListenerExpiryJob` (hourly, from where its last run stopped) re-triages the hosts whose scan expired, and a change of evidence re-triages that host. Until VT-APPLICABILITY is deployed, neither does anything.
- **Finding decisions** (VT-OVERRIDES #261). An operator records, on a Needs attention or Low risk finding, that a compensating control is in place (rule O1: the finding moves to Low risk while it lasts) or that the risk is accepted (nothing moves; the finding only leaves "decisions due"), with a reason and a last day: at most `FLEET_DECISION_MAX_DAYS` (90) days, or `FLEET_DECISION_MAX_DAYS_KEV` (30) for an advisory on CISA's KEV list. Neither changes a finding's state, severity, or any open count. A control stops applying on the day after its last day. `FindingDecisionExpiryJob` (hourly, minute 7) ends the decisions past their last day (`vulnerability.decision_expired`) and suspends those whose evidence got worse than recorded: a CVE added to KEV, the EPSS band turning high, or the severity rising (`vulnerability.decision_suspended`, with what changed). Both re-triage the findings concerned. A host's matching and every triage run do the same for their hosts first, so a KEV listing suspends a control in the run it starts; they also end decisions whose findings got a fix or all resolved (`vulnerability.decision_ended`, by the system). Decisions are never deleted, and an ended one never changes; the database refuses both. The second factor is asked once a session has recorded more than 10 host decisions within 15 minutes, and every time on a KEV-listed advisory.
- **Suggested controls.** `cmdb/config/triage_controls.yml` holds a short text per kind of Needs attention finding, advice only, checked when the server starts.
- **Attribution.** The EPSS panel shows "See EPSS at https://www.first.org/epss", as FIRST's usage terms ask. KEV is public domain (CC0).
