# ADR 0031: Second scale step: optional pooler, direct connection, replica reads, and node roles

- Status: Proposed (needs the owner's OK)
- Decision issue: #198 (steps 2 and 3); the owner chose "app-side readiness only" on 2026-11-16
- Requirements: `NFR-3`, `FR-1.4`, `FR-S.2`, `NFR-4`
- Builds on: [ADR 0025](0025-first-scale-step.md) (the first step), and follows its plan that migrations run once on a direct connection. It departs from ADR 0025 and the #198 comment on one point: the direct connection is not jobs-only (below). Known limits ([ADR 0019](0019-scale-direction.md)): "deployment on one machine" stays the default; this makes the next step possible by configuration.

## Context

Past about 10,000 agents, #198 plans PgBouncer in transaction mode, a read replica for the dashboard, and separate agent-API and dashboard nodes behind a load balancer. None of that can be switched on today without code changes: Rails uses prepared statements and a session-level migration lock, two session-level advisory locks span several transactions (the liveness evaluation, #186, and a rollout stage prepare, review of #215), no page can read a replica, and every node serves both hostnames. The owner decided (2026-11-16) to build only what the app needs, as optional settings that are all off by default, so the homelab's one container and one PostgreSQL work exactly as before with no new required service. Running PgBouncer, a replica, or more nodes stays a deployment step for later.

## Decision

- **`FLEET_DB_POOLER=transaction`** turns off prepared statements and Rails' migration advisory lock on the pooled databases (primary, cache, queue, cable, and the replica). Unset, nothing changes.
- **Migrations never run through the pooler** (ADR 0025's "migrations run once on a direct connection"). With the pooler set, every task that migrates or loads a schema stops, and the entrypoint refuses to start a server unless `FLEET_DB_PREPARE=false`. Migrations run once per deploy in a one-off container from the same image, with its database URLs straight to PostgreSQL and the pooler unset, so Rails' lock is on. That one-off is the one migrating container, so no node has to be chosen. Rejected: migrating from a serving node over `DIRECT_DATABASE_URL`, which names the primary only, not the queue, cache, and cable databases.
- **`DIRECT_DATABASE_URL`**, required with the pooler: the primary without the pooler. `SessionLock` takes the two session-level advisory locks on it, and the work under the lock still runs on the pooled connection. Before each batch (and before a rollout prepare re-times a stage) the run checks the lock's server process id, so a lost and silently reopened lock connection stops it before its next write. A stopped liveness run is caught up by the next minute's; a stopped prepare keeps the batches it committed, hidden by the stage gate, and the next prepare continues from the database's count. Unset, the locks use the primary's own connection with exactly the statements they ran before: the check does nothing there. Every other advisory lock in the app is transaction-level and stays where it is. Solid Queue (`FOR UPDATE SKIP LOCKED` in transactions) and Solid Cable (it polls a table; no `LISTEN`) need no direct connection. Action Cable's PostgreSQL adapter, the one that uses `LISTEN`, is not used.
- **`REPLICA_DATABASE_URL`**: a streaming replica. `ApplicationRecord` gets a reading role, and only the dashboard and report pages named with `reads_from_replica` use it: the fleet list, compliance, the audit log, and a host's Configuration, Packages, Vulnerabilities, and Tasks tabs (GET only). A page reads the replica only once it has replayed the primary's WAL position read at the page's start, waiting at most `FLEET_REPLICA_MAX_WAIT_MS` (100 ms); otherwise it reads the primary. So no page shows older data than the primary would, and read-after-write needs no stickiness. A server that is not in recovery (a promoted ex-replica, or the wrong URL) is never read as one; only the test environment, whose replica is the test database, allows it. A failing replica, at its check or while a page reads it (a lost connection, or a recovery conflict), is skipped for `FLEET_REPLICA_SKIP_SECONDS` (30), and the page runs again on the primary; an error from the primary is never blamed on the replica. The replica's connect timeout is `FLEET_REPLICA_CONNECT_TIMEOUT_SECONDS` (2). Writes are refused on the reading role, and the test suite runs every listed page on it, which catches Active Record writes and row locks; a write inside a `SELECT` or `WITH` is caught only by a real standby. Agent API paths, every write, step-up (second-factor) checks, and the task list and task pages, which show step-up state, never use it.
- **`FLEET_NODE_ROLE`**: `all` (default), `agent_api` (refuses the dashboard hostname), or `dashboard` (refuses `/api` on the agent hostname, keeps the health paths). Jobs placement stays as today (`SOLID_QUEUE_IN_PUMA`, `bin/jobs`).
- **`FLEET_DB_PREPARE=false`** makes the entrypoint skip `db:prepare`, so with several nodes, or behind the pooler (with no migration lock), one container runs migrations and the others do not.
- Rejected: replacing the session locks with lease rows. That changes the homelab's behaviour and schema for a case a direct connection already covers. A lease is still possible later if a pooler must carry everything.
- Rejected: Rails' automatic role switching (`DatabaseSelector`). It routes every GET, including agent API reads and the pages that check a second factor, and guards read-after-write only by a time delay after the session's own writes. It does nothing for an agent's write or a live refresh.
- Rejected: a replica for the agent API's reads. Every agent request writes, and reads under the host lock.

## Consequences

- The homelab is unchanged: with nothing set, database.yml has the same four databases, no page switches role, every node serves both hostnames, the entrypoint migrates, and the two session locks run the same statements as before. That keeps one old weakness on the homelab: if the primary connection drops between two batches of a liveness run or a prepare, Active Record reopens it at the next transaction without the lock, and the run carries on unlocked. The direct path checks for that; the default path could too, at one statement a batch, if the owner wants it.
- The direct connection is opened by the jobs and by dashboard processes, because starting a rollout and an operator's Advance prepare the stage inside the request. So dashboard nodes need a route to the primary itself, not only to the pooler. Moving those prepares into a job would make it jobs-only, as ADR 0025 and the #198 comment planned; that is a change of behaviour (the operator would wait for the job), left to the owner.
- Each replica page costs two small statements: the primary's WAL position and the replica's check. On a replica that lags, it also waits up to the configured time before reading the primary. At step 3 write rates, replay can fall behind the primary's current position during WAL bursts (vacuum, imports, fleet-wide matching), so pages return to the primary just when it is busiest. A per-session "last write" position in place of the global one would keep read-after-write without that coupling; not built.
- No CI job runs the listed pages against a real standby; a reviewer did so by hand for #237 (all ten pages answered from it). A standby smoke test in Deploy CI is a possible follow-up.
- Separate nodes still share the release binaries and the backup status file on the storage volume (`FLEET_RELEASES_DIR`, `FLEET_BACKUP_STATUS_FILE`). Splitting nodes across VMs needs shared storage, or another home for release binaries. That is a decision for the deployment step.
- Running PgBouncer, the replica, the load balancer, and the deploy changes (`cd.yml` still deploys one VM), plus step 3 (partitioning, #195; queued ingestion), stay open in #198.
