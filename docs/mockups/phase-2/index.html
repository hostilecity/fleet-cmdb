Open design questions for the owner

Each is also a review note on the page named after it. The drawn choice is the recommendation; the alternative is in the note.

  1. Q1. Where the compliance summary sits. Drawn: one row of four summary tiles under the host header, on every tab, so the answer to "is this host in good shape?" is visible whichever tab is open, and each tile links to its tab. Alternatives: tiles on the Overview tab only (the other tabs start straight at their content), or a single summary line in the header next to the status lamp. Drawn on host-overview.html.
  2. Q2. CIS results as a section of the Configuration tab, as drawn, or as their own "Compliance" tab. Drawn as a section because every result is a judgement on one of the facts below it and the diff explains why a result flipped. A separate tab would give the 40-row list its own page and leave Configuration as facts and snapshots only. Drawn on host-config.html.
  3. Q3. The pass rate. Drawn as passed ÷ (passed + failed + not readable): a check that could not be read counts against the host, because "we could not look" is not a pass. Not applicable and not evaluated checks are left out. The fleet view uses the same number. The alternative is to leave not readable out too, which makes a host with unreadable files look better than it is. Drawn on host-config.html.
  4. Q4. Default filter. Drawn as "Needs attention" (fail and not readable), so the page opens on what an operator must act on and the 29 passes do not bury it. The other filters are one click away. The alternative is to open on All, grouped the same way. Drawn on host-config.html.
  5. Q5. How the diff picks two snapshots. Drawn: a comparison opens on its own page, from a "With the one before" link in this table or from the two pickers on that page, so any pair of snapshots has a bookmarkable address (?from=&to=). The default is the latest against the one before it, which is what an operator asks after an alert. Alternatives: tick two rows in this table and press Compare, or an in-page diff with no separate page. Drawn on host-config.html.
  6. Q6. The request button. Drawn: each tab asks only for its own report (Configuration asks for a config report, Packages for a package report), and the Overview keeps today's three-way form (Overview). Every state of the button is on Report request states. Alternative: one "Request fresh reports" button in the host header that always offers all three types. Drawn on host-config.html.
  7. Q7. Rate limit. Drawn: the button is greyed out with the retry time beside it, so the operator is told before clicking. Today's page leaves the button enabled and shows the rate-limit alert after the click. Either works with the server rule; the greyed button needs the page to know the retry time and to update when it passes. Drawn on report-requests.html.
  8. Q8. How the Phase 1 fleet list links to compliance. Drawn: a two-line summary panel under the status counts, plus two columns in the list (CIS pass rate and open vulnerabilities, each a link to the host's tab). Alternatives: the summary panel only, with the list unchanged and all per-host numbers on the Compliance page; or the two columns only. The columns cost width on a narrow screen, where the table scrolls sideways as it does today. Drawn on fleet.html.
  9. Q9. Sorting by worst, and where hosts that are not evaluated go. Drawn: "worst first" orders hosts by their critical findings (CIS failures plus vulnerabilities together), then high, medium, low, and unknown, then by lowest pass rate. Hosts with nothing evaluated at all sit below everything, shaded and labelled, so an unknown host is neither at the top as an emergency nor mixed in with the clean ones. Alternative: put not-evaluated hosts first, because an unknown host is a risk too. Status filter "Not evaluated" lists only them either way. Drawn on compliance.html.
  10. Q10. Decided: three new top-level items, as drawn. Drawn on rules.html.
  11. Q11. Decided: the dashboard adds one rule from a form, as drawn now. A rule with several conditions still arrives by importing a file. Adding a rule previews its results before saving, as editing does (decided on #126). Drawn on rules.html rule-create.html, and rule-create-preview.html.
  12. Q12. Decided: editing shows a preview of which hosts would change result before saving, as drawn now. It needs a server-side dry run (P2-S14). Hosts that would drop out to not applicable are listed, and an unchanged rule previews as no change (decided on #126). Drawn on rule-edit.html and rule-edit-preview.html.
  13. Q13. The preview. Drawn: uploading shows the preview; "Apply import" then applies exactly the file that was previewed, which the server keeps for a short time (about 15 minutes) and drops when you apply, cancel, or it expires. Alternative: ask for the file again on the apply step, which stores nothing but makes the operator pick the same file twice and risks applying a file different from the one previewed. The first needs a short-lived store of an uploaded file; say if that is not acceptable. Drawn on rules-import.html.
  14. Q14. Decided: "Refresh now" has a cool-down like report requests: it is greyed out with the time it can be used again, as drawn now. The feed itself stays editable only in the server configuration. Drawn on data-sources.html.
  15. Q15. A 3,000-package host. Drawn: server-side search, sort, and pages of 50 (the mockup draws 14 rows of the page). Search and sort are in the URL so a view can be bookmarked, as on the Phase 1 fleet list. The alternative is to render every row and let the browser scroll (virtual rendering), which needs JavaScript the Phase 1 screens do not use. Drawn on host-packages.html.
  16. Q16. Decided: findings are grouped by package with the advisories nested under it, as drawn now. Drawn on host-vulns.html.

Open design questions for P2-D07 (Debian's triage)

From the P2-DEBIAN-TRIAGE spec and ADR 0022. The drawn choice is the recommendation unless the question says otherwise.

  1. T1. Where the triage sits on the Vulnerabilities tab. Drawn: inside the advisory cell, under the summary, as a quoted line that starts with "Debian:", with no lamp, pips, or severity colour. Alternative: its own column. Recommendation: as drawn. A column widens a table that already scrolls on a phone, and a column next to Severity invites reading it as a second severity. The package page, which has room, does use a column. Drawn on host-vulns.html.
  2. T2. Manual refresh of the tracker. The schedule is shared (the spec runs it right after the OSV refresh). Drawn: the one "Refresh now" button refreshes the advisory data and then the tracker, under the same 5-minute cool-down. Alternative: a separate "Refresh now" on the tracker panel with its own cool-down. Recommendation: shared, as drawn. One button and one cool-down are simpler, Debian asks automated clients to fetch sparingly, the conditional request makes an unchanged file cost nothing, and a tracker failure still never blocks the advisory refresh. The refresh confirmation gains one sentence. Drawn on data-sources.html.
  3. T3. What the "Debian: no security update planned" chip matches. Drawn, as the spec says: entries with a no-DSA note and no reason, or reason postponed. In the tracker data, "ignored" is a third reason on the same no-DSA note. Recommendation: include ignored too, since no security update is planned for it either and an operator looking for "Debian will not ship a DSA" wants all three; the label stays the same. Drawn on host-vulns.html.
  4. T4. A held-back tracker download. Drawn: a row with the counts in the tracker's imports, and a status notice on the data sources page only while it is the latest; host pages keep showing the kept data until it goes stale; no button to accept the download. Alternative: a confirmation to accept it, like the advisory withdrawal guard's, and a notice on host pages too. Recommendation: as drawn. Triage changes no finding or count, so the safe failure (after 48 hours the triage shows as not available) is acceptable, and a real large drop, such as a release reaching end of life, is a release-mapping change rather than something to click through. Revisit if it happens in practice. Drawn on data-sources-held.html.
  5. T5. Triage on resolved findings. Drawn: on the Vulnerabilities tab only open and reopened rows show it, so the resolved table is unchanged; the package page shows it on every row as today's note for context. Alternative: show it on resolved rows on the tab too. Recommendation: as drawn, so that Debian's note is never read as the reason a finding resolved. Drawn on host-vulns.html and host-vuln-package.html.
  6. T6. Extra tracker fields: the CVE's scope (local or remote) and Debian's bug number. Drawn: scope on the package page only, the bug number not shown. Recommendation: as drawn. Scope helps judge a no-DSA note but would lengthen every row on the tab; the bug is one click away on the tracker's page, which is linked. Drawn on host-vuln-package-libc6.html.
  7. T7. The wording. Drawn: the category first, in our words, and Debian's own note text after it, verbatim and escaped, in quotation marks: no reason is "no security update planned (Minor issue)"; next_point_update adds "fix planned for the next point release"; postponed is "postponed to a later update or point release", not "to a point release", because Debian's postponed means a later DSA or point release; ignored is "ignored, no fix planned for this release"; urgency is shown only when assigned ("not yet assigned" is no urgency, and an entry with neither note nor urgency reads "not triaged yet"); undetermined is "not yet determined for trixie"; a resolved entry is "fixed for trixie in X" with a line saying the host's version is older, so the finding stays open. Recommendation: as drawn, with Debian's note text capped at 200 characters and shortened with an ellipsis. Please confirm the postponed wording. Drawn on host-vulns.html.
  8. T8. Stale triage. Drawn, as the spec says: past 48 hours, findings show "Debian triage not available" with the last import date, and the tab shows a blue information notice. Alternative: keep showing the last known triage marked "as of" its date. Recommendation: as drawn, because a stale note may since have changed (for example from postponed to fixed), and the Fleet list and Compliance show nothing, since their counts do not use the triage. Drawn on host-vulns.html and data-sources-stale.html.

Wording and data

  • The product says "CIS-aligned" and "passes N of M checks", and never claims a compliance level (ADR 0010). Rule titles and remediation are in our own words; the reference is a section number only, and the numbers here are examples.
  • Hosts are *.example.lan, addresses are documentation addresses, and advisory ids such as DSA-9100-1 are invented placeholders that name no real vulnerability. The one exception is CVE-2026-19499 (glibc), the example from ADR 0022, drawn with its real tracker entry; other CVE ids such as CVE-2026-99102 are placeholders. Package names such as acme-daemon are invented.
  • No JavaScript and no external requests. Fonts are the system stack; the app will self-host the Phase 1 fonts.
  • Accessibility: every table has headers, results and severities are words as well as colour and shape, filters and form fields have labels, and errors are announced and shown beside the field.
