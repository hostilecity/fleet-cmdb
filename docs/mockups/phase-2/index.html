Open design questions for the owner

Each is also a review note on the page named after it. The drawn choice is the recommendation; the alternative is in the note.

  1. Q1. Where the compliance summary sits. Drawn: one row of four summary tiles under the host header, on every tab, so the answer to "is this host in good shape?" is visible whichever tab is open, and each tile links to its tab. Alternatives: tiles on the Overview tab only (the other tabs start straight at their content), or a single summary line in the header next to the status lamp. Drawn on host-overview.html.
  2. Q2. CIS results as a section of the Configuration tab, as drawn, or as their own "Compliance" tab. Drawn as a section because every result is a judgement on one of the facts below it and the diff explains why a result flipped. A separate tab would give the 40-row list its own page and leave Configuration as facts and snapshots only. Drawn on host-config.html.
  3. Q3. The pass rate. Drawn as passed ÷ (passed + failed + not readable): a check that could not be read counts against the host, because "we could not look" is not a pass. Not applicable and not evaluated checks are left out. The fleet view uses the same number. The alternative is to leave not readable out too, which makes a host with unreadable files look better than it is. Drawn on host-config.html.
  4. Q4. Default filter. Drawn as "Needs attention" (fail and not readable), so the page opens on what an operator must act on and the 29 passes do not bury it. The other filters are one click away. The alternative is to open on All, grouped the same way. Drawn on host-config.html.
  5. Q5. How the diff picks two snapshots. Drawn: a comparison opens on its own page, from a "With the one before" link in this table or from the two pickers on that page, so any pair of snapshots has a bookmarkable address (?from=&to=). The default is the latest against the one before it, which is what an operator asks after an alert. Alternatives: tick two rows in this table and press Compare, or an in-page diff with no separate page. Drawn on host-config.html.
  6. Q6. The request button. Drawn: each tab asks only for its own report (Configuration asks for a config report, Packages for a package report), and the Overview keeps today's three-way form (Overview). Every state of the button is on Report request states. Alternative: one "Request fresh reports" button in the host header that always offers all three types. Drawn on host-config.html.
  7. Q7. Rate limit. Drawn: the button is greyed out with the retry time beside it, so the operator is told before clicking. Today's page leaves the button enabled and shows the rate-limit alert after the click. Either works with the server rule; the greyed button needs the page to know the retry time and to update when it passes. Drawn on report-requests.html.
  8. Q8. How the Phase 1 fleet list links to compliance. Drawn: a two-line summary panel under the status counts, plus two columns in the list (CIS pass rate and open vulnerabilities, each a link to the host's tab). Alternatives: the summary panel only, with the list unchanged and all per-host numbers on the Compliance page; or the two columns only. The columns cost width on a narrow screen, where the table scrolls sideways as it does today. Drawn on fleet.html.
  9. Q9. Sorting by worst, and where hosts that are not evaluated go. Drawn: "worst first" orders hosts by their critical findings (CIS failures plus vulnerabilities together), then high, medium, low, and unknown, then by lowest pass rate. Hosts with nothing evaluated at all sit below everything, shaded and labelled, so an unknown host is neither at the top as an emergency nor mixed in with the clean ones. Alternative: put not-evaluated hosts first, because an unknown host is a risk too. Status filter "Not evaluated" lists only them either way. Drawn on compliance.html.
  10. Q10. Navigation. Drawn: three new top-level items, Compliance, Rules, and Data sources, between Fleet and Agents. Seven items still fit one line on a laptop and wrap on a phone. Alternative: one "Compliance" item whose page has the fleet table, with Rules and Data sources as tabs inside it, which keeps the bar at five items but hides rules two clicks deep. Drawn on rules.html.
  11. Q11. Creating a rule. The scope lists import, view, edit, enable and disable, but no "Add rule" button, so none is drawn: new rules arrive by importing a file, and the UI edits existing ones. A form that creates one rule would be a small addition (the server already creates rules through the same path as import). Do you want it? Drawn on rules.html.
  12. Q12. Editing. Drawn: a form for the common case, a rule with a single comparison, with the operator and expected value as two fields (this is what AC-2.2 edits). A rule built from several conditions (all, any, not) shows the condition as a text box holding YAML or JSON instead, checked as you save (example with errors). Not drawn, because the scope does not ask for it: a preview of which hosts would change result before saving. The server could compute it; the import preview is the only place the scope asks for one. Do you want it on edit too? Drawn on rule-edit.html.
  13. Q13. The preview. Drawn: uploading shows the preview; "Apply import" then applies exactly the file that was previewed, which the server keeps for a short time (about 15 minutes) and drops when you apply, cancel, or it expires. Alternative: ask for the file again on the apply step, which stores nothing but makes the operator pick the same file twice and risks applying a file different from the one previewed. The first needs a short-lived store of an uploaded file; say if that is not acceptable. Drawn on rules-import.html.
  14. Q14. Manual refresh and upload. Drawn: "Refresh now" and the upload form sit on this page beside the scheduled feed, each with a confirmation where it can resolve findings (Confirmations). The refresh button has no rate limit drawn, because the server already makes a refresh conditional (an unchanged feed downloads nothing). Is a cool-down like the report-request one wanted? Also: the feed itself can only be changed in the server configuration, not on this page, since it carries a token; say if you want it editable here. Drawn on data-sources.html.
  15. Q15. A 3,000-package host. Drawn: server-side search, sort, and pages of 50 (the mockup draws 14 rows of the page). Search and sort are in the URL so a view can be bookmarked, as on the Phase 1 fleet list. The alternative is to render every row and let the browser scroll (virtual rendering), which needs JavaScript the Phase 1 screens do not use. Drawn on host-packages.html.
  16. Q16. One row per package and advisory, as drawn, or grouped by package with the advisories nested under it. Drawn as rows because that is how findings are stored and filtered; the per-package page (click a package name) is the grouped view for one package. The alternative makes a package with several advisories one row, and the severity filter harder to read. Drawn on host-vulns.html.

Wording and data

  • The product says "CIS-aligned" and "passes N of M checks", and never claims a compliance level (ADR 0010). Rule titles and remediation are in our own words; the reference is a section number only, and the numbers here are examples.
  • Hosts are *.example.lan, addresses are documentation addresses, and advisory ids such as DSA-9100-1 are invented placeholders that name no real vulnerability. Package names such as acme-daemon are invented.
  • No JavaScript and no external requests. Fonts are the system stack; the app will self-host the Phase 1 fonts.
  • Accessibility: every table has headers, results and severities are words as well as colour and shape, filters and form fields have labels, and errors are announced and shown beside the field.
