## P2-D01: Phase 2 dashboard mockups (config, packages, vulnerabilities, compliance, rules)

### Scope

Static HTML mockups in `docs/mockups/phase-2/`:

- Host detail tabs: configuration (facts, CIS results, snapshot diff, request-fresh-report button), packages (current set, snapshot diff), vulnerabilities (open and resolved)
- Fleet compliance view with pass rate and severity counts
- Rules management: list, view, edit, enable and disable, version history, import
- Advisory data sources and freshness indicator

## P2-D02: Host configuration view: facts, CIS results, snapshot diff

### Scope

- Latest config facts grouped by area, with unreadable and unsupported facts shown with their reasons.
- CIS results per rule (pass, fail, not applicable, not readable, not evaluated), filterable, with severity, observed value, and remediation text; per-host summary; result change history.
- Snapshot picker and diff between any two config snapshots.
- "Request fresh report" button using [P2-S03](p2-config-reports.md), showing outstanding state.
- Everything agent-derived is escaped.
- Delivered as `GET /hosts/:id/config` and `GET /hosts/:id/config/compare?from=&to=` (snapshot ids; by default the latest against the one before it), `HostConfigsController`, with the host header, summary tiles (`HostSummary`), and tab bar shared by every host tab (`HostTab`, `hosts/_header`), as the approved mockups and owner decisions Q1 to Q7 on the P2-D01 review say. The "Last reports received" tile (owner decision on #255, `ReportSchedule`) judges each report type against the interval the server knows for it: the operator's inventory interval in Settings or the agent's default of 15 minutes, and the agent's default of 6 hours for config and package reports (the config report interval is set in the agent's own config file and not reported). Its headline is "On schedule" when every type is within twice its interval; "Config and packages overdue" (the types' names) when a type is older than that; "Missing packages" when a type has not arrived within one interval of the host being first seen (the Packages tab's "within 6 hours of enrolling"); both, joined, when both apply ("Missing packages, config overdue"); and "Waiting for packages" for a type still within that grace period. Under it, one line per type in the order config, packages, inventory: "Config 3 hours ago", "No package report yet" for a type never received (worded the same on the compliance page), and "Packages about 13 hours ago, older than 12 hours" for an overdue type. Before any report, until the inventory is missing too, the tile says "None yet". The ages are worked out when the page is drawn: a report that changes nothing else does not refresh an open page, so they stay as drawn until the next refresh (a known limitation). The pass rate is passed / (passed + failed + not readable) (`CisCompliance::Summary#pass_rate`, Q3). Checks open on "Needs attention" (fail and not readable, Q4), grouped by the area of the fact they inspect (`ConfigArea`); facts show the ones a rule inspects or that are not OK, `?facts=all` for all. The cause of each result change (new config report with the fact before and after, rule edited with its editor, enabled, disabled) is worked out by `CisResultHistory` from the change before it, since a change does not record why its evaluation ran. The comparison lists result changes produced from the snapshots in the range as the effect of each changed, added, or removed fact, joining a rule's report changes only while no rule edit, enable, or disable comes between them; those rule changes are listed apart. A change of reason alone (unreadable for another reason) is shown with the state changes. The pickers offer every snapshot kept, with the newest 25 labelled by how many facts changed. The pickers are labelled "From" and "To" because Swap compares newer to older. The tab's request button asks for a config report only; its states (ready, pending before and after delivery, rate limited until a time, answered, expired, host cannot be asked) follow report-requests.html, and a rate-limited button refreshes the page when the limit ends (the `refresh-after` Stimulus controller, timed by the server's clock). An answered or expired outcome is shown for an hour after it ended.

### Acceptance criteria

- [ ] A changed SSH setting shows in the diff and flips the matching rule result (AC-2.1)
- [ ] Unreadable facts show their reason in the facts list and in dependent rule results (AC-2.5)
- [ ] The request button shows pending state and is rate limited

## P2-D03: Host packages view and snapshot diff

### Scope

- Current package set with search, sort, and a count; shows the package manager and the source package.
- Snapshot picker and diff showing installs, removals, and version changes.
- Explicit state for an unsupported package manager.
- Pagination or virtual rendering so a 3,000-package list stays fast.
- Delivered as `GET /hosts/:id/packages` and `GET /hosts/:id/packages/compare?from=&to=&kind=` (snapshot ids), `HostPackagesController`, under the shared host header, summary, and tabs. The list is `HostPackageList`: server-side search of the package and source package name, architecture and "open findings only" filters, sort by name, version, or source package, and pages of 50, all in the URL (owner decision Q15); a page is a fixed number of queries whatever the package count. Version sorts as text, since dpkg's order is not available in SQL; the diff, which uses dpkg's order (`PackageDiff`), says which way a version moved. Each row shows its open findings (count, and whether one was reopened). An unsupported package manager is said so in the tab, the tab's count, the summary tile, and the snapshot list, and a pair with an unsupported side has no diff. An unreadable package database (P2-S08, owner decision) is said so in a notice with the agent's reason and the last readable report's time, the tab's count ("Unreadable" when no list was ever read), the summary tile, and the snapshot list; the kept list is still shown, and the diff of an unreadable snapshot is not available, while the snapshot after it is compared with the one before it. The comparison shows installed, removed, upgraded, downgraded, cannot compare, source changed (the same version with another source package), and equivalent version (a version dpkg treats as equal that is spelled differently, such as `1.0` and `0:1.0`; its own counter and chip, only when there is one, a deviation from the mockup), and "Skipped / incomplete" (a package that was installed and is named in the later snapshot's skipped list, with the agent's reason, never shown as removed), "Install completed" (a package the earlier snapshot skipped and the later one lists, with the earlier reason), and "Removed, was skipped" (a name the earlier snapshot skipped that the later one neither lists nor skips; no version or architecture is known) each in its own row, counter and filter that appear only when there is one, a deviation from the mockup (owner decision), filterable by kind; the mockup's optional Findings column (the findings each change opened or resolved) is left out, as the note on host-packages-diff.html allows. The oldest snapshot listed is labelled "Oldest package snapshot kept" ("No earlier snapshot kept"), not a first report, since Retention prunes old snapshots. The Configuration tab says the same ("Oldest config snapshot kept", "No earlier snapshot kept", review of #124). The tab lists the latest 10 snapshots with their diffs (`PackageSnapshotTimeline`: rows are read without their package lists, and each pair's change counts are cached by the two snapshot ids, since snapshots never change, so a refresh builds no diff; review of #124); `?to=` naming the oldest snapshot kept compares it with the one after it; older ones are picked on the comparison page, whose pickers offer every snapshot kept.

### Acceptance criteria

- [ ] The list matches the VM's package manager listing (manual check recorded for AC-2.3)
- [ ] Diff correctly shows an install, a removal, and an upgrade
- [ ] Page loads quickly with a 3,000-package host

## P2-D04: Host vulnerabilities view

### Scope

- Open and resolved findings per host, grouped by package with the advisories collapsed under it (the package row shows the advisory count, the worst severity, and how many have a fix available), filterable by severity and state, with installed version, fixed version, advisory id, and a link to the source advisory (only `http` and `https` links, opened with `rel="noopener noreferrer"`).
- A per-package view of the findings for one package.
- Clear "not evaluated" states with reasons (unmapped distribution, no advisory data imported, unsupported package manager) instead of an empty list.
- Advisory data freshness shown when [P2-S13](p2-vulns.md) is in use.
- Delivered as `GET /hosts/:id/vulnerabilities?state=&severity=&q=` and `GET /hosts/:id/vulnerabilities/package?package=` (the name is a query parameter, as in the mockup, so no stored name can break a path), `HostVulnerabilitiesController`, under the shared host header, summary, and tabs. Findings are grouped by binary package and architecture (owner decision Q16), one row per package with its advisories collapsed under it, worst first (owner request, a scope change: see Package groups below); the package row's counts are of the findings shown, so the severity filter matches single advisories. State filter: open and reopened (the default), resolved, or all; the page shows the open section, the resolved section, or both accordingly. A host that is not evaluated shows the matcher's reason (`HostVulnerabilityEvaluation`, or `HostContext` before matching has run) and what to do next, never an empty list; findings kept from an earlier evaluation are said to be possibly out of date; package and advisory pairs the matcher could not check are listed; "No open vulnerability findings" appears only for an evaluated host, with the evaluation time and how many packages and advisories it covered. Advisory links are drawn only for an http or https URL with a host, opened in a new tab with `rel="noopener noreferrer"`, checked again in the view; otherwise "No link recorded". The freshness indicator is the existing P2-S13 partial. A finding stores only its latest resolution and reopening, so the per-package history lists first seen, the latest resolution (with how), and the latest reopening. The per-package page (review of #120) shows the same not-evaluated notice and freshness indicator as the tab, and shows "No findings" only for a package known to have been checked: not before matching ran, without advisory data, or when its advisories could not be compared (listed for the package) or the matcher's unchecked list was cut short. When the package manager is unsupported it says whether the package is installed is not known, and after an unreadable database the installed package is the last readable report's. A "fixed" resolution reads "the installed version is outside the affected ranges", since the matcher also records it when an advisory's ranges change with no update (a wording change from the mockup's "package updated", owner decision); the fix advice names the recorded range's fixed version and does not promise later versions are safe.

- **Package groups** (owner request: "group vulnerabilities by their package" and make the tab actionable; a scope change to [FR-2.4](../../requirements.md#fr-24-vulnerability-matching--server-side) and the mockup's open list). Delivered as `HostFindingGroups` and the `keep-open` Stimulus controller.
  - **Row.** One row per binary package and architecture: the package (linked to its page) and installed version, how many advisories, the worst severity with the count per severity, the fix count (open list) or how they resolved (resolved list), the states ("45 open, 2 reopened"), and the earliest first seen. On the open list the column is headed "Fixes" and says how many of the package's findings have a fix: "Fix for 12 of 47", "Fix for all 3", "Fix available", "No fix for any of 6", or "No fix available", never "47 findings". On the resolved list it is headed "Resolutions" and says how they resolved ("2 fixed, 1 removed"): a resolved finding is not something to act on, so it gets no fix count (review of #253; #252 question 7). The advisory rows keep "Fixed in".
  - **Fixable** means the finding has a fixed version: the affected range of the advisory for the host's release (its ecosystem, such as `Debian:13`) that the installed version is in has a `fixed` event ([P2-S11](p2-vulns.md#p2-s11-vulnerability-matching-job-and-finding-lifecycle)). A fix only in a later release is not a fix for this one, since the ecosystem is release scoped. Whether the fixed version is in the host's configured repositories yet is not known (the agent reports installed packages only), so it is not checked. Debian's triage never changes it ([DEC-22](../../decisions/0022-distribution-triage.md)).
  - **Order.** The open list puts the biggest offenders first: by the count of critical findings, then high, medium, low, and unknown (compared in that order, so one critical outranks any number of high), then the most with a fix, then the package name and architecture (bytewise). The resolved list keeps the tab's earlier order: worst severity, then the earliest first seen, then the name.
  - **Disclosure.** Each package's advisories are a native `<details>` in a full-width row under the package row, closed by default, with the summary "Show the N advisories" ("Hide ..." when open) naming the package for screen readers, holding a table of the advisory rows as before (advisory, severity, fixed in, state, first seen and resolved, and Debian's triage). It needs no JavaScript. A text search (`q`) opens the groups it finds. The disclosures have stable ids, and a live refresh (a Turbo morph) never closes one the operator opened: `keep-open` cancels Turbo's `turbo:before-morph-attribute` when it would remove `open` (mutation type `remove`); a refresh may still open one. Its spec drives Turbo's own morph code from the shipped `turbo.js`, and the behaviour was checked in headless Chromium with a real `Turbo.session.refresh`.
  - **Pages.** Each section (open and reopened, resolved) shows 50 packages a page, keyset on the whole sort key, so a page keeps its place when counts change under a live refresh (it shows what now sorts after the key it was drawn from): `?after=` and `?before=` for the open section (`critical,high,medium,low,unknown,fixable,package,architecture`), `?resolved_after=` and `?resolved_before=` for the resolved one (`worst,first seen,package,architecture`). A link that does not parse, or one with nothing left past it, shows the first page with a notice saying why and a link to the first page. The heading counts every finding the filters keep, not only the page's. The groups are aggregated in the database in one query whatever the page, and only the page's findings are loaded (their package and architecture pairs), so the tab sends a fixed number of statements whatever the host's finding count. A package whose findings leave the list between the two statements (a matching run committing, or a replica replaying) is left off that page instead of failing it. The state chips count the findings alone, in one grouped query (from #254), and the "Debian: no security update planned" chip is one SQL count with the same rule as the rows' triage (`FindingTriage.no_dsa`), so the tab never loads every open finding.
  - **Measured** (request spec, sandbox PostgreSQL with table statistics, other suites running): a host with 6,000 open findings over 1,000 packages and 3,000 advisories took about 1.0 to 1.2 s and 3.5 MB of HTML on `main`, and about 0.13 to 0.22 s and 230 KB with this (30 statements); a second page 0.14 s, `?state=all` 0.13 s. On a benchmark seed of 5,000 hosts and 900,000 findings (`bin/benchmark explain --only "vulnerabilities tab"`), the group query takes about 4 ms for a host with 450 findings, by index scans.

### Acceptance criteria

- [ ] Findings can be filtered by severity and state
- [ ] A host that cannot be evaluated says so and why
- [ ] A resolved finding shows when and how it resolved
- [ ] Findings are grouped one row per package, the open list worst first, each row saying how many advisories, the worst severity, and how many have a fix ("Fix for N of M"); the resolved list says how they resolved instead
- [ ] A package's advisories are collapsed by default and open without JavaScript, and a live refresh does not close a group the operator opened
- [ ] Packages are paged by keyset; a page keeps its place when counts change, and a link with nothing left past it says so and shows the first page
- [ ] The tab sends the same number of statements and draws one page of package rows whatever the host's number of findings
