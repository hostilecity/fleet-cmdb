# P1-DEPLOY: Server deployment, backups, and installation docs

Implementation details for the GitHub issue with this key. The issue states only the goal and acceptance criteria; this file is the source of truth for everything else. Goal, requirement IDs, acceptance criteria, and blockers live in [`../issues.yml`](../issues.yml).

## P1-O03: Server deployment: Docker Compose, Cloudflare tunnel, and private agent TLS

**Changed by the owner's review of #88 ([ADR 0023](../../decisions/0023-deploy-with-github-actions.md)):** the server is one container deployed by GitHub Actions onto the existing PostgreSQL container's network, and the tunnel on another VM reaches it over plain HTTP. The agent hostname's TLS is [#137](https://github.com/hostilecity/fleet-cmdb/issues/137), and backups in the deployment get their own issue; the criteria marked below moved there.

### Context

[DEC-05](../../decisions/0005-hosting-tls-deployment.md): Docker Compose; the dashboard is published through a Cloudflare tunnel (TLS at Cloudflare) with Cloudflare Access; the agent API is on a private LAN hostname with a Let's Encrypt certificate (DNS-01 through Cloudflare) and is never exposed through the tunnel.

### Scope

- Production Dockerfile (the Rails 8 default is a good start) and a compose file running Rails (Puma) with Solid Queue, PostgreSQL, a TLS proxy for the **agent hostname** that obtains its certificate by the Cloudflare DNS challenge, and the Cloudflare tunnel connector for the **dashboard hostname** only.
- Two hostnames, configured by environment: a public dashboard hostname and a private agent hostname. `config.hosts` allows exactly those two; route separation is implemented and tested in [P1-S13](p1-access.md).
- Document the tunnel configuration (it must not publish the agent hostname or any `/api/v1` path), the Cloudflare Access policy for the dashboard, and the internal DNS record that points the agent hostname at the server's LAN address.
- Rails trusts the proxies for client addresses (`assume_ssl`, trusted proxies) so per-host rate limiting and logs see the right address.
- Configuration through environment and Rails credentials, with an `.env.example` containing placeholders only. No real hostnames, addresses, tokens, or keys in the repository. The Cloudflare API token used for DNS challenges is a secret and is scoped to DNS edit for the one zone.
- Migrations on deploy (`db:prepare`), persistent volumes for PostgreSQL, certificates, and release files, and a documented upgrade procedure.
- Verify from a VM: the agent hostname serves a trusted certificate with no custom CA; the same `/api/v1` path is **not** reachable via the public dashboard hostname.

### Acceptance criteria

- [ ] A deploy by `.github/workflows/cd.yml` brings up a working dashboard with the documented configuration
- [ ] A request to `/api/v1/*` through the public dashboard hostname fails; the same request on the agent hostname succeeds (Deploy CI checks both over HTTPS)
- [ ] An agent on a Debian VM verifies the agent hostname certificate with its compiled-in trust and no `ca_file` (#137, ADR 0024)
- [ ] The certificate's expiry is visible before it lapses (the Settings page, with a warning 30 days ahead; renewal is the owner's, ADR 0024)
- [ ] Rebuilding the stack from backups restores state (ties into [P1-O01](p1-deploy.md); moved to [#138](https://github.com/hostilecity/fleet-cmdb/issues/138), where Deploy CI rehearses it)

### As built

- `.github/workflows/cd.yml` (workflow "Deploy"): every push to `main`, and `workflow_dispatch` on `main`; `runs-on: self-hosted`, environment `production`, one deploy at a time. Over SSH (key from `SSH_PRIVATE_KEY`, host key from `DEPLOY_KNOWN_HOSTS` or `ssh-keyscan`) it deploys the run's own commit (`GITHUB_SHA`; rollback is a re-run of an earlier Deploy run, or a revert), ships `cmdb/`, `docs/api/`, and `agent/trust/` as a tar of the checkout (the runner needs no `git`: `actions/checkout` downloads through the API), writes the app's settings over SSH standard input into a mode-0600 env file, and on the VM checks the database network (`docker network inspect`), creates the volume `fleet-cmdb_storage` (`/rails/storage`: release files, backup status), builds `fleet-cmdb:<sha>`, replaces the `fleet-cmdb` container (`-p 80:3000`, the database network, `--restart unless-stopped`, `--env-file`, then the file is deleted), waits for `/up`, and prints the status. No secret value is on a command line.
- The PostgreSQL container, its network, the role `cmdb`, and its four databases exist on the server already (provisioned elsewhere); `PGHOST` is `FLEET_DB_HOST` (default `postgres`). `db:prepare` runs the migrations on every start.
- **HTTPS (ADR 0024, #137):** Puma serves HTTPS itself on 3443 (published as 443, the only published port) with a Cloudflare Origin CA certificate for the internal hostname, from the secrets `FLEET_TLS_CERT` and `FLEET_TLS_KEY` (base64 in the env file, `lib/tls/server_tls.rb`). The tunnel's origin and the agents both connect to that hostname; the tunnel passes the browser's hostname in `Host`. The deploy stops if agents would not trust the certificate (`openssl verify` against `agent/trust` and the system store); the boot stops if the key does not match or the certificate does not cover `FLEET_AGENT_HOST`. The image runs `puma -C config/puma.rb`, since `rails server` replaces the config's listeners. The Settings page shows the expiry.
- **Trusted proxies:** none. The tunnel connector connects directly and passes on headers a browser sent, so `FLEET_TRUSTED_PROXIES` stays unset and `HostSeparation` drops every forwarded header; a client cannot claim the agent hostname through the tunnel. The guide recommends a firewall rule allowing port 443 only from the tunnel VM and the agents' VMs.
- **No Thruster:** the image runs Puma directly on port 3000. Behind Thruster every request reaches Rails from loopback, which `HostSeparation` always trusts, so a forged `X-Forwarded-Host` would pass (confirmed against the app in production mode).
- **Release import egress:** the import uses only `github.com` and the download host it redirects to (`release-assets.githubusercontent.com`), not `api.github.com`.
- **Jobs container and sizing (#198, [ADR 0025](../../decisions/0025-first-scale-step.md), proposed):** background jobs run inside the app container (`SOLID_QUEUE_IN_PUMA`) by default. With the deploy variable `FLEET_JOBS_CONTAINER=true` the app runs without them and a second container, `fleet-cmdb-jobs`, runs `bin/jobs` from the same image, settings without the TLS certificate and key (`FLEET_TLS_*`, checked by Deploy CI), network, and volume, with no port, no capabilities, and no privilege gain. It is started after `/up` (the migrations), the deploy waits until its workers register, and the old one is stopped (30 s to finish) and removed before the app is replaced. Any other value stops the deploy; unset or `false` removes a leftover jobs container. Puma processes (`WEB_CONCURRENCY`) and the thread settings are documented with a connection budget in [scaling.md](../../operations/scaling.md); each database pool is the largest thread count plus 2 (`cmdb/lib/sizing/process_sizing.rb`).
- **Scale readiness, steps 2 and 3 (#198, [ADR 0031](../../decisions/0031-second-scale-step-readiness.md), proposed):** optional settings, all off by default, documented in [configuration.md](../../operations/configuration.md) and [scaling.md](../../operations/scaling.md#step-2-up-to-about-100000-agents). `FLEET_DB_POOLER=transaction` turns off prepared statements and the migration lock on the pooled databases, and needs `DIRECT_DATABASE_URL`, where `SessionLock` takes the liveness and rollout-prepare session-level advisory locks (checked before each batch), and `FLEET_DB_PREPARE=false`: no migration runs through the pooler; they run once per deploy in a one-off container on direct connections. `REPLICA_DATABASE_URL` lets the pages named with `reads_from_replica` read a replica once it has replayed the primary's WAL position from the page's start (waiting at most `FLEET_REPLICA_MAX_WAIT_MS`), never agent API paths, writes, or step-up; a server not in recovery is never read, and a failing replica is skipped for `FLEET_REPLICA_SKIP_SECONDS` while the page runs again on the primary. `FLEET_NODE_ROLE` (`all`, `agent_api`, `dashboard`) limits which hostname a node serves, and `FLEET_DB_PREPARE=false` makes the entrypoint skip migrations. Running PgBouncer, a replica, or more than one node is not part of `cd.yml` yet.
- **Verification:** `.github/workflows/deploy-ci.yml` builds the image as `cd.yml` does, runs it against a throwaway `postgres:17` with the role `cmdb` owning the four databases (the same env-file mechanism and a published port), waits for `/up`, and checks that the dashboard hostname serves sign-in, refuses `/api/v1` (also with a forged `X-Forwarded-Host` or `Forwarded`) and `/health`, and that `/health` is 503 until a backup exists. Then it runs the image as `FLEET_JOBS_CONTAINER=true` does (the app without jobs, plus a jobs container) and checks that the liveness evaluation ran on the realtime queue in the jobs container and that `/health` sees it. It also runs shellcheck and actionlint. The tunnel, Access, and the runner need the owner's accounts and are checked by following [install-server.md](../../operations/install-server.md).

## P1-O01: Database backup and tested restore procedure

### Context

NFR-2 requires a documented, restorable backup procedure. A backup that has never been restored is not a backup.

**Moved to [#138](https://github.com/hostilecity/fleet-cmdb/issues/138) by the owner (2026-11-08):** the procedure and scripts below are delivered, but setting up backups in the GitHub Actions deployment and performing the restore drill there are done later in testing. They no longer block P1-DEPLOY or either phase's acceptance.

### Scope

- Scheduled logical backups (for example `pg_dump` via a systemd timer or a compose sidecar) with a retention policy and a location off the server machine.
- The release files (`FLEET_RELEASES_DIR`, [P1-RELEASES](p1-releases.md)) are in the backup or can be rebuilt: say which. Imported releases can be re-imported from GitHub, but uploaded ones cannot, and the database rows are checked against the files. The restore drill covers a release download after restore.
- Documentation of what else is needed to restore: the Rails master key (or credentials), the Cloudflare API token and tunnel credentials, the agent hostname certificate state, and the configuration environment. These must be backed up separately and never committed.
- A restore script or runbook, and a **restore drill**: restore into a scratch database, boot the app against it, and check that hosts, snapshots, and the audit log are present.
- A check that fails loudly if the latest backup is older than expected (surface it in [P1-S11](p1-operability.md) health or documentation of the alert).
- Delivered as `ops/backup/` (`backup.sh`, `restore.sh`, `restore-drill.sh`, systemd units) and [docs/operations/backup-and-restore.md](../../operations/backup-and-restore.md). The backup touches a status file that `/health` watches (`FLEET_BACKUP_STATUS_FILE`, `FLEET_BACKUP_MAX_AGE_HOURS`); the drill's checks are `bin/rails backup:verify_restore`.

### As built (#138)

Owner decision (2026-11-16): backups run on the **app VM**, set up by `cd.yml`; the PostgreSQL container is provisioned by a separate task and needs only the one-time `ALTER ROLE cmdb CREATEDB;` for the drill.

- **Set:** `fleet-cmdb.dump` and `queue.dump`, `cache.dump`, `cable.dump` (all four databases), `releases.tar`, `counts`, `SHA256SUMS`. `backup.sh` checks first that `pg_dump` is the server's major version or newer.
- **Where it runs:** the deploy user's systemd **user** timer `fleet-cmdb-backup.timer` (daily 02:30, up to 10 min random delay, `Persistent=true`), installed by `ops/backup/install.sh`, which `cd.yml` runs before it replaces the app. It needs lingering for the deploy user (one-time root step); without it the deploy stops with the old app running. A failed image pull only warns. `ops/backup/docker.sh backup` checks `BACKUP_DIR` on the VM (it must exist and be a mount point unless `FLEET_BACKUP_ALLOW_LOCAL=true`), then runs `backup.sh` in a throwaway `FLEET_BACKUP_PG_IMAGE` container (default `postgres:17`, may be pinned by digest) on `FLEET_DB_NETWORK`, as uid 1000 with no capabilities and `--init`, with the storage volume mounted **read-only** for the release files. The app's own image, with no network, then touches the status file in the volume, so `/health` reports it. The database needs no published port.
- **Password:** never stored for the backup. `docker.sh` reads `PGHOST` and `DATABASE_PASSWORD` from the `fleet-cmdb` container's settings (`docker inspect`; running or stopped) at run time and passes the password to containers by name (`docker run -e PGPASSWORD`). `~/.config/fleet-cmdb/backup.env` (mode 0600, written by `cd.yml`) holds only non-secret settings and is read literally, never sourced.
- **No empty set displaces a good one:** `backup.sh` refuses a database with fewer hosts or audit entries than the newest set (neither is ever deleted), writing and pruning nothing (`BACKUP_FORCE=1` or `docker.sh backup --force` overrides: for a deliberate restore of an older set, which `docker.sh restore` forces itself, or a deliberate fresh start; the forced set becomes the baseline). It relies on hosts and audit entries never being deleted (FR-S.3, ADR 0027 decision 7). The deploy starts a first backup, in the background, only when `BACKUP_DIR` holds no set (`docker.sh first-backup`). The drill with no set named, and `docker.sh restore`, refuse a set with no host and no audit entry. Retention goes by the time in the set's name, keeps the newest 3 and the newest set holding more hosts or audit entries than the newest one (until `docker.sh delete`, which refuses the newest set and a set that does not exist), and removes `.incoming-*` directories more than a day old, by the time in their name.
- **One lock** (`~/.local/state/fleet-cmdb/backup.lock`, `flock`): backup and drill wait up to an hour for another holder, and read the app container's settings and image only once they hold it; `ops/deploy/deploy.sh` (cd.yml's "Build and run") waits up to 20 minutes for a running backup or drill before it builds (cd.yml's job timeout is 60 minutes), so migrations never queue behind `pg_dump`'s share locks; a restore refuses while anything runs, and backup, drill, `install.sh`, and the deploy refuse during a restore. A restore leaves `restore-incomplete` until it succeeds; `restore.sh` exits 64 when it refused without changing anything, which clears a marker only this run created (an earlier run's marker stays). The marker's text names the four databases to drop and the release directory to empty, then a new restore. Backups, `install.sh`, and the deploy refuse while it exists.
- **Kept:** sets in `FLEET_BACKUP_DIR` (default `/var/backups/fleet-cmdb`), retention `FLEET_BACKUP_RETENTION_DAYS` (14).
- **Restore and drill:** `restore.sh` restores every dump of a set with `--single-transaction`, into new databases or existing ones holding nothing of their own (objects of extensions do not count), and refuses others; on a failure it names the databases already restored. `docker.sh restore SET` (app stopped) restores, then backs up the restored state at once, forced. `docker.sh restore-drill` restores into four scratch databases and a scratch volume, on the live server or on `FLEET_BACKUP_DRILL_HOST`, prints the space they need, then runs `backup:verify_restore` in the deployed image against the scratch primary, with the running container's settings.
- **Verification:** Deploy CI installs it as `cd.yml` does (the runner user as the deploy user, lingering on, a tmpfs mount as the backup location; `backup.env` is written by the same lines, not by `cd.yml` itself), takes the deploy's first backup with `docker.sh first-backup` through the user unit, checks the set and `/health`, runs the drill with an uploaded release (it fails with the `CREATEDB` hint, then passes, including the download check) and once on a second PostgreSQL, checks the lock (including a backup that waits while a deploy swaps the container and removes the old image tag) and the restore marker (a restore that fails part-way into reused empty databases leaves it; a re-run that refuses keeps it; a successful restore clears it), and recovers a lost server in the guide's order with `ops/deploy/deploy.sh` as the deploy: the deploy waits for a backup holding the lock and takes no first backup, the nightly backup refuses the empty databases, a forced empty set cannot be drilled or restored by mistake, and after `dropdb` and `docker.sh restore` the host, operator, and release come back and the drill of the newest set passes. Not covered: `cd.yml` itself over SSH, and the owner's real mount and systemd instance.

### Acceptance criteria

- [ ] The restore drill is performed and the result recorded on #138 (Deploy CI runs it against the deployed setup on every change; the owner's first drill on the server is still to be recorded)
- [ ] A restored database boots the app and shows the expected hosts and audit entries
- [ ] The procedure is in the install and operations documentation ([P1-X03](p1-deploy.md))

## P1-X03: Installation and operations documentation (server, agent, enrollment, upgrade, uninstall)

### Scope

- Server: prerequisites, deploy, first operator, TLS, configuration reference (including the release public keys and outbound access for release import: `api.github.com`, `github.com`, and the release asset download hosts GitHub redirects to, over HTTPS; none is needed for uploaded releases), upgrade, backup and restore (from [P1-O01](p1-deploy.md)), where logs are, and the health endpoint.
- Agent: the dashboard install page ([P1-D08](p1-releases.md)) as the primary path; pre-registration for unattended installs; remote updates and rollouts; manual upgrade by re-running the installer; uninstall.
- Operations: revoke and re-enroll, retire, recover from a lost credential, change thresholds, read the audit log.
- Troubleshooting: certificate trust errors, `401` responses, clock skew, host stuck offline, an expired onboarding request, a halted rollout, and a rolled-back update.
- Validate by following the documents on a clean server and clean VM using only the documents; fix gaps found.

### Acceptance criteria

- [ ] The owner (or a fresh reader) completes server setup and enrolls a VM from the documents alone
- [ ] Every command in the docs has been run at least once
- [ ] Documentation links from the root `README.md`

### As built

[docs/operations/](../../operations/README.md): `install-server.md` (the GitHub Actions deployment, with HTTPS on the internal hostname from #137, and backups from #138), `configuration.md` (every environment variable the server reads, checked against every `ENV` use in `cmdb/`), `install-agent.md`, `fleet-operations.md`, `troubleshooting.md`, with the existing `backup-and-restore.md` and `health-and-jobs.md`. The settings tables formerly in `cmdb/README.md` moved to `configuration.md`. Rollouts are started from the Rails console until their dashboard view ([P1-UPDATES](p1-updates.md), P1-D09) arrives; `install-agent.md` says so and should switch to the dashboard then.
