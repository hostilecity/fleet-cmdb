# VT-BUCKETS: Put every open finding in exactly one triage bucket with a reason

Implementation details for the GitHub issue with this key. The issue states only the goal and acceptance criteria; this file is the source of truth for everything else. Goal, requirement IDs, acceptance criteria, and blockers live in [`../issues.yml`](../issues.yml).

Part of [VT-EPIC](vt-epic.md) (approved by the owner, 2026-11-19); decided in [ADR 0032](../../decisions/0032-vulnerability-triage-buckets.md). The buckets, the rules and their order, and the missing-data rules are the epic's VT-M1; work items are VT-M4; where things are computed is VT-M6.

## VT-S05: The classifier, stored buckets, work events, and re-triage

### Scope

- **Classifier.** `VulnerabilityTriage.classify(inputs)`: a pure function from one finding's inputs to `[bucket, rule_id, kev]`, implementing VT-M1's table in order. Inputs: the verdict (fixed version, installed version, source), the advisory (normalised severity, `cvss_av`, `cvss_pr`, `cvss_ui`, CVE ids), Debian's triage for the host's release (status, fixed version, urgency, no-DSA, next point release, scope, removed), the stored KEV entries and EPSS bands per CVE and whether each source has ever been imported, the host's running kernel and installed kernel images, its listener evidence when there is one (owner decision 2026-11-21: escalation only), and an active control (VT-OVERRIDES). Unit specs cover every rule, every precedence pair in VT-M1, and every missing-data case.
- **Staleness never reaches the classifier** (B1, S3): N1 and N2 use the stored data whatever its age, and I5 needs only that KEV data has been imported once. Staleness is a read-time qualifier on reasons, tiers, and badges, so a source going stale or recovering rewrites nothing.
- **Reasons** are built at render time from the rule id and the same inputs; the rule id is stored, not the text. Attack vectors are shown in words ("network, no login, no user action"), with the vector as secondary text.
- **Applicability table** per distribution, `cmdb/config/triage_applicability.yml`, checked at boot, so other distributions (#163) are a data change: the kernel image package pattern, how to read its kernel release and flavour (Debian: `linux-image-<release>`, `-unsigned`), how to compare two images (dpkg order of their versions), and the "no runtime code" packages of a source.
- **Proposal for the owner (from #270, not decided): signed images carry the kernel's findings.** Since #270 the signed image (`linux-image-6.12.48+deb13-amd64`, source `linux-signed-amd64`) and the metapackages built with it (`linux-image-amd64`, and `linux-headers-amd64` where the signed source builds it) have `linux`'s findings, with source `linux` and the binary's version (which is `linux`'s). #270 proposes, for the owner to accept or change, that the applicability table's kernel image pattern exclude the flavour metapackages (`linux-image-<flavour>` has no kernel release in its name) and list them, with `linux-headers-<flavour>`, among I2's "no runtime code" packages (so they become Ignorable). Without some such rule, I1 would read `amd64` as a release that is not running.
- **Kernel rules (B2).** K1 and K2 need no agent change: the installed images come from the package report and the running release from the inventory. A newer image installed and not running is a pending kernel reboot.
- **Base bucket per chunk.** Every rule that does not depend on the host (F1, F2, I2 to I5, N1 to N4, L2 to L5) is computed once per `chunk_matches` row into `base_bucket`, `base_rule`, and `kev`, when the chunk is matched and when an input of its advisories changes. A host's transitions then apply the host rules (I1, K1, K2, O1, N5) on top.
- **Storage.** `vulnerability_findings.bucket`, `bucket_rule` (smallints) and `kev` (boolean), null while resolved, written by the host's transitions in the same pass that writes the stored fixed version (VT-S01's fix flag), only where they changed. The `kev` flag makes a KEV change on a finding whose bucket stays the same still fire the summary triggers, so points and tier never go stale (S2).
- **Work events.** The transitions append to `vulnerability_work_events` (host, time, kind, source package or kernel release, findings cleared), time-partitioned and kept 90 days (ADR 0027): `upgrade` when a package report changed a source package's installed version and that resolved at least one Fix available finding; `kernel_installed` when a new image turns K2 findings into K1; `reboot` when the running kernel changed and K1 findings moved to I1. A resolution caused by an advisory change writes nothing (S5a).
- **Re-triage runs.** `EvaluationRun::Triage` recomputes the base bucket of the chunks holding advisories whose inputs changed (a CVE added to or removed from KEV, an EPSS band change, a tracker status, urgency, no-DSA, scope, or fixed version change for a fleet release, a vector or severity change), then runs the transitions of the hosts on sets holding chunks whose base bucket or KEV flag changed (ADR 0028's path), in batches locked in host-id order and sized by lock time (`LOCK_TARGET`, as #204 and #196). KEV changes start a run at once; EPSS and tracker changes are coalesced into one run a day after the EPSS import. Runs supersede each other like advisory runs.
- **Hand-off from the signals (built in #257).** `triage_signal_changes` holds dirty markers, one row per kind and CVE or advisory, which the run recomputes from the current data: `kev` (a CVE added to or removed from KEV), `kev_all` (KEV data appeared or was cleared, so I5 turns on or off for every finding), `epss` (a CVE whose band changed, an EPSS reset included), and `advisory` (an advisory whose vector parts or severity changed, or whose CVE set gained or lost a CVE in KEV or the EPSS high band). Tracker changes are not in it: this slice gives them their own path (a new kind, or the tracker import's own change list). The run must follow the claim protocol (`TriageSignalChange`, reviews of #269), which loses no change, never waits on an import, and never deadlocks with one:
  1. `TriageSignalChange.claim(kinds:, limit:)` reads a batch, oldest id first, with a plain SELECT (no lock).
  2. The run recomputes from the current data (whatever the row says, the data decides) and commits its work.
  3. `TriageSignalChange.release!(ids)` deletes the claimed ids in a transaction of its own, skipping any row an import has locked (`FOR UPDATE SKIP LOCKED`). Recording a change that is already pending gives its row a new id, so a change recorded between 1 and 3 is not deleted and is claimed next time. A row an import is re-recording is skipped: if the import commits, the row has a new id and must stay; if it rolls back, the row is processed again, which is harmless. `release!` raises inside an open transaction. A run that fails releases nothing.
  Claimed rows are never held in the run's transaction, and rows are never deleted by kind or key. Within one run, process the `advisory` rows after the `kev` rows: an advisory import that adds an alias reads KEV before a concurrent KEV import commits that CVE, and the `kev` row then covers it. "KEV imported at least once" (I5) is `KevEntry.exists?` (`Signals::Freshness.kev_imported?`), never "a KEV import succeeded".
- **Host facts.** A new inventory (kernel, reboot flag), a change of listener evidence or its expiry after 24 hours, or a decision change re-classifies that host only, in its transitions.
- **Summaries.** `host_compliance_summaries` gains `vuln_fix`, `vuln_attention`, `vuln_low`, `vuln_ignorable` (finding counts that always add up to `vuln_open`) and `vuln_kev_open`, recounted by the existing triggers; `compliance_summaries:check` covers them. Proposed, for the owner when this slice is built: name the Low risk count `vuln_low_risk`, not `vuln_low`, which already holds the open low-severity findings (review of #267, N6).
- **VT-FIXABLE's columns** (#256, review of #267, N6). `vuln_fixable` counts findings whose advisory data names a fix (rule F1's input), `vuln_fix` the Fix available bucket (F1, F2, K1, K2), so they differ by F2 and by kernel findings that I1 makes Ignorable. Proposed, for the owner when this slice is built: keep `vuln_fixable` and `vuln_fix_packages` for the existing "N with a fix" lines until VT-SCORES replaces the fleet column, then move the Compliance filter and lines to the bucket (`vuln_fix`); replace `vuln_fix_severities` with per-bucket severity counts, which VT-SCORES' points table needs and a bitmask cannot give; drop the kernel note on the tab (VT-FIXABLE's) when K1 and K2 give the kernel its own work item.
- **Tracker churn first.** Before the runs are built, the Debian triage import records how many trixie entries changed (status, urgency, no-DSA, fixed version) per import; 14 days of it on the test VM give the daily re-triage estimate (VT-M6), recorded here.
- **Suggested controls** table, `cmdb/config/triage_controls.yml`: a short text per rule and attack vector (network service, crafted file, local privilege escalation, unsupported package, known exploited), our own words.
- **Measure** with `bin/benchmark`, at about 4,000 open findings per host (S12): a package report's transitions, a triage run for one KEV CVE on 100,000 hosts, a day's coalesced run at the measured churn, and the summary recount; record them here.

### Acceptance criteria

- [x] Every open finding of an evaluated host has exactly one bucket and rule, the four summary counts add up to the open count, and a kernel fixed in an installed newer image is K1 until the reboot, then I1, with a `reboot` work event (`spec/services/vulnerability_triage_matching_spec.rb`)
- [x] A source going stale or being turned off changes no finding's bucket, KEV flag, points, or tier; a never-imported source keeps I5 from applying (spec per rule: `spec/services/vulnerability_triage_spec.rb`; stale and off: the matching spec). Points and tier are VT-SCORES'; they read the stored bucket and `kev`, which do not change.
- [x] A KEV import that adds one CVE re-triages only the hosts on sets holding its chunks, and a KEV change on a Fix available finding updates its host's `kev` flags and `vuln_kev_open`, from which VT-SCORES' points and tier are recounted (the matching spec)

## As built (#259)

- **Classifier.** `VulnerabilityTriage.classify` (`cmdb/app/services/vulnerability_triage.rb`) walks the 19 rules in order. `base` is the same function with the host's facts left out; `host_layer` adds I1, K1, K2, O1, and N5 on top. A spec checks `host_layer(base(x)) == classify(x)` on 2,000 random inputs. Rule ids are stored as their position (I1 = 1 ... L5 = 19), buckets as 1 Fix available, 2 Needs attention, 3 Low risk, 4 Ignorable. A check constraint ties each rule to its bucket and keeps resolved findings without one (added `NOT VALID`, then validated by `20261121259003`; see Migration). N4's "medium or higher" counts an `unknown` severity as medium: it is missing data (owner's OK, review of #277).
- **Combining a multi-CVE advisory's tracker entries** (the spec is silent; decided conservatively, corrected in the review of #277, B1): F2, I3, I4, and I5 need **every CVE of the advisory** to have an entry for the release, and every entry to agree (all resolved for F2 to I4, F2's version the highest; each unimportant or already fixed for I5, at least one unimportant). A CVE with no entry, or an undetermined one, blocks them. N3 fires if any CVE is end-of-life; L4 needs every open CVE to be no-DSA. With no CVSS vector, N4 fires if any CVE's scope is remote, and L2 needs every CVE with a scope to be local. A version dpkg cannot order fixes nothing and clears nothing. N1, N2, and the KEV flag fire on any CVE.
- **`<removed>` (N3's second half) is not built**: the tracker's JSON, which P2-S16 imports, has no field for it. N3 fires on urgency `end-of-life` only.
- **Kernel rules.** `cmdb/config/triage_applicability.yml` (checked at boot) has Debian's image pattern (`linux-image-<release>`, its `-unsigned` twin; not the `-dbg` packages and not the flavour metapackages) and the no-runtime-code list. Images are found from the host's chunks through the source index (`linux` and the signed sources built from it, `SignedSources`), so signed images count. #270's proposal is built: the flavour metapackages (`linux-image-<flavour>`, `linux-headers-<flavour>`) and the `-dbg` images are I2. K1 needs an installed image of the same flavour at or above the fix (F1's, or F2's stored as `chunk_matches.triage_fixed_version`). A running release that no installed image boots (the running image purged, or a kernel that is not packaged) counts as "running kernel unknown": I1, K1, and K2 do not apply, and the images' findings fall to the other rules, rather than all being Ignorable (review of #277, S4). The pattern reads trixie's `<version>+deb13-<flavour>` and bookworm's `<version>-<ABI>-<flavour>`, so `686-pae` is one flavour in both. Known limit (#163): bullseye-backports names (`linux-image-6.1.0-0.deb11.17-amd64`) do not match, so such a host's kernel reads as unknown (safe). The I1 reason says an image older than the running one will not run again and that removing it is a tidy-up, never progress (VT-M5 rule 4).
- **Host facts from later slices.** `VulnerabilityTriage::HostFacts` reads the running kernel from the inventory, and listener evidence (N5) and controls (O1) through two hooks, `listener_source` and `control_source`, which are `nil` here: this PR merges with both off, and every finding is triaged as without them (a spec checks it). **Owner decision 2026-11-21:** in-use evidence only escalates; L1 and N4's idle check are gone, and N5 (rule 15, Needs attention) fires when a process holding a listening socket loads the package. VT-APPLICABILITY (#258, PR #268 rebased onto this one) writes the adapter against `HostApplicability#in_use_by_listener?(package, now:, network: false)` and `listeners_loading` (the listener's package, network or loopback, the host's scan time; the listening unit and address when it reports them), the `changed!` call from `record_in_use!`, and the index on `library_scanned_at` that `listener_hosts_expiring` needs, and has the final text of this bullet. Evidence is used while the host's scan is at most 24 hours old; `TriageListenerExpiryJob` (hourly) re-triages the hosts whose scan time is in the window (from, to], from its checkpoint (a row in `triage_checkpoints`, not the cache) to 24 hours ago, so evidence escalates for 24 to about 25 hours. A clock that went back does nothing and keeps the checkpoint; one that jumped forward moves the window ahead: while the clock is ahead every match reads evidence as expired (as any time-based check would), and once it is back, the hosts whose window was used early are not re-triaged at their real expiry, so their findings stay in Needs attention until the host's next report (the cautious side). When several listeners load a package, one listening on the network wins over loopback-only ones; a loopback-only listener escalates too (its reason says so). The listening unit and address are optional; #268 caps their length and drops control characters before storing them, and the reason cuts them again at 128 characters.
- **Storage.** `chunk_matches` gains `base_bucket`, `base_rule`, `kev`, `triage_fixed_version`, written by `VulnerabilityMatcher::Chunks` when a chunk is matched and by `VulnerabilityTriage::Base.refresh!` (under the chunks' matching locks, in ecosystem and id order) when inputs change. A verdict found without a base (written before the migration's run reached it) gets one in memory in the transitions, so no active finding is left without a bucket. `vulnerability_findings` gains `bucket`, `bucket_rule`, `kev`, written with the finding's other details, only where they change.
- **Summaries.** `vuln_fix`, `vuln_attention`, `vuln_low_risk` (the review of #267's proposal: `vuln_low` already counts low-severity findings), `vuln_ignorable`, `vuln_kev_open`. They are counted for every host, evaluated or not, so the four add up to `vuln_open` once the migration's run has reached the host. A host that is not evaluated now keeps its findings; its transitions (so the full run) and every re-triage triage them as an evaluated host's are, from the set they were last moved from: its verdicts' base, with the host rules on top from that set's kernel images and the running kernel its inventory reports (read for every host), and its listener evidence and controls (review of #277, S5, and its re-check S3a). A triage run selects hosts by that set too, so a host whose current set is gone or unsupported is re-triaged (S3b); `vuln_fixable` and the other VT-FIXABLE columns are unchanged (the proposal to move them is left to VT-SCORES).
- **Work events.** `vulnerability_work_events` (weekly partitions, `Partitions::TABLES`, kept 90 days by `Retention`, `max_age`). `upgrade`: per source package, findings in Fix available resolved as fixed with a new installed version. `kernel_installed`: findings moved from K2 to K1, subject the newest qualifying image's release. `reboot`: K1 to I1, subject the release now running. K2 to I1 between two passes writes both.
- **Runs.** `EvaluationRun::Triage` (kind `triage`). `prepare!` stores its own id in its scope, claims changes (reason `kev`: kinds kev, kev_all, advisory; `daily`: every kind), waits at the signals barrier, recomputes the verdicts of the advisories they name, recording each slice's changed chunks in `triage_run_chunks` in the transaction that changes them, stores its prepared scope, and only then releases the claimed rows outside any transaction (the claim protocol). So a fan-out retried after a failure part way, or a retry started from the failed run's scope, reaches every host a committed slice changed (review of #277, B2). **The signals barrier** (B3): a chunk match takes a transaction-level advisory lock shared before it reads the signals for its verdicts' bases; the run takes it exclusive in a short transaction of its own before it reads which chunks hold the advisories. So every match that read the signals before they changed has committed by then and is re-triaged, and every later match reads the new signals. Both locks are transaction-level, so they hold behind a transaction-mode pooler (#237). `kev_all`, or reason `all`, recomputes every verdict and every host. The hosts are those on sets holding a recorded chunk. The sets are found once, as the run is prepared, through the sets' GIN index into `triage_run_sets` (sets are immutable; a set made later comes with a report whose own transitions read the refreshed bases), and each batch reads only its own range of hosts, probing those rows by key, in one query (the range on the hosts and on both subqueries, joined by a `UNION`, not an `OR`) that is not a prepared statement, since PostgreSQL's generic plan for a range ignores how narrow it is (third and fourth reviews of #277; measured below). Each re-triages only the findings of the run's advisories (`VulnerabilityMatcher.retriage!`, under the same host locks and batch sizing): a signal or tracker change moves nothing else, so a KEV listing costs a host its few findings of that advisory, not its thousands (a host whose set changed since its last transitions is left to its own match job). A full run, or one naming more than 20,000 advisories (a first tracker import names most of them), runs the hosts' whole transitions: about 80 ms a host instead of about 1 ms, so such a day costs about what the migration's full run costs (21 thread-hours at a million hosts). A run's scope keeps its recorded runs, so a retry runs the same hosts without claiming again. A run covers an older one only when it re-runs every host the older one would (its chunks, or all); a run that is not prepared is covered only by a run that carries its id (a retry from its scope), never just by a full run, since it may still be preparing (re-check of #277, S2). **A killed worker** (a deploy's restart, the OOM killer) makes Solid Queue fail the run's job without a retry: `TriageRunWatchJob` (every 10 minutes) reads the live Solid Queue jobs, then the triage runs untouched for 10 minutes, and resumes each one with no live fan-out job (in any state, a pending retry included) and, once running, no live batch job (re-checked under its row lock, state and `updated_at` as read): its fan-out is queued again, which prepares a queued run again or queues a running run's remaining batches, so a full run carries on rather than restarts; a running run with no batches left is finished. Only resumes with no progress since the last count (scope `resumes`, with the state and batches done at the last in `resume_progress`): after 3 in a row the run is failed, with "Re-triage again", and keeps its batches; so a long full run survives any number of deploys (fourth review of #277). "Re-triage again" (`EvaluationRun::Triage.retry!`) starts with a fresh count: a prepared run with batches left is reopened and carries on from them, any other is started again from its scope. A run that failed by raising every retry is never resumed and never taken over by another run, so one bad advisory or host cannot stop later runs (third review of #277). Advisory re-matching runs share the killed-worker gap (#278). KEV imports that change the catalog, and `signals:kev_clear`, start a run once they commit; `TriageDailyJob` (15:37 UTC, an hour after the EPSS refresh) starts one when anything is pending; `bin/rails vulnerabilities:triage` re-triages everything. Triage runs show on Data sources like advisory re-matches.
- **Tracker hand-off.** Kind `tracker` in `triage_signal_changes` (one row per CVE). Each replaced release's import counts `added` and `changed` (status, urgency, fixed version, no-DSA and its reason, scope) beside `dropped`, and hands every CVE added, changed, or dropped over in the import's transaction.
- **Tracker churn: counted, not yet measured.** The counts above are recorded from this PR on; the 14 days on the test VM can only start once it is deployed, so the daily estimate is not recorded yet and the daily run is built before it (follow-up #276; "Needs the owner's OK" in the PR). The run's cost per changed CVE is measured below.
- **Reasons.** `VulnerabilityTriage::Reasons.sentence(rule, inputs, kev:, epss:, details:)` builds the sentence at render time (attack vectors in words with the vector as secondary text), with "Not re-checked against CISA's KEV list since ..." and "Not checked against ... : none has been imported." for the rules a stale or missing source could have changed, and "No EPSS score yet.". `VulnerabilityTriage::Explain.load(findings)` loads a page's inputs in a fixed number of queries (for VT-HOST-TAB).
- **Suggested controls.** `cmdb/config/triage_controls.yml`, checked at boot: known exploited (N1), likely exploited (N2), unsupported (N3), network service (N4), crafted file (L3), local privilege escalation (L2).
- **Measured** (`bin/benchmark jobs`, 2 CPUs and 7 GB shared with other work, PostgreSQL 16 defaults; medians of 3 to 5 runs). Two seeds, both with 1,500 package hosts and 4,450 open findings each (`--advisories-per-source 5`): A, `--hosts 100000` with one package set (every host shares its chunks); B, `--hosts 20000 --package-variants 150` (150 sets, 424 chunks, 34,787 chunk verdicts; seeded with triggers off, then `compliance_summaries:rebuild`), as the review of #277 asked. B is the closer one to ADR 0028's mostly distinct sets.

  **A batch's hosts at a million hosts** (fourth review of #277): a synthetic database of 1,000,000 hosts on 20,000 package sets of 64 chunks (each host with a current set and an evaluation's set), `EXPLAIN ANALYZE` and timed from Rails, 5 to 8 runs each. A sparse run (24 chunks: 31 sets, 1,550 hosts, 2 batches, each range spanning about 640,000 host ids) and a dense one (2,000 chunks: every set, every host, 1,000 batches):

  | A batch's host query | Sparse | Dense |
  | --- | --- | --- |
  | Before (sets by GIN index in each batch, prepared statement) | 260 to 490 ms | 625 to 730 ms |
  | Before, not prepared | 220 to 260 ms | 630 to 715 ms |
  | Now (`triage_run_sets`, `UNION`, not prepared) | 4.5 to 10 ms | 5 to 6 ms |
  | Finding the run's sets once (`record_sets!`) | 10 ms | 420 ms |
  | The whole run's hosts, once (`split!`) | 9 to 46 ms | 1.2 to 1.4 s |

  Before, a dense run's 1,000 batches spent about 11 minutes of database time finding their hosts, growing with the sets (up to about 900,000 at a million hosts, ADR 0028); now about 6 seconds. With a bound range, PostgreSQL switched to a generic plan from a statement's sixth run, and a sparse batch went from 5 ms to about 450 ms; so the query is not prepared.

  The base of a change costs per **chunk verdict** of the advisories it names, not per CVE: one kernel CVE can sit in thousands of chunks when sets are mostly distinct, so the daily run's cost is (verdicts of its advisories × about 0.05 ms) + (affected hosts × about 1 ms); #276 records both per day. In ADR 0028's terms, each package report's transitions now triage every finding, about 12 to 25 ms more a report on 4,450 findings (+15 to 35%), with no lock held longer than the batch sizing allows: about 3.3 to 7 thread-hours for each million reports that change a host's package set (matching runs only when a report's content changes): a few thread-hours a day at a million hosts if, as on a stable fleet, a minority of their 4 million daily reports change it, and 13 to 28 if every report did. A full run (the migration's, KEV data appearing or being cleared, `vulnerabilities:triage`, or a day naming more than 20,000 advisories) costs every affected host's transitions, about 80 ms a host: 2 thread-hours at 100,000 hosts and about 21 at a million, divided by `EVALUATION_THREADS`.
- **Migration.** `20261121259001` adds the columns, tables, constraints (`NOT VALID`), and function versions (metadata only, no table rewrite). `20261121259002` creates the work events' partitions and queues a full re-triage (reason `all`) in the background; until it reaches a host, its bucket counts read 0 (`docs/operations/upgrades.md`). `20261121259003` validates both checks (every existing row has the three columns NULL, which passes) on tables of at most 2 GB of heap (seconds with a warm cache, up to about a minute cold), read from `pg_relation_size`, which is always known (PostgreSQL's row estimate is -1 on a table never analysed); a larger one is left `NOT VALID` and `bin/rails vulnerabilities:validate_triage_checks` validates it while the server runs. Rolling the code back needs the checks dropped first, since the older code resolves findings without clearing their bucket; the same task restores them on rolling forward (`docs/operations/upgrades.md`).
