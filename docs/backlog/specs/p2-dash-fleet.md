# P2-DASH-FLEET: Dashboard: fleet compliance and rule management

Implementation details for the GitHub issue with this key. The issue states only the goal and acceptance criteria; this file is the source of truth for everything else. Goal, requirement IDs, acceptance criteria, and blockers live in [`../issues.yml`](../issues.yml).

## P2-D05: Fleet compliance view and fleet-wide severity counts

### Scope

- A table of every active host with its CIS pass rate, open CIS failures by severity, and open vulnerability findings by severity; sortable and filterable by tag.
- Fleet-wide counts of open findings by severity at the top, and a link or summary from the Phase 1 fleet list.
- Hosts that are not evaluated are visibly distinct from hosts with no findings.
- Efficient queries (no N+1, aggregated in the database).
- Delivered as `GET /compliance?q=&tag=&status=&cis=&vuln=&sort=&page=`, `ComplianceController`, and `FleetCompliance`, with the **Compliance** item in the top navigation after Fleet (owner decision Q10), as the approved mockups compliance.html, fleet.html, and states-empty.html and owner decisions Q8 and Q9 say. Per-host counts are lateral subqueries on `cis_results` and on open and reopened `vulnerability_findings` with their advisories, so a page reads only its own hosts' rows; a CIS failure takes the severity of the rule version that produced it (the current version when it names none), as the Configuration tab does, and the pass rate is the host page's, passed / (passed + failed + not readable) (Q3). The fleet-wide counts are one more aggregate over every active host, whatever the filters, so each equals the sum of its column in the unfiltered table; each count links to `?cis=` or `?vuln=` with that severity. CIS-aligned checks are not evaluated on a host with no pass, fail, or not readable result (with the reason: no rules, no config report, or no check with a pass or fail result yet); vulnerabilities are not evaluated when the host's last matching run could not evaluate it, or before matching has run (`HostContext` gives the reason). Findings kept from an earlier evaluation are still open and still counted, as on the host's tab, and the row says they are from an earlier evaluation; the host counts as not evaluated in "N of M hosts evaluated" (owner decision on #128). Three looks never meet: a grey 0 (a severity with nothing open on a host with something open), "None open" (evaluated, nothing open), and "Not evaluated" with its reason; a strip with no host evaluated is replaced by a "Not evaluated" line rather than zeros. Status filters: has open failures or findings, has critical or high (CIS and vulnerabilities together), no open findings (evaluated for both, nothing open), and not evaluated (either part not evaluated, which is what the "see which and why" link lists) (owner decision on #128). `?ecosystem=` (a supported ecosystem such as `Debian:13`) keeps the hosts whose inventory reports that distribution release (`Ecosystems::TABLE`), for the Data sources page's "Hosts using it" link (owner decision on #128). Sorts: worst first (Q9: nothing evaluated at all last and shaded, then critical, high, medium, low, and unknown counts of both kinds together, then lowest pass rate), lowest pass rate, most open vulnerabilities (not evaluated last), and name; ties by name. Pages of 100. The fleet list gains the panel (fleet-wide sentences, or "not evaluated" in words) and the two columns, CIS pass rate and open vulnerabilities, each linking to the host's tab, sortable with not evaluated and not tracked (not active) hosts last in either direction; the per-host counts are joined into `FleetList`'s one row query. The detail under each number names the worst severity open when it is critical or high, for both columns (the mockup named high only for vulnerabilities; owner decision on #128). The cell says "passes N of M checks" (the mockup's "N of M checks"; owner decision on #128), and nothing says "compliant" (ADR 0010). The mockup's "Manage rules" and "Data sources" buttons come with those pages (P2-D06). Live refresh (owner decision on #128): the page and the fleet list are on the fleet stream, and each CIS evaluation run and vulnerability matching run sends one Turbo page refresh (`FleetBroadcast`, enqueued after the run's per-host transactions have all committed) when what they show changed on any host: a CIS result, or the rule version a failure is counted under; a finding opened, reopened, or resolved, or a host's evaluation state, reason, or ecosystem. A run that changes none of these sends nothing; a run after an advisory import that changed advisories always sends one, since a new severity moves the counts with no finding changing state. Every rule changed in one transaction (a rules file import) is evaluated by one `CisEvaluationJob`, so an import is one run and one refresh, and the browser's Turbo debounces refreshes that arrive close together. 50 hosts with 40 rules each (2,000 results) and about 250 open findings render in about 80 ms in 13 queries, the same number as for 3 hosts (`spec/requests/compliance_spec.rb`; the fleet list 14).

### Acceptance criteria

- [ ] Loads in under 2 seconds with 50 hosts ([P2-S12](p2-accept.md))
- [ ] Counts match the underlying findings and results (spec)
- [ ] "Not evaluated" and "zero findings" are never shown the same way

## P2-D06: Rules and data sources management UI

### Scope

- Rules: list with filters, rule detail with version history, add one rule from a form (a single comparison; a rule with several conditions comes in by importing a file), edit the condition and metadata with validation in place, a preview of which hosts would change result before a new rule or an edit is saved (Add rule or Edit, then Preview, then Save; uses the dry run in [P2-S14](p2-rule-dryrun.md); an unchanged definition previews as "no change"), enable and disable (with confirmation), upload a rules file with a preview of what would change before applying.
- Advisory data: show sources, last import, counts per ecosystem, upload an advisory file, trigger a manual feed refresh if [P2-S13](p2-vulns.md) exists, with the cool-down of [P2-S15](p2-refresh-limit.md) (the button is disabled and shows when it is available again).
  - Delivered as `GET /data-sources` ("Data sources" in the main navigation, as drawn: owner decision Q10, confirmed on #129), `DataSourcesController` and `AdvisoryDataSources`, from the approved mockups data-sources.html, data-sources-stale.html, data-sources-import.html, and dialogs.html. Freshness per ecosystem (`Advisories::Freshness`), current and withdrawn advisories, and hosts using it, each aggregated in the database. The scheduled feed shows its host and path only (`Advisories::Feed#source`: never the token, userinfo, or query string), its interval read from `config/recurring.yml`, and whether a token is configured. "Refresh now" is `GET /data-sources/refresh` (the confirmation) and a CSRF-protected `POST` to `Advisories::ManualRefresh.request!`; during the cool-down the button is disabled with "Available again in N minutes (last refresh ...)" from `next_allowed_at` and comes back by itself (`refresh-after`, Q14), and a stale page's request is refused by the server with the time it is next allowed. With no feed configured the page and the freshness notice say automatic refresh is off and offer no button. Upload is a CSRF-protected `POST /data-sources/upload` of a `.json` record or a `.zip` archive (only these two: owner decision on #129), up to 64 MiB (the server's request body limit; larger archives go through `bin/rails advisories:import`), imported in the background (owner decision on #129, a scope change from importing while the operator waits). The file is stored with its import, queued, in one transaction (`advisory_uploads`, audited `advisory.uploaded`), at most 3 at once, and `AdvisoryUploadImportJob` imports it with `Advisories::Import`, which finishes the same `advisory_imports` row, audited with the operator. The file is kept in the database rather than on disk, so the job can read it in whichever process or container runs it, and nothing is left where the web server could serve it. The job deletes it however the import ends; `AdvisoryUploadPruneJob` (every 10 minutes) deletes any left after an hour and fails their imports with a reason. An unreadable file fails the import with the reason and no retry; any other error is retried with backoff, then fails the import with a reason and the job, so it shows on the failed-jobs page. The import's page, `GET /data-sources/imports/:id`, shows queued and importing, refreshing itself every 2 seconds (`refresh-after`) until the import is done, then the counts, re-matching (stored on the import as `matching`), and each malformed record's location, id, and reason; an unreadable file imports nothing and says why. A full import opens the full import confirmation (the `confirm-full` Stimulus controller), and the server refuses a full import that did not come from its button. The stale notice on this page counts the refreshes that failed since the last success; elsewhere it links here. Deviations from the mockups (owner decisions): `.gz` and `.tar` are not offered, since the importer reads JSON and zip only; "Refresh" says "up to 5 attempts" (5 attempts, not 5 retries); "Hosts using it" is a count, not a link, until the Compliance page ([P2-D05](#p2-d05-fleet-compliance-view-and-fleet-wide-severity-counts)) is on main, which then links it to Compliance filtered to that distribution (owner decision on #129); the "What this does" link is left out, since the full import confirmation says it; and "older imports" are kept indefinitely (freshness needs them), not for the retention period.
- Every change audited with the operator as actor; edits show before and after.

### Acceptance criteria

- [ ] AC-2.2: editing a rule's expected value in the UI re-evaluates and changes results with no agent contact
- [ ] Invalid edits are rejected with errors in place
- [ ] A second manual feed refresh within 5 minutes is refused by the server, and the button shows the time left
- [ ] Adding a rule creates version 1 through the same checks as import, re-evaluates every host, and is audited
- [ ] The edit preview lists the hosts whose result would change, with before and after, and writes nothing
- [ ] The add-rule form previews the new rule's results (pass, fail, and the hosts it does not apply to or that have no config report) before saving, and writes nothing
- [ ] The import preview lists adds, changes, and unchanged rules before anything is written
