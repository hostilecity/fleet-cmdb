# VT-SCORES: Exposure tier and points and work remaining on the summaries, the fleet list, and the summary tiles

Implementation details for the GitHub issue with this key. The issue states only the goal and acceptance criteria; this file is the source of truth for everything else. Goal, requirement IDs, acceptance criteria, and blockers live in [`../issues.yml`](../issues.yml).

Part of [VT-EPIC](vt-epic.md) (approved by the owner, 2026-11-19). The tier, points, and work definitions are the epic's VT-M3 and VT-M4. Drawn in [fleet.html](../../mockups/vuln-triage/fleet.html) and [tiles.html](../../mockups/vuln-triage/tiles.html).

## VT-S07: Tier, points, and work on the summaries

### Scope

- `host_compliance_summaries` gains, recounted by the existing triggers (ADR 0026): `exposure_tier` (0 to 4), `exposure_points` (the published table, each advisory once per host in its worst bucket, "by a control" rows for O1, KEV doubled outside Ignorable, from the findings' stored `kev` flag so a KEV change always recounts, S2), `vuln_attention_undecided` (Needs attention advisories with no accepted risk: VT-OVERRIDES' accepted risks are not due, and counting them on the summaries is #298), `work_items` (source packages to upgrade by F1 or F2, plus 1 for a K2 kernel install, plus 1 for a pending reboot: K1, or the agent's reboot flag), and the run timestamps `fixable_critical_since` and `no_fixable_critical_since`. Whether KEV or EPSS was ever imported, and whether it is stale, is not a column: it is read once per page and shown as a qualifier (B1), so a freshness change rewrites no summary.
- The recount groups the host's open findings by advisory to count each once; measure it at about 4,000 findings per host and at 100,000 hosts with `bin/benchmark`, against ADR 0026's figures.
- Indexes for the sorts, partial on active hosts with the name tie-break: **tier descending, then points descending** (S6, so one known-exploited host always ranks above any number of medium findings), and work items descending.
- The tier and points of a host are computed with whatever KEV and EPSS data is stored; when a source is stale or was never imported, the page shows the tier with "not re-checked against KEV since ..." or "not checked against KEV", never a lower tier.
- Adds the score breakdown ("why N points") and the run badge to the host tab (VT-D04).

### Acceptance criteria

- [x] A host's points equal the table applied to its findings (spec over every bucket and severity, a control, an acceptance, KEV doubled, one advisory on two packages counted once), and a KEV change on a Fix available finding updates them (`spec/services/vulnerability_exposure_spec.rb`; an acceptance is VT-OVERRIDES', #261: it keeps the finding's bucket, so the spec's Needs attention rows stand for it)
- [x] `compliance_summaries:check` covers the new columns and finds no drift (every example of the same spec ends with it)

## VT-D06: Fleet list columns and summary tiles

### Scope

- Fleet list: the "Open vulnerabilities" column becomes **Exposure** (tier word, points, how many need attention) and **Work** (work items: upgrades, a new kernel, a reboot), sorted by keyset (Exposure: tier, then points). The hostname and tags move under the name, so the table fits the page at 1,280 px (N6; measured in headless Chrome). Progress is not on the fleet list (it is a 30-day window the summaries cannot keep; host tab and tiles only, S5c). A vulnerabilities filter (known exploited, needs attention, has a fix, nothing to install, not evaluated). Not evaluated and not tracked hosts read as today, never 0 points.
- Fleet compliance panel: one more line with the bucket totals and work items.
- Host summary tiles: "Open vulnerabilities" becomes **Vulnerability exposure** (tier, points) and **Work remaining** (work items and 30-day progress, read for that host); the Packages tile is dropped, since the Packages tab shows the count (epic decision 18).
- Compliance page: one line of bucket totals under the severity strip, each a filter (`?bucket=`).
- The honesty rules of epic VT-M5 for every badge and run shown here, including the wording during a run's grace.

### Acceptance criteria

- [x] Sorting the fleet list by Exposure (tier, then points) or Work reads one page of summaries in a fixed number of statements at any fleet size (`spec/requests/host_exposure_spec.rb`; the index reads in As built)
- [x] A not evaluated or stale host never shows 0 points, "Nothing to install", or a run badge, and a stale or never-imported KEV source never shows a lower tier (the same spec, and `hosts_spec.rb`)

## As built (#262)

- **Summaries** (`host_compliance_counts` v04, `host_compliance_summaries_refresh` v04, ADR 0026's triggers). Each open advisory of the host counts once, in the worst bucket of its triaged findings (Needs attention, Fix available, Low risk by a control (O1), Low risk, Ignorable), with the stored `kev` flag of any of them. New columns:
  - `exposure_tier` (0 Minimal to 4 Known exploited) and `exposure_points`, by VT-M3's table (`vulnerability_exposure_points`, the same table as `VulnerabilityExposure::POINTS`; a spec checks every cell). Both are NULL until the host is **scored**: its last matching run evaluated it and every open finding has a bucket. A host not evaluated now, or one the upgrade's re-triage has not reached, is never 0 points or a lower tier.
  - `vuln_kev_advisories` (KEV advisories outside Ignorable), `vuln_fix_critical` (critical advisories with a finding in Fix available), `vuln_attention_undecided` (advisories with a finding in Needs attention: every one until VT-OVERRIDES records decisions).
  - `work_upgrades` (source packages with F1 or F2 findings, by `last_source`, which matching keeps current), `work_kernel_install` (K2), `work_reboot` (K1, or the agent's flag, `host_applicability.reboot_required`), and their sum `work_items`; NULL counts until scored.
  - `fixable_critical_since` and `no_fixable_critical_since`, the run's times (below).
- **Listener points** (owner decision 27). `vulnerability_findings.listener` (2 network, 1 loopback only, NULL none; checked by `vulnerability_findings_listener_valid`, only beside a bucket), written by the host's transitions beside `bucket`, `bucket_rule`, and `kev` from the same fresh evidence N5 reads, in whatever bucket the finding ends up; `TriageListenerExpiryJob`'s re-triage clears it, so a score never depends on the clock at read time. Once per advisory, the widest listener among its findings outside Ignorable adds, not doubled: **network 10 / 5 / 2 / 1, loopback only 4 / 2 / 1 / 0** (critical, high, medium, low or unknown): a network listener weighs as much as a control removes, a loopback one less ("Needs the owner's OK"). The upgrade writes it in SQL, before the recount, from the evidence in force (review of #305, S2), so no host is scored without its listener points; measured below.
- **Triggers.** `host_compliance_summaries_changed` v06 also notes a finding whose rule (K2 to K1 changes a work item, not the bucket), listener, or source changed; two row triggers on `host_applicability` note the reboot flag (insert or delete, and an update only when `reboot_required` changes, so steady in-use reports queue nothing). Severity changes already queue a recount (`host_compliance_recounts`).
- **The run** (VT-M5 rule 5, owner decision 7). `no_fixable_critical_since` is when the host's run began; it is kept while a fixable critical is open. When the last one goes, the run carries on if it was open for less than the grace and starts again otherwise (`host_compliance_summaries_refresh` reads the grace from `settings`; a stored value that is not a whole number reads as 7 rather than failing every flush). A run never counts days the server could not see (review of #305, S4): a host that stops being scored (not evaluated, or a finding not triaged) loses its run, and a package report that comes after a gap longer than the badge setting ends it (a row trigger on `host_package_sets` that fires only for gaps over a day, `host_compliance_summaries_flush` v03); a new run starts from then. A gap while the advisory data is stale does not end runs (that is fleet-wide and not the host's doing); the badge is withheld meanwhile ("Needs the owner's OK"). Read by `VulnerabilityExposure.run`: "No fixable critical for 12 days", or during the grace "12-day run · 1 fixable critical, 4 days left". Withheld, saying why, when the package report is older than the badge setting or the host's advisory data is stale (fixes come from it); not shown on a host that is not scored.
- **Settings** (owner decision 7): `vulnerabilities.badge_report_max_age_days` (3; #281 item 5's constant, which progress on the tab now reads too) and `vulnerabilities.run_grace_days` (7), database settings like `retention.days`, changed with `bin/rails settings:vulnerability_badges REPORT_DAYS=3 GRACE_DAYS=7`, audited. They are database settings, not environment variables like `FLEET_SIGNAL_MAX_AGE_HOURS`, because the database reads the grace.
- **Freshness is read once per page** (B1; review of #305, S1). Every source the rules read qualifies the tier and points when it is stale or was never imported: KEV (N1, I5), EPSS (N2), and the Debian tracker data of the release the host was evaluated for (F2, I3 to I5, N3, L4): "not checked against KEV, EPSS, or Debian's tracker", "not re-checked against EPSS since 2026-11-10". None lowers a tier on its own, and a feed going stale rewrites no summary.
- **Fleet list** (VT-D06). Exposure (tier word with its bars, points, how many findings need attention) and Work (work items and what they are, or "Nothing to install" with the Needs attention count and, when not withheld, the run) replace Open vulnerabilities; the hostname and tags are under the name. Sorted highest first only, by keyset on two expression indexes partial on hosts in the fleet (`host_compliance_summaries_exposure`: tier, then points, then name; `_work`: work items, then name), with hosts not active or not scored last; the fleet list lists pending and revoked hosts too, so the indexes cover every host in the fleet rather than only active ones, and the keys are NULL for those. Filter `?vulns=` known exploited (tier 4), needs attention, has a fix, nothing to install (scored hosts with no work and a package report within the badge setting, as the cells say), not evaluated (hosts not triaged yet are in none of these). A package report overdue by `ReportSchedule` adds "as of the package report 2 days ago"; one older than the badge setting turns a 0 into "Not known", never 0 points or "Nothing to install". Kept beyond the mockup: the Last seen and Operating system columns (the table fits at 1,280 px with them; measured below).
- **Fleet compliance panel and Compliance page.** One line of bucket totals with the work items, saying which hosts each covers ("412 fix available (61 work items on 9 scored hosts) · 47 need attention · 11,280 low risk · 23,173 ignorable: open findings of the 10 active hosts, 9 evaluated now"), each a link to `/compliance?bucket=`. The Compliance page's `?bucket=` filter, its select, and each row's "N fix available · N need attention" (linking to the tab's sections) replace VT-FIXABLE's `?fix=available` filter and "N with a fix" lines, as #281 item 1 decided. With nothing reading them, the summary's `vuln_fixable`, `vuln_fix_packages`, and `vuln_fix_severities` are dropped (they cost about 2 ms a host recount); the findings keep their fix flag, which the tab's `?fix=available` line still counts, now worded without the pages that no longer link to it ("Needs the owner's OK").
- **Host summary tiles.** Vulnerability exposure (tier, points, known exploited advisories, findings that need attention, the KEV qualifier) and Work remaining (work items, what they are, the findings they clear, and the 30-day progress as a native `<meter>`, from that host's work events) replace Open vulnerabilities and Packages (epic decision 18). Three statements more per host page (the summary row, the 30-day events, the settings), one less (the Packages tile's last change), and one for KEV's freshness when the host is scored.
- **Host tab.** "Why N points" (`HostExposure`, one grouped query for the host): the advisories by worst bucket, known exploited apart, Fix available split into kernel steps and package upgrades, a row per listener kind, and the total, which is the summary's; the published table and the tier rule under it. The run badge is in Progress. Work remaining lists the agent's reboot flag when no K1 finding names the kernel ("the host reports that one is required, for libc6"), so the tab and the summaries count the same items.
- **Measured** (`docs/operations/benchmark.md`, "Exposure scores on the summaries"; 100,001 hosts, 1,201 with 3,560 to 4,450 open findings, 200 rewritten to a realistic bucket mix): the counts 16 to 18 ms a host against v03's 11.6 to 11.9 (+4 to 6 ms, paid only by hosts whose counts changed; one pass over the findings, grouped by advisory and by source package); the fleet list sorted by exposure or work, 101 index rows a page, 10 statements and 4.9 ms for two pages of each; `compliance_summaries:check` 75 s, no drift; the upgrade's recount 53 s, inline (estimate 77 s). At 1,280 px the fleet table fits its frame (1,166 px); axe-core reports no violations.
- **Upgrade.** `20261123262001` (metadata-only columns, functions, triggers, the listener check `NOT VALID`, the progress row), then `20261123262002`: the two indexes concurrently (an index a stopped build left INVALID is dropped and built again, as #196's), each finding's listener written in SQL, the listener check validated (or left for `vulnerabilities:validate_triage_checks` on a large table), and the resumable recount, with its own rates (20 microseconds a finding, about 2.5 times measured) (`ComplianceFixRecount`, now given its progress table; inline when its estimate is at most 90 s, else the upgrade step `bin/rails compliance_summaries:recount_scores`, `docs/operations/upgrades.md`).
