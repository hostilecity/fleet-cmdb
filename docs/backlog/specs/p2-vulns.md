# P2-VULNS: Advisory import and refresh, and vulnerability findings

Implementation details for the GitHub issue with this key. The issue states only the goal and acceptance criteria; this file is the source of truth for everything else. Goal, requirement IDs, acceptance criteria, and blockers live in [`../issues.yml`](../issues.yml).

## P2-S10: Advisory model and OSV import

### Scope

- Tables for advisories and their affected packages per [DEC-11](../../decisions/0011-vulnerability-data.md): advisory id, source, ecosystem (release scoped), package (source name), range events (introduced and fixed), severity (normalised and raw), reference URL, published, modified, and withdrawn.
- Importer for the chosen format (OSV JSON per [DEC-11](../../decisions/0011-vulnerability-data.md)) accepting a file, a directory, or an archive via `rake advisories:import`; idempotent by advisory id and `modified`; withdrawn advisories are retained and marked so existing findings resolve.
- Validation: reject malformed input without partial writes; cap file size; sanitise text; only `http` and `https` reference URLs are stored.
- Severity normalisation rule from [DEC-11](../../decisions/0011-vulnerability-data.md).
- Import audited (who, what source, counts).
- Triggers targeted re-matching ([P2-S11](p2-vulns.md)) for packages named in changed advisories.
- Malformed input, decided here because [DEC-11](../../decisions/0011-vulnerability-data.md) does not say: OSV publishes one record per file, so a malformed record is reported (where, which id, why) and skipped, and the valid records import. A record never imports in part. Input that cannot be read at all (an unreadable archive, a broken limit) imports nothing.
- Delivered as `Advisories::Import`, `Advisories::Reader`, `Advisories::Record`, and `Advisories::Severity` (`cmdb/app/services/advisories`), `bin/rails advisories:import FILE=... [FULL=1]` and `advisories:status`, and the tables `advisories`, `advisory_packages` (one row per advisory, ecosystem, and source package, with the OSV `ECOSYSTEM` ranges' events, indexed by ecosystem and package), and `advisory_imports` (`cmdb/README.md`, "Advisory data").
  - **Dashboard uploads** ([P2-D06](p2-dash-fleet.md)) use the same importer in a background job: `advisory_imports` rows can be `queued` and `importing` (with no `finished_at`) before they succeed or fail, and `advisory_uploads` holds the file until the job has read it. Uploads are read with lower limits (`Advisories::Reader::UPLOAD`) within a time limit, and are for small files: a full archive comes through the feed or the rake task (owner decision on #129).
  - **Withdrawal guard** (owner decision on #129, a scope change). Every full import is guarded against mass withdrawal: the scheduled refresh, `bin/rails advisories:import FULL=1`, and a full upload (review of #129, owner decision). Before the absence sweep writes, the import counts per ecosystem how many current advisories it would mark withdrawn. If that is more than `FLEET_ADVISORY_WITHDRAW_SHARE` (0.10) of an ecosystem's current advisories, or any of them when the import has fewer than `FLEET_ADVISORY_WITHDRAW_MIN_RECORDS` (1,000) records for that ecosystem, it is refused: nothing is written, and the import is recorded as held back (its own state, `held_back`, not a failure) and audited as `advisory.import_held_back` with the counts per ecosystem. The share is of the ecosystem's current advisories before the import, so advisories it adds cannot dilute it. An operator's allowance is a ceiling, not a bypass: once one is given, each ecosystem may withdraw at most its allowed count (none for one it does not name), whatever the thresholds say (review of #131). The rule and its thresholds are the same for every ecosystem. `bin/rails advisories:import FULL=1` prints the counts and is run again with `ALLOW_WITHDRAWALS=<ecosystem>:<count>[,...]` naming them; an upload's result page offers a confirmation that names them. Delivered in `Advisories::Import#check_withdrawals!`, with the thresholds in `config/initializers/advisories.rb`.
  - **Ecosystems.** `Ecosystems` (`cmdb/app/models/ecosystems.rb`) is the fleet-profile table, built here because the importer keeps only its ecosystems: `debian` `13` → `Debian:13`. Records for other ecosystems are skipped.
  - **Transactions and limits.** One transaction per import, under an advisory lock. Each document is read to at most 2 MiB; an archive may be at most 512 MiB (`FLEET_ADVISORY_MAX_DOWNLOAD_MB`), a million documents, and 8 GiB of JSON read, which counts refused entries too. Sized against the real archive: measured by the owner on 2026-11-07, OSV's Debian `all.zip` was 77.4 MiB zipped, 73,658 JSON records, 260.9 MiB of JSON in all, and its largest record 34.1 KiB (`DLA-4008-1.json`), which leaves 6x to 60x headroom; check again when distributions are added. A record whose shape the parser did not expect is reported as malformed rather than rolling back the import.
  - **Stored values.** Text has control characters removed and a length cap; summaries are at most 512 characters. Ids, package names, and range versions are pattern-checked; whether dpkg can parse a version is left to matching.
  - **Severity rule.** A CVSS v3 base score (computed from the vector, banded as CVSS bands it), then `database_specific.severity`, then a Debian urgency, else unknown. The raw value is kept. v2 and v4 vectors are kept as raw but not scored.
  - **Withdrawn and absent advisories.** Withdrawn advisories are kept and marked. A full import (the refresh, or `FULL=1`) also marks advisories it does not contain as withdrawn (`absent`), because OSV moves withdrawn records out of an ecosystem's archive, so the archive alone would never withdraw anything. This was added beyond the original scope. The sweep is skipped when any record was malformed. It only touches advisories no newer than the newest record in the import, so an older archive, or an older download imported after a newer one, cannot withdraw advisories it never knew about.
  - **Re-matching.** The import returns the packages that changed advisories name, before and after. Once it commits, a fleet-wide `EvaluationRun` re-matches those packages on the hosts that have them (#197) ([P2-S11](#p2-s11-vulnerability-matching-job-and-finding-lifecycle)).
  - **Measured** (sandbox, PostgreSQL on the same machine), with a synthetic 60,000-record archive of 29.5 MiB, 40,000 records for `Debian:13`: a first import took 25 s, and re-importing it, which changed nothing, took 14 s.

### Acceptance criteria

- [ ] Re-importing the same data changes nothing
- [ ] Updated advisories replace older versions and trigger re-matching
- [ ] A malformed record is reported and does not prevent valid records from importing (decided above, since [DEC-11](../../decisions/0011-vulnerability-data.md) does not decide it)
- [ ] Reference URLs with other schemes are rejected

## P2-S13: Advisory feed refresh job and data freshness indicator

### Context

Stale vulnerability data fails silently: the dashboard would report zero findings while advisories are weeks old. [DEC-11](../../decisions/0011-vulnerability-data.md) chose a scheduled download of OSV data for `Debian:13`, with manual import as well.

### Scope

- Scheduled job fetching the configured advisory source (HTTPS, certificate verified), with size limits, conditional requests where supported, and the importer from [P2-S10](p2-vulns.md).
- Source configuration and any API key stored in Rails credentials or environment, never logged or shown.
- Dashboard shows "advisory data last updated" per ecosystem, with a clear warning when older than a configured threshold, and the same on [P2-D04](p2-dash-host.md) and [P2-D05](p2-dash-fleet.md).
- Failures retry with backoff and surface through the failed-jobs indicator ([P1-O02](p1-operability.md)). A refresh the withdrawal guard refuses ([P2-S10](#p2-s10-advisory-model-and-osv-import)) is not a failure: it is not retried and does not page the failed-jobs indicator, but the Data sources page and the freshness notice warn about it, and an operator can confirm its counts.
- A manual refresh from the dashboard has a cool-down: [P2-S15](p2-refresh-limit.md).
- Delivered as `AdvisoryFeedRefreshJob` and `Advisories::Feed`, every 6 hours in production (`cmdb/config/recurring.yml`), and `bin/rails advisories:refresh`.
  - **Source.** The default is OSV's `https://storage.googleapis.com/osv-vulnerabilities/Debian/all.zip`. OSV publishes no per-release archive, so this covers every Debian release and the importer keeps `Debian:13`, and `Debian:14` for matching trixie's backports (#274). Set `FLEET_ADVISORY_FEED_URL` empty to turn the refresh off.
  - **Download.** HTTPS only, with the certificate verified (`VERIFY_PEER`). At most 3 HTTPS redirects, at most `FLEET_ADVISORY_MAX_DOWNLOAD_MB`, and within 15 minutes for the whole exchange (`Timeout`), including the status line and headers. Requests are conditional (`If-None-Match`, `If-Modified-Since`), unless the last download had malformed records, in which case the archive is fetched in full again. A 304 is recorded as a successful refresh that imports nothing and is not audited. The import is full.
  - **Token.** An optional bearer token comes from `FLEET_ADVISORY_FEED_TOKEN` or credentials (`advisories.feed_token`) and is sent only to the configured host. Errors, logs, and stored sources name only the feed's host and path, never the query or the token.
  - **Withdrawal guard** (owner decision on #129). A refused refresh writes nothing; it is recorded as held back with the counts per ecosystem and audited as `advisory.import_held_back`, and the job ends normally (no retry, no failed job). It is not counted among failed refreshes, so the stale notice never reports a failure for it (review of #131). `Advisories::Freshness.held_refresh` is the newest refusal no refresh has succeeded since and no operator has confirmed: the freshness notice on every page that shows it says the refresh was held back and the data may be going stale. An operator confirms the counts on the refusal's page (`Advisories::ManualRefresh.confirm_withdrawals!`), once, which records a manual attempt, audits `advisory.withdrawals_confirmed`, and runs the same job with `allowed_withdrawals` up to the counts, downloading the archive again (it is not stored: a full archive is larger than the upload store holds, and the new download is held to the confirmed counts). `bin/rails advisories:refresh` prints the counts and takes `ALLOW_WITHDRAWALS`.
  - **Failures.** Any failure is retried 5 times with backoff. After the last attempt it is recorded as a failed import, audited (`advisory.import_failed`), and raised, so it shows on the failed-jobs banner and page and in `/health`. `bin/rails advisories:refresh` makes one attempt and records and audits a failure the same way.
  - **Freshness.** `Advisories::Freshness` dates each ecosystem by its last successful full import. The fleet page shows "Advisory data last updated", or a warning when the data is older than `FLEET_ADVISORY_MAX_AGE_HOURS` (48) or was never refreshed. The warning reuses the existing notice style, since there is no Phase 2 mockup yet. The same indicator on [P2-D04](p2-dash-host.md) and [P2-D05](p2-dash-fleet.md) is built with those views.

### Acceptance criteria

- [ ] A failed or timed-out fetch retries and is visible to an operator
- [ ] The freshness warning appears when data is older than the threshold
- [ ] No secret appears in logs or error messages

## P2-S11: Vulnerability matching job and finding lifecycle

### Scope

- A host-to-ecosystem mapping from the inventory's distribution id and release (table maintained with the [DEC-01](../../decisions/0001-fleet-profile.md) fleet profile). Hosts with no mapping or no advisory data show "not evaluated" with the reason.
- Matching on source package name within the host's ecosystem, comparing the installed version to affected ranges with the manager's comparator ([P2-S09](p2-packages.md)). One finding per host, package, and advisory.
- Finding states: `open`, `resolved` (installed version outside every affected range, whether the package was updated or the advisory's ranges changed; package removed; or advisory withdrawn), and `reopened` (condition returns). Timestamps for first seen, resolved, and reopened.
- Decision (skipped packages, [P2-S08](p2-packages.md)): a package the agent reports as skipped (an interrupted installation) is not installed as far as matching goes, so its findings resolve as `removed` and reopen when the package is listed again. The matcher does not read the skipped names. A host whose package database was unreadable is not evaluated and its findings stay as they were.
- Runs in a background job triggered by a new package snapshot (that host only) and by advisory imports (affected packages only). Idempotent.
- Efficient for 50 hosts by 2,000 packages: indexed lookups by ecosystem and package, no per-package queries in loops.
- Delivered as `VulnerabilityMatcher` (`cmdb/app/services/vulnerability_matcher.rb`, ranges in `vulnerability_matcher/ranges.rb`), `HostContext`, and `VulnerabilityMatchJob`, with the tables `vulnerability_findings` and `host_vulnerability_evaluations` (`cmdb/README.md`, "Vulnerability findings").
- Scale (#197): after an import, `VulnerabilityMatchJob` no longer matches the fleet in one job. A fleet-wide `EvaluationRun` (`EvaluationRun::Advisories`) finds the affected hosts with the source-package indexes (#185; since #196, the chunks holding a changed source, then the sets holding them, then their hosts), or no evaluation with data yet. It splits them into keyset ranges of at most 1,000 host ids, one `EvaluationBatchJob` each on the `evaluation` queue. A batch runs its range's transitions (since #196, in full, from chunk verdicts), its hosts locked in id order in short transactions. "No advisory data yet" is a correlated `NOT EXISTS` on the evaluations' `host_id` index. Batches are retry-safe and counted once; an import of the same sources (or more) supersedes an unfinished or failed run, and a failed run can be started again from the page (`EvaluationRun.retry!`, under the run's row lock, so a second press changes nothing; a run with batches left carries on from them, so a failed run keeps its batches). A run whose worker is killed (#278: Solid Queue 1.7 fails its job without a retry, and `after_discard` never runs) is resumed by `EvaluationRunWatchJob`, triage's watch (VT-BUCKETS) shared by every kind: every 10 minutes it reads the live jobs, then the runs untouched for 10 minutes, and, re-checked under the row lock, queues a dead run's fan-out again, which prepares it again or queues its remaining batches (a running run with none left is finished). After 3 resumes in a row with no progress (state and batches done unchanged) the run is failed with the reason "stopped", shown on Data sources with what to check first (the job workers' memory and restarts) and the button, whose run starts the count again: **Re-match the remaining hosts** when it has batches left, **Re-match again** when it starts over (review of #292). Preparation records a checkpoint (#295, `EvaluationRun::Checkpoint`: columns `prepare_step` and `prepare_cursor`): the import's stamp is read once and kept in the scope, then each ecosystem's chunks are matched in id order, 1,000 at a time, and the cursor (the last chunk id) moves after each page; then the restamp. A resume, and the retry of a run stopped before it was split ("Stopped: before its hosts were found", button **Re-match again**, which reopens the same run), carry on from the checkpoint, and a move of it counts as progress (`resume_progress` holds the step and cursor with the state and batches done), so a long preparation (a kernel source at a million hosts) survives any number of deploys as long as each attempt moves it. Each page commits before the cursor moves, and matching with force is idempotent, so a page killed part way is matched again whole. Each checkpoint write is a compare-and-set on the run's row (from where this preparation left it, while the run is queued): a second preparation of the same run, or one of a run superseded meanwhile, stops at its next write. The split that follows is one transaction, so a run's batches are all there or none are (the batches' unique `(run, position)` index also forbids a second copy). Rule runs (P2-S06) are watched the same way. The Advisory data sources page shows the progress as plain text while the run is unfinished, and the dashboard refreshes once when it finishes. A new package snapshot still matches that host in one `VulnerabilityMatchJob`.
  - **Ecosystem mapping.** `Ecosystems` (from [P2-S10](#p2-s10-advisory-model-and-osv-import)) maps the inventory's os id and version to an ecosystem.
  - **Ranges.** OSV's evaluation algorithm over `ECOSYSTEM` ranges: `introduced`, `fixed`, `last_affected`, `limit` (an exclusive upper bound on the range), and `introduced: "0"` for all versions. A finding's fixed version is the fix of the range the installed version is in, or none when that range has no fix. Versions are compared with `PackageVersions` (dpkg), never as strings.
  - **Not evaluated.** A host is not evaluated, with a reason and a sentence, when it has no inventory, is on a distribution outside the fleet profile, has no package report, has an unsupported manager, or its ecosystem has no advisory data. Its findings are then left unchanged. A version dpkg cannot parse, installed or in a range, leaves that package and advisory not evaluated: it is listed (at most 100, all counted) and its finding is unchanged.
  - **Finding states.** Resolutions are `fixed`, `removed`, `withdrawn`, and `not_affected` (the advisory stopped naming the package). `resolved_at` keeps the last resolution after a reopen. An advisory withdrawn by an update that lists no packages still resolves its findings as `withdrawn`.
  - **When matching runs.** After commit, for the host, when `PackageRecorder` writes a new snapshot. After an import, for the hosts on sets holding a chunk with a changed source package, and for hosts never evaluated or evaluated as "no advisory data". Since #196 every run covers the host's whole set (from its chunks' verdicts), so there is no targeted run and the not-evaluated count is always exact. On demand: `bin/rails vulnerabilities:match`.
  - **Concurrency.** Hosts are handled in batches, each in a short transaction holding its hosts' row locks (`FOR UPDATE` in id order, as every package report and heartbeat takes it), so matching never sees half of a report; a batch is sized from the last one's time to hold its locks for about 0.2 s (#196). Chunks are matched before the locks are taken. Per batch there is a fixed number of queries whatever the package count, and writes are batched upserts.
- Decision (binary packages): one finding per host, advisory, and installed binary package (name and architecture). Binary packages built from one source each get their own finding, because each is installed, updated, and removed on its own, and the operator acts on what dpkg lists. Multi-arch copies (`libssl3t64:amd64` and `:i386`) are separate findings. Dashboards may group them by source.
- Matching per chunk (#196, [ADR 0028](../../decisions/0028-content-addressed-package-sets.md)): what is matched, what a finding is, and the lifecycle above are unchanged; the unit of matching is a package chunk (P2-S08's storage). `VulnerabilityMatcher::Chunks` matches each distinct chunk once per ecosystem into `chunk_matches` (the affected packages, with the installed and fixed versions) and `chunk_evaluations` (which chunks are matched, stamped with the newest succeeded advisory import, read before the data, and the package and advisory pairs dpkg could not parse). A host's current findings are its set's chunks' verdicts. Before a host's transitions, every chunk of its set must be evaluated for its ecosystem and current with the newest import, or it is matched first; a set naming a chunk that is not stored refuses that host's transitions and fails the job. `vulnerability_findings` keeps only the lifecycle (key, state, resolution, first seen, resolved, reopened); its source and versions are the verdict's while it is active, and `last_source`, `last_installed_version`, `last_fixed_version`, and `last_ecosystem` keep them at each transition for a resolved finding; a resolution takes them from the finding's verdict in the set the host's findings were last moved from, and an open finding's moved fix or source is written, so a resolved finding shows the source the advisory matched, its last versions, and its own release, as before #196. An import's `EvaluationRun` matches the chunks holding a changed source again, moves every other evaluation to the new import when no import since its stamp changed one of its sources (each import records what it changed; a not-modified feed refresh stamps nothing), and runs the transitions of the hosts on sets holding those chunks (and of hosts never evaluated), in batches locked in id order and sized to hold their locks for about 0.2 s (`LOCK_TARGET`, as #204). Transitions always cover the host's whole set: they only read verdicts, and a host whose findings do not change writes nothing. `bin/rails vulnerabilities:match` matches every evaluated chunk again, then every host.
- Time budget: 20 s for 50 hosts by 2,000 packages. Measured (`spec/services/vulnerability_matcher_performance_spec.rb`, sandbox, PostgreSQL on the same machine), with 600 advisories over 300 source packages and 20,000 findings opened: 5.0 s and 354 queries (about 7 per host). Matching again, with nothing changing, takes 2.5 s.

### Acceptance criteria

- [ ] AC-2.4: importing an advisory for an installed version creates an open finding; after the package is updated on the VM and re-reported, the finding resolves
- [ ] A downgrade or reinstall of a vulnerable version reopens the finding
- [ ] Binary packages built from the same source package yield one finding per binary package actually installed (decision recorded and tested)
- [ ] Matching 50 hosts completes within the time budget recorded in the PR
