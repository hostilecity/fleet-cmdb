# P3-AGENT-LEDGER: Agent task config, capabilities, poller, and durable ledger

Implementation details for the GitHub issue with this key. The issue states only the goal and acceptance criteria; this file is the source of truth for everything else. Goal, requirement IDs, acceptance criteria, and blockers live in [`../issues.yml`](../issues.yml).

## P3-A01: Agent: local task configuration, embedded catalog, and capability reporting

### Scope

- `[tasks]` section in the agent config: enabled task types (default: none or only `refresh_reports`, per [DEC-14](../../decisions/0014-task-trust-model.md)), allowed services, limits. Invalid configuration fails safe (nothing enabled).
- The task catalog is compiled into the binary from the shared catalog file ([P3-S01](p3-task-model.md)); the agent never loads task definitions at runtime from the server.
- Reports supported task types, enabled task types, and catalog version to the server (heartbeat or inventory), so the server only offers what the host will run.
- Config validation message when a listed type or service is unknown.

### Acceptance criteria

- [ ] With default configuration, `apply_package_updates` and `restart_service` are not enabled
- [ ] The catalog compiled into the binary matches the shared file (build-time check)
- [ ] The server sees the capability report and stops offering disabled types

### As built

- **Catalog.** The shared file is `docs/api/tasks/task-catalog.json` (JSON, not YAML, so the agent reads it with `serde_json` and has no YAML parser; [P3-S01](p3-task-model.md)). The agent compiles in that file itself with `include_str!` (`agent/src/tasks/catalog.rs`), with no copy to drift. A unit test compares the compiled-in bytes with the file, `agent/tests/contract.rs` checks that the `include_str!` path is the shared file and that the file passes its schema, and the server's contract spec checks that no other copy exists. Building the agent therefore needs the repository, not just `agent/`, and the Docker command in `agent/README.md` mounts the root. The agent parses the catalog on first use, reads every field and refuses unknown ones, and checks what it relies on: format 1, unique type ids, `since` within the catalog version, only `read_only` types on by default, and closed parameter schemas. A catalog that failed these checks would leave the agent supporting nothing; the unit tests parse it, so that fails CI first.
- **Config.** `[tasks]` in the agent config, with `enabled` (task type ids; absent means the catalog's `enabled_by_default` types, which is `refresh_reports` alone, and only a `read_only` type can be on by default) and `allowed_services` (full service unit names matching the catalog's `service` pattern, at most 64, empty by default). Protected units (DEC-15) are refused even when listed: the agent's own units (`fleet-agent*`), `ssh`/`sshd`, `systemd`/`systemd-*`, `networking` and `NetworkManager`, `dbus` and `dbus-broker`, template instances included. `apply_package_updates` has no local setting (DEC-16 fixes its policy). There are no other limits in this section: the poll interval belongs to P3-A02 and timeouts come from the catalog and the server (P3-A03). Code: `agent/src/tasks/settings.rs`.
- **Fails safe.** The section is validated as strictly as the rest of `config.rs` (unknown keys, wrong types, unknown types, malformed, protected, or repeated services), but an error turns every task off instead of stopping the agent: heartbeats and reports carry on, the error is logged at startup, the capability report says `local_config: invalid`, and `fleet-agent check-config` fails with exit 78 and the message. Messages name an unknown type and list the catalog's, and never repeat a configured service name. `fleet-agent install` keeps the section when it rewrites the config; one that was invalid is written as `enabled = []` with the old error in a comment, so a reinstall never turns a task on.
- **Capabilities.** Every heartbeat (including the installer's first) carries `tasks`: `catalog_version`, `supported` (the types this agent version implements: none until P3-A03 onwards fill `tasks::IMPLEMENTED`), `enabled`, `allowed_services` (the local restart allowlist, sorted), and `local_config`. The heartbeat was chosen over inventory so a change shows within a minute of the agent restarting. Schema and examples in `docs/api` (`heartbeat.request`); the heartbeat body limit rose to 32 KiB for the largest lists the schema allows. The local service allowlist is reported so the server leaves out a host that would refuse a restart before anything is sent (owner, P3-D01 Q7); the agent still refuses a restart outside it (AC-3.9), and the server's own allowlist is P3-S05's.
- **Server.** The heartbeat writes the report to the host columns P3-S02 added (`task_catalog_version`, `task_types_supported`, `task_types_enabled`, `task_capabilities_reported_at`) and `task_services_allowed`, in the heartbeat's one UPDATE (`Liveness.record_heartbeat!`). `local_config: invalid` stores no enabled types and no services. A restart of a service the host does not list is excluded with `not_allowed_locally`. A heartbeat without `tasks` clears the columns, so the host is excluded with `no_capability_report`. `Host#task_exclusion_reason` (P3-S02) reads them when a batch is created, which is how the server stops offering disabled types. `local_config` itself is not stored yet; a dashboard view (P3-D*) can add it.
- **Not in this part:** the poller and ledger (P3-A02), and showing capabilities, including `local_config`, on the dashboard (P3-D*).

## P3-A02: Agent: task poller and durable local task ledger

### Scope

- Poll at a configurable interval (default 30 seconds) and promptly when the heartbeat directive says tasks are available; at most one task in flight; backoff on failures as in [P1-A02](p1-agent-core.md).
- A durable ledger in the state directory (append-only records, `fsync`ed) with these steps per task id: `received`, `started`, `finished`, `reported`.
- **The `started` record is written and flushed before anything is executed.** Only then is the server acknowledged ([P3-S03](p3-task-api.md)) and the task run.
- A task id already present in the ledger is never run again. At startup the agent reconciles: `started` without `finished` is reported as `failed` with reason `interrupted`; `finished` without `reported` is re-reported; unknown states are reported, not executed.
- Ledger growth is bounded (compaction of old reported tasks).
- Result reporting retries until accepted, idempotently.
- An agent update ([P1-AGENT-UPDATE](p1-agent-update.md)) is deferred while a task is in flight, and an update in progress blocks new claims until it is confirmed or rolled back.

### Acceptance criteria

- [ ] Duplicate delivery of the same task id results in one execution
- [ ] Killing the agent after the `started` record is written and restarting reports `interrupted` and does not re-run the task
- [ ] A corrupted or truncated ledger tail is handled without running anything that may have run before

### As built

- **Ledger.** `task-ledger.jsonl` in the state directory (mode `0600`), so the unit's `StateDirectory=` sandbox allows it; `scripts/sandbox-smoke.sh` checks the sandboxed agent creates it. Append-only lines of `<16 hex digits of SHA-256> <JSON>`, one per step: `received` (id, type, catalog version, `timeout_seconds`, parameters), `started`, `finished` (outcome and reason), `reported`, and, after compaction, `done`. Each append is `write` then `fsync`, and the directory is flushed when the file is created or replaced, before the step returns. An append that fails leaves the ledger unusable until it is reopened from the file. The full result body (with `report_id` and output) is written atomically to `task-result.json` before `finished`, so a re-report sends the same body and the server sees a duplicate. An exclusive `flock` (`task-ledger.lock`) keeps a second process out. Code: `agent/src/tasks/ledger.rs`.
- **Never twice.** A task id already in the ledger, in any state, is never received again, and `started` can only follow `received`, once. The poll's redelivery of a claimed task (P3-S03) therefore runs nothing.
- **Order.** `received`, then the local checks, then `started` (flushed), then `start`; the task runs only after `run: true`. Any other answer is recorded as not run and answered, with no result sent (`docs/api/README.md`). A failed `start` is retried with backoff, and nothing runs meanwhile; a `401`, `403`, or `426` gives up on the task (it stays `started`, so recovery reports it `interrupted`), so the task slot never holds back the update a `426` needs.
- **Recovery** before any poll, starting with the task whose result is stored (no other task's recovery may overwrite it): `received` or `started` with no stored result is reported `failed`/`interrupted` and never run (the contract has no `not_run` reason, so L2's proposed distinction is not made; the server's own `lease_expired` covers the lost-acknowledgement race); `started` with a stored result sends that result; `finished` re-sends the stored body (a body rebuilt from the ledger, when the stored one is lost, is stored before its first send, so retries keep its `report_id`); a valid record this version cannot read is an unknown state, reported `failed`/`agent_error`.
- **Corruption.** Only an unterminated last line is a torn tail: a bad one is dropped, and a whole record missing only its newline is kept (the safe reading). A bad line that ends in a newline, anywhere, an unreadable file, or a missing ledger beside a damaged copy (a crash while repairing) keeps the readable records, saves the file as `task-ledger.damaged`, and records a hold of 25 hours (the catalog's longest `expiry_seconds` plus its longest `timeout_seconds`), during which every task received is reported `failed`/`agent_error` and nothing runs: by then every task that existed before has expired or ended on the server.
- **Size.** Records at most 16 KiB (parameters at most 4 KiB), the file at most 1 MiB. Past 256 KiB, once every task is reported, it is rewritten with a `done` line for each of the last 1,000 ids and for every id reported within the 25-hour hold window, with its own reported time, so an id is known for as long as the server could deliver it. A full ledger that cannot be compacted receives nothing (fails closed).
- **Poller.** A fifth loop in `report::run` (`agent/src/tasks/poller.rs`). A delivery it does not take (an id it already has) waits the poll interval before the next poll. It polls only when a type is enabled locally and implemented (`tasks::IMPLEMENTED`), every `[task_poll] interval_seconds` (default 30, allowed 5 to 3600; the server sends no interval, so `min`/`max` only bound a future directive) and within 5 s of a heartbeat carrying `tasks_available`. Failures back off as in P1-A02. Refusals with nothing started: `unknown_type`, `not_enabled_locally`, `not_supported`, oversize parameters as `invalid_params`, then the executor's own checks. Results are retried until a `200`; `404`, `409 task_conflict`, and `422` are final, recorded as `reported` with `rejected`, and the id still never runs again. Every decision is logged with task id and type (threat model A3); parameters stay in the ledger only.
- **Updates.** The poller holds the updater's task slot from each poll to the end of the task (`Updater::task_slot`): an `agent_update` directive that arrives meanwhile is deferred until a later heartbeat, and while an update record exists (until confirmed or rolled back) the poller does not poll (L7).
- **No executor yet.** `agent/src/tasks/executor.rs` is the seam for P3-A03: `implements`, `check` (typed parameters, local allowlist, protected units), and `run`, called only after `run: true`. This build's `NoExecutor` implements nothing, so the agent reports no supported type, the server offers it nothing, the poller never polls, and a task that arrived anyway would be refused `not_supported`. The tests drive steps 4 to 6 with a counting executor, including a crash after each step.
- **Left for later:** progress reports and the reconciliation of a still-running transient unit (L8) belong to the executor (P3-A03, P3-A04); a real kill-and-restart matrix on a VM is P3-X03.
