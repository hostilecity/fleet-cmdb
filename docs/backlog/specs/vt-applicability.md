# VT-APPLICABILITY: The agent reports listening services, the reboot flag, and (where enabled) library use

Implementation details for the GitHub issue with this key. The issue states only the goal and acceptance criteria; this file is the source of truth for everything else. Goal, requirement IDs, acceptance criteria, and blockers live in [`../issues.yml`](../issues.yml).

Part of [VT-EPIC](vt-epic.md) (approved by the owner, 2026-11-19), not in the first cut (epic decision 21), and blocked by VT-HOST-TAB because it adds the in-use signals to the tab (the agent half can be written earlier). It feeds rule N5 (owner decision 2026-11-21: in-use evidence only escalates; [VT-EPIC](vt-epic.md) decision 27) and the reboot work item. This slice writes the adapter `VulnerabilityTriage::HostFacts.listener_source` (#277 leaves it off). It is an agent contract change ([FR-2.3](../../requirements.md#fr-23-package-reporting)); no backward compatibility is needed before Phase 3 ends (NFR-5). The agent reports facts and the server decides; nothing here runs a command chosen by the server.

## What the server already knows without this slice

The package report lists every installed kernel image and the inventory has the running kernel release (`kernel_version`), so rules I1, K1, and K2 and "reboot into the installed kernel" need no agent change (VT-S05). In trixie each kernel update is a new package, so "a newer image is installed and not running" is exactly a pending kernel reboot. This slice adds what the server cannot infer.

## VT-A01: Listening services and the reboot flag, with no new privilege

### Scope

- **Listening sockets**: read `/proc/net/{tcp,tcp6,udp,udp6}` (no privilege): local address, port, state, uid, and socket inode for each listening TCP socket and bound UDP socket.
- **Socket to service**: ask the kernel's `sock_diag` netlink interface for the same sockets with their cgroup id (`INET_DIAG_CGROUP_ID`, what `ss --cgroup` shows); map the cgroup id to its cgroup path under `/sys/fs/cgroup` (the directory's inode number is the id), the path to the systemd unit, the unit to its main executable (`systemctl show --property=ExecStart`, which the agent already runs with fixed arguments), and the executable to its binary package (dpkg's file lists under `/var/lib/dpkg/info/`, read-only). The unit already allows `AF_NETLINK` (`agent/src/install/fleet-agent.service`), so nothing in it changes; the exposure stays 1.9 (`agent/scripts/check-unit.sh` fails above 2.0).
- **Report**, in the package report: `in_use.listening`, each binary package owning a listening service with its class, `network` (any non-loopback address) or `loopback`, and `in_use.services`, the packages of running services' executables. Never process ids, command lines, user names, addresses, or ports. A socket whose cgroup is not a systemd service (a container, a user session) is counted, not named (`in_use.unnamed_listeners`, `network` and `loopback` counts; a service whose executable no package owns is counted there too).
- **Built (#258), decided conservatively:** a socket systemd itself holds for socket activation (cgroup `init.scope`) is named by matching its port and address with `systemctl list-sockets`, so a socket-activated service is not missed; if anything (the sockets, `sock_diag`, the cgroup tree, the services, the file lists) cannot be read whole, `in_use` is `null` with a `warnings` entry (field `in_use`) rather than a partial answer that could make a package look idle; that includes `systemctl list-sockets --show-types` when a socket is held by systemd (in `init.scope`, or, as systemd 257 does, in the socket unit's own cgroup, `system.slice/<name>.socket`, then matched within that unit's lines) (matched on protocol, port, and address, the socket's own address before the wildcard; review of #268; VM scenario 309 checks a socket-activated test service is named). Only `system.slice` and `init.scope` are walked under `/sys/fs/cgroup`. The server stores it in `host_applicability`, one narrow row per host written only when it changes, as `hosts` is after #220; a report without `in_use` clears it, an `unreadable` or `unsupported` one too (review of #268, S1). The contract is in `docs/api/README.md` ("What is in use"). Limits beyond the spec's: 20,000 cgroups under those two, `/proc/net` files up to 32 MiB, file lists up to 64 MiB each, at most 20,000 packages named by the scan.
- **Positive evidence only (owner decision 2026-11-20).** A service is named by its `ExecStart=` executable's package, so a wrapper hides the program it starts: Debian's `postgresql@.service` runs `pg_ctlcluster` (`postgresql-common`), so a listening PostgreSQL shows as `postgresql-common` `network` and `postgresql-17` in neither list; so do `sh -c`, `env`, and interpreters. Naming the program itself would need `/proc/<pid>/exe` of other users' processes, which needs ptrace access the agent's unit does not have, so it is not done (the limit is documented). `listening` and `services` are positive evidence only: a package left out is never idle on that account.
- **Reboot flag** in the inventory: `reboot_required` is true when Debian's `/run/reboot-required` exists, with `/run/reboot-required.pkgs` (at most 50 names); **null, never false, when it does not**, because Debian's kernel packages have not reliably created it (Debian bug #1010699, as the review notes). The server's own kernel rule (a newer image installed and not running) is the main signal; the flag adds reboots for other packages (for example libc).
- **Kernel build** (`/proc/sys/kernel/version`, which on Debian names the image's package version) is reported for distributions that update a kernel package in place (#163); Debian 13 does not need it.
- Bounded: at most 10,000 sockets and 1,000 units, 10 s. Measure on a 2,000-package host and record CPU and memory here.
- **Measured (#258):** under the agent's unit on GitHub's Ubuntu 24.04 runner (the sandbox smoke test, about 1,200 packages): 175 to 275 ms per report, 20 running services, 3 listening packages, the same as without the sandbox. On Debian 13 (VM scenario 309, 329 packages): 73 ms; the agent's memory peak over the scenario 3.8 MiB, inside the unit's `MemoryMax=128M` (scenario 374). CPU, on a 1,047-package host (`cargo test cpu_on_this_host -- --ignored`, debug build): 140 to 270 ms for the pass over dpkg's file lists, which dominates; the library scan's whole pass (maps, file lists, ELF checks of 672 native packages) 375 ms of CPU, 353 ms wall. Memory and time on a generated host of 3,000 packages × 300 files (about 900,000 listed files; `cargo test --release scan_peak_memory -- --ignored`, third review S1): peak RSS 8 MiB with nothing mapped and 55 MiB with both mapped-file limits full (50,000 + 50,000), against `MemoryMax=128M` (judging each package as its lists are read; the reviewer measured 112 and 161 MiB before). Time 9.3 s with a cold cache (caches dropped) and 3.1 s warm, inside the 25 s budget on this disk; a much slower disk could take a large host past it, and the scan then reports `failed` (no L1), never a partial answer. After the re-review's stricter native check (every file of a candidate package inspected), the scan on that host took 380 to 520 ms of CPU and wall time with a warm cache and 6.7 s with a cold one (lstat of about 166,000 files), inside its 25 s budget. On Debian 13 (scenario 309) a scan took about 0.5 s of wall time, and the agent had used 147 ms of CPU from its start through its first reports, the in-use collection included.

### Acceptance criteria

- [ ] On a test VM, `smbd` listening on a LAN address marks `samba` `network`, and `sshd` bound to 127.0.0.1 only marks `openssh-server` `loopback`, with no change to the agent's unit and its exposure still 1.9 (CI's VM scenario 309 checks the same with test services on the VM's LAN address and on 127.0.0.1, and sshd on every address; the owner checks samba and a loopback-only sshd on the test VM)
- [x] A missing `/run/reboot-required` is reported as null, and the report has no process id, command line, address, or port (VM scenario 309; `agent/src/in_use/tests.rs`)

## VT-A02: Library use and stale code (optional, off by default)

### Scope

- Which packages' files are mapped by running processes (`/proc/<pid>/maps`, `/proc/<pid>/exe`), and `stale` (a process still maps a deleted version of a package's file, so it runs old code until restarted). Only this needs ptrace read access to other processes.
- **Never in the main unit.** `CAP_SYS_PTRACE` is not read-only: it allows `PTRACE_MODE_ATTACH` and reading `/proc/<pid>/mem` of every process, so in the network-facing agent a file-read bug would disclose other processes' secrets (threat model F-2: the sandbox exists for non-exec bugs). Adding it to `fleet-agent.service` raises its `systemd-analyze security` exposure from 1.9 to 2.2, above the 2.0 gate (measured in the review). And the agent cannot work around it: `ProtectProc=invisible` and the capability rules hide every other user's process and every root daemon with more capabilities than the agent's.
- **A separate, short-lived unit**, as `apply_package_updates` runs apt (threat model F-1): the agent starts a transient oneshot (`systemd-run`, fixed unit name and properties) running its own binary in a scan mode with `CapabilityBoundingSet=CAP_SYS_PTRACE` alone (`CAP_DAC_READ_SEARCH` dropped: `CAP_SYS_PTRACE` alone reads every process's maps, and the dpkg lists are world-readable; owner decision 2026-11-20), `PrivateNetwork=yes`, `ProtectSystem=strict`, `ProtectHome=yes`, `ProcSubset=pid`, `RuntimeMaxSec=30`. The scan receives no input from the server.
- **At most once an hour (owner decision 2026-11-20).** The server can ask for package reports (`report_request`, the `refresh_reports` task), so it could otherwise decide how often a root process with `CAP_SYS_PTRACE` runs. The agent runs the scan at most once an hour and reuses the last result, or the last failure, in reports in between, with its time (`in_use.scanned_at`). **Across restarts and updates too** (owner decision 2026-11-20, re-review S4): the last scan's wall-clock time and result are kept in the state directory as `library-scan.json` (mode 0600, written atomically by the agent's own unit, which may write only its state directory; the scan unit cannot see it). A record is checked as the scan's own output is (RFC 3339 time, package names within the contract, each once, at most 20,000; a reason of at most 512 characters; third review, N3). A record over an hour old by the wall clock (after a suspend, for example), dated in the future, missing, corrupt, or unreadable means a new scan, never a crash; one that cannot be written is logged.
- **Built (#258):** `fleet-agent-library-scan.service`, `fleet-agent library-scan` (`agent/src/in_use/scan.rs`). It needs **no** write access at all: `systemd-run --wait --pipe` hands its result to the agent on standard output, so the state directory is hidden from it with the credential (`InaccessiblePaths=`), stricter than the result file first proposed. It also sets `IPAddressDeny=any`, only `AF_UNIX`, `NoNewPrivileges=yes`, the agent unit's system call filter, `MemoryMax=128M`, and `TasksMax=16`. It reads `/proc/<pid>/maps` only (which includes each process's executable), counting files under `/usr`, `/bin`, `/sbin`, and `/lib*` toward the 50,000-file limit and every other mapped file (under `/opt`, a home, `/tmp`) toward a second 50,000-file limit; both are looked up, so a package under `/opt` that a process maps is in `libraries`.
- **Native code only (owner decision 2026-11-20).** Python, Perl, Ruby, Node, and Java read their code with `read(2)` rather than mapping it, so a package of such code can be in use with nothing of it mapped. The scan reports `in_use.native`: the packages that ship at least one ELF executable or shared library under `/usr`, `/bin`, `/sbin`, or `/lib*`, no ELF file elsewhere (code under `/opt` is not judged), no file ending in `.py`, `.pyc`, `.pyo`, `.pyz`, `.pm`, `.pl`, `.rb`, `.js`, `.mjs`, `.cjs`, `.jar`, `.class`, `.war`, `.beam`, `.php`, `.lua`, `.tcl`, `.sh`, or `.bash` outside `/usr/share/doc`, and no `#!` script anywhere (a file with an execute bit, a file named like code, or the target of one of its symlinks), and all of whose files the scan could read (re-review of #268, B1, S2). **Never idle, code run on demand (owner decision 2026-11-20, re-review S3):** a package with any file in `security/` (PAM), `sasl2/`, `gconv/`, `pkcs11/`, `ossl-modules/`, `engines-3/` or `engines-1.1/`, `krb5/plugins/`, `gio/modules/`, `gdk-pixbuf-2.0/`, `gtk-3.0/modules/` or `gtk-4.0/modules/`, any `libnss_*` file, or any set-user-ID or set-group-ID file (`unix_chkpwd`) is not native: such code is mapped only while a login or lookup runs. Because init scripts, cron jobs, and maintainer helpers are scripts, many daemons (for example `openssh-server`, `cron`) are not native and never idle: conservative by design. A diverted or shared file marks every package that lists it (S7). A package's lists for every architecture count together (`libfoo:amd64` and `libfoo:i386`; third review, N1). A package whose ELF file is reached through a directory symlink other than the `/usr` merge is not native, since the maps show its real path and it would never be matched (N2), and nor is one whose list has a line that is not UTF-8 (N5). Each package is judged as soon as its lists are read, so the scan holds one package's files at a time (S1). If the scan's 25 s budget runs out, or a file cannot be read, the scan fails or leaves the package out rather than judge it on part of its files (B2). `complete` means `libraries` lists every native-code package mapped by running processes. Only a package in `native` and absent from `libraries` may be called idle; the server's `HostApplicability#provably_idle?` encodes it.
- **Off by default.** Enabled only on the VM, `[packages] library_scan = true` in the local config (as task types are enabled locally, ADR 0014). With it off no agent unit runs with the capability routinely. A report says whether the scan ran (`in_use.complete`, with `in_use.library_scan` `off`, `ran`, or `failed`); **without it, rule L1 applies to no package** (owner decision 2026-11-20, replacing "only to packages whose only use is a service that is not running": the report carries no evidence of that).
- Reported: package names and classes only. Bounded: at most 4,096 processes and 50,000 mapped paths, 30 s.
- A threat model row is added when built: the capability lives only in a no-network oneshot with a fixed program and no server input, for at most 30 s every package report.

### Acceptance criteria

- [x] With the scan off, the agent's own unit does not carry `CAP_SYS_PTRACE`; with it on, the transient scan unit carries it alone and has no network (VM scenario 309 reads its properties while it runs). As before this slice, the `apply_package_updates` task units and `fleet-agent-rollback.service` set no capability bound, by design (threat model F-1, F-13); neither reads process maps
- [x] With the scan on, a library used only by a stopped service is idle, and after an upgrade without a restart the library is `stale` (VM scenario 309)

## Decided by the owner (2026-11-20, review of #268)

1. **Idle needs proof.** Rule L1 applies only when the library scan ran and the package is native code (in `in_use.native`) and absent from `in_use.libraries`. Without the scan, or for interpreted packages, no package is called idle. `listening` and `services` are positive evidence only; a wrapper names the wrapper's package, a documented limit.
2. **The scan runs at most once an hour**, reusing the last result in between, however often reports are asked for (threat model F-13). The server ignores a stale scan (re-review of #268, S5; third review, S2; `HostApplicability#provably_idle?`): no L1 once the host's latest package report arrived (server clock) more than 12 hours ago (twice the default report interval), or arrived more than 1 hour before or after it was collected (agent clock: a re-sent report, or a skewed clock), or its scan ran more than 2 hours before that report was collected or more than 5 minutes after it.
3. **The scan unit keeps `CAP_SYS_PTRACE` alone**, with `ProtectHome=yes` and `ProcSubset=pid`.
4. **Code run on demand is never idle** (re-review S3): plugin and on-demand directories, `libnss_*`, and set-ID programs make a package not native (the list above).
5. **The hourly limit survives restarts** (re-review S4): the last scan is kept in the state directory and aged by the wall clock.
