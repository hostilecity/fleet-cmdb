# VT-APPLICABILITY: The agent reports listening services, the reboot flag, and (where enabled) library use

Implementation details for the GitHub issue with this key. The issue states only the goal and acceptance criteria; this file is the source of truth for everything else. Goal, requirement IDs, acceptance criteria, and blockers live in [`../issues.yml`](../issues.yml).

Part of [VT-EPIC](vt-epic.md) (approved by the owner, 2026-11-19), not in the first cut (epic decision 21), and blocked by VT-HOST-TAB because it adds the in-use signals to the tab (the agent half can be written earlier). It feeds rule N4 (exposure), the escalation of packages that listening processes load (VT-BUCKETS, VT-SCORES), and the reboot work item. It is an agent contract change ([FR-2.3](../../requirements.md#fr-23-package-reporting)); no backward compatibility is needed before Phase 3 ends (NFR-5). The agent reports facts and the server decides; nothing here runs a command chosen by the server.

## What the server already knows without this slice

The package report lists every installed kernel image and the inventory has the running kernel release (`kernel_version`), so rules I1, K1, and K2 and "reboot into the installed kernel" need no agent change (VT-S05). In trixie each kernel update is a new package, so "a newer image is installed and not running" is exactly a pending kernel reboot. This slice adds what the server cannot infer.

## VT-A01: Listening services and the reboot flag, with no new privilege

### Scope

- **Listening sockets**: read `/proc/net/{tcp,tcp6,udp,udp6}` (no privilege): local address, port, state, uid, and socket inode for each listening TCP socket and bound UDP socket.
- **Socket to service**: ask the kernel's `sock_diag` netlink interface for the same sockets with their cgroup id (`INET_DIAG_CGROUP_ID`, what `ss --cgroup` shows); map the cgroup id to its cgroup path under `/sys/fs/cgroup` (the directory's inode number is the id), the path to the systemd unit, the unit to its main executable (`systemctl show --property=ExecStart`, which the agent already runs with fixed arguments), and the executable to its binary package (dpkg's file lists under `/var/lib/dpkg/info/`, read-only). The unit already allows `AF_NETLINK` (`agent/src/install/fleet-agent.service`), so nothing in it changes; the exposure stays 1.9 (`agent/scripts/check-unit.sh` fails above 2.0).
- **Report**, in the package report: `in_use.listening`, each binary package owning a listening service with its class, `network` (any non-loopback address) or `loopback`, and `in_use.services`, the packages of running services' executables. Never process ids, command lines, user names, addresses, or ports. A socket whose cgroup is not a systemd service (a container, a user session) is counted, not named (`in_use.unnamed_listeners`, `network` and `loopback` counts; a service whose executable no package owns is counted there too).
- **Built (#258), decided conservatively:** a socket systemd itself holds for socket activation (cgroup `init.scope`) is named by matching its port and address with `systemctl list-sockets`, so a socket-activated service is not missed; if anything (the sockets, `sock_diag`, the cgroup tree, the services, the file lists) cannot be read whole, `in_use` is `null` with a `warnings` entry (field `in_use`) rather than a partial answer; that includes `systemctl list-sockets --show-types` when a socket is held by systemd (in `init.scope`, or, as systemd 257 does, in the socket unit's own cgroup, `system.slice/<name>.socket`, then matched within that unit's lines) (matched on protocol, port, and address, the socket's own address before the wildcard; review of #268; VM scenario 309 checks a socket-activated test service is named). Only `system.slice` and `init.scope` are walked under `/sys/fs/cgroup`. The server stores it in `host_applicability`, one narrow row per host written only when it changes, as `hosts` is after #220; a report without `in_use` clears it, an `unreadable` or `unsupported` one too (review of #268, S1). The contract is in `docs/api/README.md` ("What is in use"). Limits beyond the spec's: 20,000 cgroups under those two, `/proc/net` files up to 32 MiB, file lists up to 64 MiB each, at most 20,000 packages named by the scan.
- **Positive evidence only (owner decision 2026-11-20).** A service is named by its `ExecStart=` executable's package, so a wrapper hides the program it starts: Debian's `postgresql@.service` runs `pg_ctlcluster` (`postgresql-common`), so a listening PostgreSQL shows as `postgresql-common` `network` and `postgresql-17` in neither list; so do `sh -c`, `env`, and interpreters. Naming the program itself would need `/proc/<pid>/exe` of other users' processes, which needs ptrace access the agent's unit does not have, so it is not done (the limit is documented). `listening` and `services` are positive evidence only: a package left out is simply not known to be in use. The library scan, which reads `/proc/<pid>/exe`, names the listening program's package (`loaded_by_listeners`).
- **Reboot flag** in the inventory: `reboot_required` is true when Debian's `/run/reboot-required` exists, with `/run/reboot-required.pkgs` (at most 50 names); **null, never false, when it does not**, because Debian's kernel packages have not reliably created it (Debian bug #1010699, as the review notes). The server's own kernel rule (a newer image installed and not running) is the main signal; the flag adds reboots for other packages (for example libc).
- **Kernel build** (`/proc/sys/kernel/version`, which on Debian names the image's package version) is reported for distributions that update a kernel package in place (#163); Debian 13 does not need it.
- Bounded: at most 10,000 sockets and 1,000 units, 10 s. Measure on a 2,000-package host and record CPU and memory here.
- **Measured (#258):** under the agent's unit on GitHub's Ubuntu 24.04 runner (the sandbox smoke test, about 1,200 packages): 175 to 275 ms per report, 20 running services, 3 listening packages, the same as without the sandbox. On Debian 13 (VM scenario 309, 329 packages): 73 ms; the agent's memory peak over the scenario 3.8 MiB, inside the unit's `MemoryMax=128M` (scenario 374). CPU, on a 1,047-package host (`cargo test cpu_on_this_host -- --ignored`): 140 to 270 ms (debug build) for the pass over dpkg's file lists, which dominates. The library scan after the owner's 2026-11-21 redesign (maps, the host's listening sockets, the descriptors of each process, one pass over the file lists): 66 ms of CPU and 124 ms wall on that host (release build, its own process only); for a generated host, see VT-A02.

### Acceptance criteria

- [ ] On a test VM, `smbd` listening on a LAN address marks `samba` `network`, and `sshd` bound to 127.0.0.1 only marks `openssh-server` `loopback`, with no change to the agent's unit and its exposure still 1.9 (CI's VM scenario 309 checks the same with test services on the VM's LAN address and on 127.0.0.1, and sshd on every address; the owner checks samba and a loopback-only sshd on the test VM)
- [x] A missing `/run/reboot-required` is reported as null, and the report has no process id, command line, address, or port (VM scenario 309; `agent/src/in_use/tests.rs`)

## VT-A02: Library use and stale code (optional, off by default)

### Scope

- Which packages' files are mapped by running processes (`/proc/<pid>/maps`), and `stale` (a process still maps a deleted version of a package's file, so it runs old code until restarted); and which packages a process that holds a listening socket maps (`/proc/<pid>/fdinfo`, `/proc/<pid>/exe`, `/proc/<pid>/cgroup`). Only this needs ptrace read access to other processes.
- **Never in the main unit.** `CAP_SYS_PTRACE` is not read-only: it allows `PTRACE_MODE_ATTACH` and reading `/proc/<pid>/mem` of every process, so in the network-facing agent a file-read bug would disclose other processes' secrets (threat model F-2: the sandbox exists for non-exec bugs). Adding it to `fleet-agent.service` raises its `systemd-analyze security` exposure from 1.9 to 2.2, above the 2.0 gate (measured in the review). And the agent cannot work around it: `ProtectProc=invisible` and the capability rules hide every other user's process and every root daemon with more capabilities than the agent's.
- **A separate, short-lived unit**, as `apply_package_updates` runs apt (threat model F-1): the agent starts a transient oneshot (`systemd-run`, fixed unit name and properties) running its own binary in a scan mode with `CapabilityBoundingSet=CAP_SYS_PTRACE` alone (`CAP_DAC_READ_SEARCH` dropped: `CAP_SYS_PTRACE` alone reads every process's maps, and the dpkg lists are world-readable; owner decision 2026-11-20), `PrivateNetwork=yes`, `ProtectSystem=strict`, `ProtectHome=yes`, `ProcSubset=pid`, `RuntimeMaxSec=30`. The scan receives no input from the server.
- **At most once an hour (owner decision 2026-11-20).** The server can ask for package reports (`report_request`, the `refresh_reports` task), so it could otherwise decide how often a root process with `CAP_SYS_PTRACE` runs. The agent runs the scan at most once an hour and reuses the last result, or the last failure, in reports in between, with its time (`in_use.scanned_at`). **Across restarts and updates too** (owner decision 2026-11-20, re-review S4): the last scan's wall-clock time and result are kept in the state directory as `library-scan.json` (mode 0600, written atomically by the agent's own unit, which may write only its state directory; the scan unit cannot see it). A record is checked as the scan's own output is (RFC 3339 time, package names within the contract, each once, at most 20,000; a reason of at most 512 characters; third review, N3). A record over an hour old by the wall clock (after a suspend, for example), dated in the future, missing, corrupt, or unreadable means a new scan, never a crash; one that cannot be written is logged.
- **Built (#258):** `fleet-agent-library-scan.service`, `fleet-agent library-scan` (`agent/src/in_use/scan.rs`). It needs **no** write access at all: `systemd-run --wait --pipe` hands its result to the agent on standard output, so the state directory is hidden from it with the credential (`InaccessiblePaths=`), stricter than the result file first proposed. It also sets `IPAddressDeny=any`, only `AF_UNIX`, `NoNewPrivileges=yes`, the agent unit's system call filter, `MemoryMax=128M`, and `TasksMax=16`. It reads `/proc/<pid>/maps` (which includes each process's executable), and, for each process, its descriptors' `fdinfo` (mount and inode; `/proc/<pid>/fd` itself would need `CAP_DAC_READ_SEARCH` for another user's process), its program's link (`/proc/<pid>/exe`), and its cgroup, counting mapped files under `/usr`, `/bin`, `/sbin`, and `/lib*` toward the 50,000-file limit and every other mapped file (under `/opt`, a home, `/tmp`) toward a second 50,000-file limit; both are looked up, so a package under `/opt` that a process maps is in `libraries`.
- **Positive evidence only (owner decision 2026-11-21, after the fourth review of #268, replacing the 2026-11-19 L1 decision and the 2026-11-20 and 2026-11-21 "never idle" decisions).** "Not continuously running does not equal low risk, and trying to prove a package is never executed is a trap": an hourly snapshot cannot see short-lived helpers, cron jobs, or `sftp-server` sessions. So nothing is ever demoted from scan evidence, and the scan reports only what it saw: `in_use.libraries` (every package a process maps) and `in_use.loaded_by_listeners`, one entry per program and systemd unit whose processes hold a listening TCP socket or bound UDP socket (fifth review of #268, N6: stored the same way): `listener`, the package of the program (`/proc/<pid>/exe`, `null` when no package owns it); `service`, the unit from `/proc/<pid>/cgroup` (a service or socket unit in `system.slice`, `init.scope`, or `null`); `class`, `network` when one of the sockets is on a non-loopback address, else `loopback`; `sockets`, up to 4 of the listening sockets as `address:port/protocol`, network ones first (#277's third review: N5's reason names them; the only addresses and ports in a report), leaving out a UDP socket on an ephemeral port (32768 to 60999, Linux's default `ip_local_port_range`; the scan cannot read `/proc/sys`), whose port changes whenever a client re-creates it (N3). UDP services that listen in that range keep their escalation but lose their names: tailscaled (41641), wireguard-go (51820), Plex (32410 to 32414). An entry's `sockets` can then be empty, and a reason must not print "listening on" with nothing after it (re-review, N4); and `packages`, every package that lists a file (ELF or not) those processes map.
  - **How a listener is found.** A process holds a socket when one of its descriptors' `fdinfo` (`/proc/<pid>/fdinfo/<fd>`, which needs only ptrace access; `/proc/<pid>/fd` would need `CAP_DAC_READ_SEARCH`) shows the socket filesystem's mount (named from a socket the scan opens) and the inode of a listening socket in `/proc/1/net/{tcp,tcp6,udp,udp6}`: the host's network namespace, since the scan's own is empty. Only the first 256 bytes of each `fdinfo` are read: `pos`, `flags`, `mnt_id`, and `ino` come first, and an epoll or inotify descriptor's `fdinfo` has a line per registered descriptor or watch (fifth review, B1; a real-kernel test has an epoll set of 1,200 sockets, over 64 KiB of `fdinfo`, and an inotify descriptor).
  - **Linux 5.14 or later.** `fdinfo` has had `ino:` since 5.14. On an older kernel (Debian 11 has 5.10) the scan still lists `libraries` but reports `loaded_by_listeners: null` with a warning, and nothing is escalated (S4); the server stores that `null` apart from an empty list (`HostApplicability#listeners_known?`, re-review N3). No privilege is added for it.
  - **Chroots and containers.** A listener counts when its root (`/proc/<pid>/root`) is pid 1's, or is a directory of the host's tree: a `chroot`, which haproxy's workers and postfix's `smtpd` use by default, whose maps the kernel shows as host paths (re-review of #268, S1). It is skipped when its root is a filesystem of its own that the host's tree cannot reach: a container with host networking holds the host's sockets, but the files it maps are its image's, which the host's dpkg lists would wrongly name (fifth review, S3). A sandboxed host service has its own mount namespace but the host's root, so it counts. A process in another network namespace is not seen as listening either. VM scenario 309 runs a chroot'd listener, which counts, and a `pivot_root`ed one with a tmpfs root, which does not (the image has no Docker).
  - **Memory (S1).** Each mapped path is held once, each process's files once (a library has a maps line per segment; re-review N1), and processes of the same program and unit that hold the same sockets (a prefork server's children) are merged as they are read, each keeping only path indices. Measured on a generated host of 3,000 packages × 300 files, four maps lines per file as a library has (`cargo test --release scan_peak_memory -- --ignored`, against `MemoryMax=128M`): one listener mapping 50,000 + 50,000 files, 32 MiB peak, 0.61 s; 200 listeners × 2,000 files, 18 MiB, 1.1 s; 1,000 × 1,000, 19 MiB, 1.4 s; 4,000 × 600, 19 MiB, 3.0 s; with a different program for every listener, so none merge, 20, 22, and 35 MiB, 0.8 to 2.9 s. The distinct-path limits bound it; no other limit is needed.
  - Stated limits: interpreted code is read, not mapped, so a Python daemon shows the interpreter's and libraries' packages, not its own; under socket activation systemd (`init.scope`) holds the socket, so its own packages are named as loaded by a listener; what the scan misses is simply not reported. At most 1,000 listeners, 50,000 package names across them, and 500,000 descriptors, or the scan fails.
- **Off by default.** Enabled only on the VM, `[packages] library_scan = true` in the local config (as task types are enabled locally, ADR 0014). With it off no agent unit runs with the capability routinely. A report says whether the scan ran (`in_use.complete`, with `in_use.library_scan` `off`, `ran`, or `failed`); without it nothing is escalated from scan evidence, and every package keeps its standard severity.
- Reported: package names, classes, unit names, and, in `loaded_by_listeners`, up to 4 listening sockets per entry. Bounded: at most 4,096 processes, 50,000 + 50,000 mapped paths, 500,000 descriptors, and 25 s within the unit's 30 s.
- A threat model row is added when built: the capability lives only in a no-network oneshot with a fixed program and no server input, for at most 30 s, at most once an hour.

### Acceptance criteria

- [x] With the scan off, the agent's own unit does not carry `CAP_SYS_PTRACE`; with it on, the transient scan unit carries it alone and has no network (VM scenario 309 reads its properties while it runs). As before this slice, the `apply_package_updates` task units and `fleet-agent-rollback.service` set no capability bound, by design (threat model F-1, F-13); neither reads process maps
- [x] With the scan on, the libraries that processes holding a listening socket map are reported with the socket's class, one no process maps is not, and after an upgrade without a restart the library is `stale` (VM scenario 309)

## Decided by the owner

1. **Positive evidence only; nothing is demoted from the scan (2026-11-21, after the fourth review of #268).** This replaces the 2026-11-19 L1 decision (Low risk when no process uses the package), the 2026-11-20 "idle needs proof" rule (the `native` list and its rules), and the 2026-11-20 and 2026-11-21 "never idle" rules (on-demand directories, set-ID programs, and the D-Bus, timer, and cron parsing), all of which are removed. Packages keep their standard severity; only a package a listening process loads is escalated: it cannot be demoted by L2 to L5, counts toward Needs attention, and adds exposure points in VT-SCORES (`vt-buckets.md`). The server exposes it as `HostApplicability#in_use_by_listener?(package, now:, network: false)` and `#listener_details(package, now:)` (which listeners, their units, their class, and up to 4 of their sockets). **An escalation expires 24 hours after the server received the report that carried the host's latest scan** (`library_scan_received_at`, the server's clock, set when a report brings a scan the row does not have yet, so a skewed agent clock changes nothing; `HostApplicability::ESCALATION_MAX_AGE`; fifth review, S5). A report with a failed scan, the scan turned off, or no in-use report drops the escalations at once (S2). When evidence expires or is withdrawn, an escalated finding returns to the bucket the other rules give it, never below; the epic's acceptance criterion names this exception (for the owner's OK).
2. **The scan runs at most once an hour**, reusing the last result in between, however often reports are asked for (threat model F-13), **and the limit survives restarts** (re-review S4): the last scan is kept in the state directory and aged by the wall clock.
3. **The scan unit keeps `CAP_SYS_PTRACE` alone**, with `ProtectHome=yes` and `ProcSubset=pid`.

## What this slice leaves to others

The rules that read this data (the escalation, N4, the reboot work item) are VT-BUCKETS (#277; its builder implements the escalation itself) and VT-SCORES, and the in-use signals on the host tab are #260 VT-HOST-TAB. `HostApplicability.record_inventory!` and `record_in_use!` return whether anything changed, for re-triage of that host; an escalation's 24-hour expiry is time-based, so the builder also re-triages a host whose scan has aged past it.
