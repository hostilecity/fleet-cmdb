Implementation details for the GitHub issue with this key. The issue states only the goal and acceptance criteria; this file is the source of truth for everything else. Goal, requirement IDs, acceptance criteria, and blockers live in [`../issues.yml`](../issues.yml).

Part of [VT-EPIC](vt-epic.md) (approved by the owner, 2026-11-19). Builds what [host-vulns.html](../../mockups/vuln-triage/host-vulns.html) draws, on top of #253's package groups ([P2-D04](p2-dash-host.md#p2-d04-host-vulnerabilities-view)), approved 2026-11-19. Parts the mockup draws that need later slices are added by those slices (S9): the score breakdown and the run badge by [VT-SCORES](vt-scores.md), the decision links and tags by [VT-OVERRIDES](vt-overrides.md), and the in-use and listening signals by [VT-APPLICABILITY](vt-applicability.md). ## VT-D04: The tab

### Scope

- **Heading and strip.** "N open findings, by what you can do about them", the four bucket counts (findings) as links to their sections, and a proportion bar (SVG with a text equivalent). The tab bar's count becomes "N to act on" (Fix available plus Needs attention, epic decision 17); the open count stays in the heading.
- **Work remaining** (epic VT-M4), in work items: the source packages to upgrade (the update task can do these), "install the new kernel package" when K2 applies (a documented manual step, since the task installs no new packages, DEC-16), "reboot into the installed kernel" when K1 applies, and decisions due beside them. The "Apply package updates on this host" link into the create-task flow (#252 question 9) says the task covers the package upgrades only: it installs every pending upgrade, no new packages, and never reboots.
- **Progress, last 30 days**, in work items: a native `<meter>`, "N of M work items done", with findings cleared as secondary text; done items come from work events (VT-S05), so advisory corrections never count. "Nothing to install" when there is nothing in either part. Shown here and in the host summary tiles only.
- **Sections**, one native `<details>` per bucket, in the order of epic decision 16 (recommended: Fix available, Needs attention, Low risk, Ignorable); Fix available and Needs attention open by default; `keep-open` as #253.
  - Fix available: the kernel row first when K1 or K2 applies (its action and the number of advisories it clears), then #253's package rows with an "Upgrade to" column.
  - Needs attention: one row per advisory (its packages listed), severity, signals (known exploited, EPSS, the attack vector in words), and the reason; then the suggested controls for the rules present.
  - Low risk and Ignorable: one row per rule with its count and largest package, each opening that rule's package rows.
- **Staleness qualifiers** at read time (epic VT-M1): when KEV or EPSS is stale or never imported, the freshness line and the affected reasons say so.
- **Filters**: state, severity, text, and a signal filter (known exploited, EPSS high, network without login); `?bucket=` keeps one section. They combine with AND and stay in the URL; bucket counts are over the open list whatever the other filters.
- **Statements**: a fixed number whatever the host's finding count; bucket counts from the summary row.

### Acceptance criteria

- [x] The tab shows the four buckets with counts that add up to the open count, each finding with its reason and rule id, and a kernel fix as "reboot" or "install the new kernel package" rather than a package upgrade (`spec/requests/host_vulnerability_triage_spec.rb`)
- [x] Work remaining and progress are both in work items, and progress counts only actions the host's reports show (an advisory correction counts nothing) (the same spec)
- [x] The tab sends the same number of statements for a host with 10 findings and one with 4,000, and passes axe-core with no violations (the same spec and `debian_triage_views_spec.rb`; axe-core in As built)

## As built (#260)

- **Counts.** The state counts' one grouped query (`group(:state, :bucket)`) gives the four bucket counts too, so they add up to the open count in the same snapshot and cost no statement. The spec says "from the summary row"; this reads the same stored buckets the summary counts, without the summary's lag behind a severity recount. The tab bar says "N to act on" (Fix available plus Needs attention), from `HostSummary`'s existing per-severity query, now grouped by bucket too.
- **Not triaged yet** (#277 item 15). An open finding with no bucket (the upgrade's background re-triage has not reached its host) is counted as "Not triaged yet", never as 0 in a bucket. With every open finding untriaged, the strip is replaced by a notice, only #253's package rows are drawn, the tab bar says "N open", and work and progress say "not counted yet". With some untriaged, a fifth count stands beside the four and a fifth section lists them.
- **Sections** (`HostTriageSections`). Fix available: the kernel's rows (K1, K2; "Reboot into <release> (installed)" or "Install the new kernel package (`apt full-upgrade`), then reboot") before the package rows (F1, F2; "Upgrade to <version>", the highest fix of the row). Package rows stay #253's binary package rows and order, as the spec says; the mockup grouped them by source package, which Work remaining does instead. Needs attention: one row per advisory (`HostAdvisoryGroups`, keyset pages, worst severity first, ties broken by KEV status, as the owner decided on 2026-11-22: epic decision 30), its packages, signals (known exploited, the highest EPSS score, the attack vector in words, and "Listening: network" or "loopback only" when VT-APPLICABILITY reports a listener), and the reason of each distinct rule; then the suggested controls of the rules on the page. Low risk and Ignorable: one row per rule (`HostTriageRules`, one query), each linking to `?rule=` with that rule's package rows. Each finding shows its reason (`VulnerabilityTriage::Reasons`, with the staleness qualifiers) and rule id. The reason is built from the current inputs only while they still give the stored rule; when they no longer do (an input changed and the host's re-triage has not run: N5 whose listener evidence expired before `TriageListenerExpiryJob` reached the host), the stored rule's summary says "Re-triage pending" (review of #281, B1). On a host that is not evaluated now, whose inputs cannot be read, the rule's summary (`Reasons::SUMMARIES`). The Low risk and Ignorable rule rows carry the KEV and EPSS qualifiers their rule takes (S2). At most 200 findings are drawn under a package row, worst severity first; the rest are on its package page (N3). Each section has its own cursors (`kernel_`, `fix_`, `attention_`, `rule_`, `untriaged_`).
- **N5** (owner decision 2026-11-21). Its reason names the listener's package, unit, and up to 4 sockets, all escaped (a spec renders markup and a bidi override in them). Its control is its own text (`listening_service`), since N4's says "reachable without a login", which N5 does not claim. The Needs attention section says when listening services are not read at all (no `HostFacts.listener_source`, as on main until #268) or when the source says this host cannot tell (`HostFacts.listener_coverage`, which asks `listeners_known?(host_id)` when the source answers it), so their absence is never read as "nothing listens". Nothing on the tab says "idle"; the approved mockups were revised to match (no L1 row; an N5 row; `states.html#no-in-use`), and the owner accepted the revision on 2026-11-22 (epic decision 29).
- **Work and progress** (`HostVulnerabilityWork`, two queries). Remaining: one upgrade per source package with F1 or F2 findings (the first 8 named), "install the new kernel package" for K2, "reboot" for K1; decisions due are the Needs attention advisories (no decision can be recorded before VT-OVERRIDES). Done: the work events of the last 30 days, each one work item. "Nothing to install" when both are zero, with the Needs attention count beside it (VT-M5 rule 3). Progress is withheld on a host that is not evaluated or whose package report is older than 3 days (VT-M5 rule 2; a constant until VT-SCORES makes it the setting of decision 7). "Apply package updates on this host…" opens the task flow's parameters step for `apply_package_updates` with the host filled in, shown only with upgrades left on an active host.
- **Filters.** `?signal=kev` (the stored KEV flag), `epss` (any CVE of the advisory in the stored high band), `network` (CVSS AV:N/PR:N/UI:N); with the state, severity, text, and Debian no-DSA filters, all ANDed and in the URL. `?bucket=` keeps one section. VT-FIXABLE's "Fix available" and "No fix available" chips are removed (owner decision 2026-11-22, epic decision 28): their fix flag and the bucket meant different things under the same words. `?fix=available`, where the Compliance page's and the fleet list's "N with a fix" link, still shows exactly the findings they count, with a line saying how the Fix available bucket differs (F2, kernel steps, images not running; review of #281, S1). The EPSS filter is labelled by the stored band ("10% or more, kept until below 7%").
- **Statements.** A fixed number whatever the host's finding count (`spec/requests/host_vulnerability_triage_spec.rb` compares 9 and 49 findings on four addresses; `debian_triage_views_spec.rb` 1 and 500): 54 on the default page of the 4,450-finding bench host, against 31 on `main`.
- **Measured** (`bin/benchmark explain --only "vulnerabilities tab"`, and in-process requests in development mode; a seed of 2,000 hosts with 100 package hosts and `--advisories-per-source 5`, about 3,560 to 4,450 open findings a host, its buckets rewritten to a realistic mix: 650 Fix available with 30 kernel, 50 Needs attention, about 1,600 Low risk, about 2,000 Ignorable). The data path is 28 statements and 33 ms of database time (`?rule=I2` with `?signal=network`: 31 and 43 ms); loading the sections 23 ms, of which the page's triage inputs 8 ms; work and progress 7 ms. The whole request, development mode on a shared 2-CPU container: 150 to 195 ms (main's tab: 114 ms), 200 KB of HTML. The planner's sequential scans are on near-empty tables (KEV, EPSS, tracker entries) that have indexes on their keys.
- **axe-core 4.14** (WCAG 2.1 A and AA, best practices) reports no violations on the default tab, `?rule=L2`, `?state=all`, and a host not triaged yet.
- **Left for #258 (#268) and later:** `listeners_known?` on the listener source; the "Listening on the network" signal filter the mockup draws (it needs #258's data in SQL); the score breakdown and run badge (VT-SCORES), the decision links and tags (VT-OVERRIDES).
