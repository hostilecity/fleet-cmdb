Implementation details for the GitHub issue with this key. The issue states only the goal and acceptance criteria; this file is the source of truth for everything else. Goal, requirement IDs, acceptance criteria, and blockers live in [`../issues.yml`](../issues.yml).

Part of [VT-EPIC](vt-epic.md) (approved by the owner, 2026-11-19). Builds what [host-vulns.html](../../mockups/vuln-triage/host-vulns.html) draws, on top of #253's package groups ([P2-D04](p2-dash-host.md#p2-d04-host-vulnerabilities-view)), approved 2026-11-19. Parts the mockup draws that need later slices are added by those slices (S9): the score breakdown and the run badge by [VT-SCORES](vt-scores.md), the decision links and tags by [VT-OVERRIDES](vt-overrides.md), and the in-use and listening signals by [VT-APPLICABILITY](vt-applicability.md). ## VT-D04: The tab

### Scope

- **Heading and strip.** "N open findings, by what you can do about them", the four bucket counts (findings) as links to their sections, and a proportion bar (SVG with a text equivalent). The tab bar's count becomes "N to act on" (Fix available plus Needs attention, epic decision 17); the open count stays in the heading.
- **Work remaining** (epic VT-M4), in work items: the source packages to upgrade (the update task can do these), "install the new kernel package" when K2 applies (a documented manual step, since the task installs no new packages, DEC-16), "reboot into the installed kernel" when K1 applies, and decisions due beside them. The "Apply package updates on this host" link into the create-task flow (#252 question 9) says the task covers the package upgrades only: it installs every pending upgrade, no new packages, and never reboots.
- **Progress, last 30 days**, in work items: a native `<meter>`, "N of M work items done", with findings cleared as secondary text; done items come from work events (VT-S05), so advisory corrections never count. "Nothing to install" when there is nothing in either part. Shown here and in the host summary tiles only.
- **Sections**, one native `<details>` per bucket, in the order of epic decision 16 (recommended: Fix available, Needs attention, Low risk, Ignorable); Fix available and Needs attention open by default; `keep-open` as #253.
  - Fix available: the kernel row first when K1 or K2 applies (its action and the number of advisories it clears), then #253's package rows with an "Upgrade to" column.
  - Needs attention: one row per advisory (its packages listed), severity, signals (known exploited, EPSS, the attack vector in words), and the reason; then the suggested controls for the rules present.
  - Low risk and Ignorable: one row per rule with its count and largest package, each opening that rule's package rows.
- **Staleness qualifiers** at read time (epic VT-M1): when KEV or EPSS is stale or never imported, the freshness line and the affected reasons say so.
- **Filters**: state, severity, text, and a signal filter (known exploited, EPSS high, network without login); `?bucket=` keeps one section. They combine with AND and stay in the URL; bucket counts are over the open list whatever the other filters.
- **Statements**: a fixed number whatever the host's finding count; bucket counts from the summary row.

### Acceptance criteria

- [x] The tab shows the four buckets with counts that add up to the open count, each finding with its reason and rule id, and a kernel fix as "reboot" or "install the new kernel package" rather than a package upgrade (`spec/requests/host_vulnerability_triage_spec.rb`)
- [x] Work remaining and progress are both in work items, and progress counts only actions the host's reports show (an advisory correction counts nothing) (the same spec)
- [x] The tab sends the same number of statements for a host with 10 findings and one with 4,000, and passes axe-core with no violations (the same spec and `debian_triage_views_spec.rb`; axe-core in As built)

## As built (#260)

- **Counts.** The state counts' one grouped query (`group(:state, :bucket)`) gives the four bucket counts too, so they add up to the open count in the same snapshot and cost no statement. The spec says "from the summary row"; this reads the same stored buckets the summary counts, without the summary's lag behind a severity recount. The tab bar says "N to act on" (Fix available plus Needs attention), from `HostSummary`'s existing per-severity query, now grouped by bucket too.
- **Not triaged yet** (#277 item 15). An open finding with no bucket (the upgrade's background re-triage has not reached its host) is counted as "Not triaged yet", never as 0 in a bucket. With every open finding untriaged, the strip is replaced by a notice, only #253's package rows are drawn, the tab bar says "N open", and work and progress say "not counted yet". With some untriaged, a fifth count stands beside the four and a fifth section lists them.
- **Sections** (`HostTriageSections`). Fix available: the kernel's rows (K1, K2; "Reboot into <release> (installed)" or "Install the new kernel package (`apt full-upgrade`), then reboot") before the package rows (F1, F2; "Upgrade to <version>", the highest fix of the row). Package rows stay #253's binary package rows and order, as the spec says; the mockup grouped them by source package, which Work remaining does instead. Needs attention: one row per advisory (`HostAdvisoryGroups`, keyset pages, worst severity first, ties broken by KEV status, as the owner decided on 2026-11-22: epic decision 34), its packages, signals (known exploited, the highest EPSS score, the attack vector in words, and "Listening: network" or "loopback only" when VT-APPLICABILITY reports a listener), and the reason of each distinct rule; then the suggested controls of the rules on the page. Low risk and Ignorable: one row per rule (`HostTriageRules`, one query), each linking to `?rule=` with that rule's package rows. Each finding shows its reason (`VulnerabilityTriage::Reasons`, with the staleness qualifiers) and rule id. The reason is built from the current inputs only while they still give the stored rule; when they no longer do (an input changed and the host's re-triage has not run: N5 whose listener evidence expired before `TriageListenerExpiryJob` reached the host, a KEV entry removed, a reboot), it reads "When triaged: <the rule's summary> Re-triage pending: the data changed since this finding was triaged.", in the past and without qualifiers, so the old rule's evidence is never stated as today's (review of #281, B1, and its re-check, N5). The kernel row's action follows the same guard: it names the image to reboot into only while today's data still gives K1, and otherwise says "the newer kernel" with the pending note (re-check, S1). On a host that is not evaluated now, whose inputs cannot be read, the rule's summary (`Reasons::SUMMARIES`). The Low risk and Ignorable rule rows carry the KEV and EPSS qualifiers their rule takes (S2). At most 200 findings are drawn under a package row, worst severity first (`NESTED_MAX`); a row below them says how many more match and links to the package page with the tab's filters, starting after the last finding drawn (#283, below). A Fix available row's "Upgrade to" is read from all its findings (re-check, N3). Each section has its own cursors (`kernel_`, `fix_`, `attention_`, `rule_`, `untriaged_`).
- **N5** (owner decision 2026-11-21). Its reason names the listener's package, unit, and up to 4 sockets, all escaped (a spec renders markup and a bidi override in them). Its control is its own text (`listening_service`), since N4's says "reachable without a login", which N5 does not claim. The Needs attention section says why N5 cannot escalate this host's findings now, from #268's data (`HostApplicability::ListenerSource.coverage`, one statement by host): the agent doesn't report listening data yet (no in-use report: an agent that predates #258), the library scan is off on the VM (its default) or failed, the kernel can't tell (before Linux 5.14), or the scan is more than 24 hours old; with no listener source at all, that listening services are not read. Each note says nothing is made less urgent for lack of it. With current evidence there is no note, and the Low risk section says a listening process loading a package escalates it. Nothing on the tab says "idle"; the approved mockups were revised to match (no L1 row; an N5 row; `states.html#no-in-use`), and the owner accepted the revision on 2026-11-22 (epic decision 33).
- **Work and progress** (`HostVulnerabilityWork`, two queries; three since VT-SCORES #262, which adds the agent's reboot flag, so the tab and the summaries' work items agree). Remaining: one upgrade per source package with F1 or F2 findings (the first 8 named), "install the new kernel package" for K2, "reboot" for K1 (or, with no K1 finding, for the agent's reboot flag, naming the packages that asked for it); decisions due are the Needs attention advisories (no decision can be recorded before VT-OVERRIDES). Done: the work events of the last 30 days, each one work item. "Nothing to install" when both are zero, with the Needs attention count beside it (VT-M5 rule 3). Progress is withheld on a host that is not evaluated or whose package report is older than 3 days (VT-M5 rule 2; the `vulnerabilities.badge_report_max_age_days` setting since VT-SCORES #262). "Apply package updates on this host…" opens the task flow's parameters step for `apply_package_updates` with the host filled in, shown only with upgrades left on an active host.
- **Filters.** `?signal=kev` (the stored KEV flag), `epss` (any CVE of the advisory in the stored high band), `network` (CVSS AV:N/PR:N/UI:N); with the state, severity, text, and Debian no-DSA filters, all ANDed and in the URL. `?bucket=` keeps one section. VT-FIXABLE's "Fix available" and "No fix available" chips are removed (owner decision 2026-11-22, epic decision 32): their fix flag and the bucket meant different things under the same words. `?fix=available`, where the Compliance page's and the fleet list's "N with a fix" linked until VT-SCORES (#262) replaced those counts with the buckets, still shows exactly the findings with the stored fix flag, with a line saying how the Fix available bucket differs (F2, kernel steps, images not running; review of #281, S1). With other filters too, the line counts what they keep and names the host's whole count beside it (re-check, N1). The EPSS filter is labelled by the stored band ("10% or more, kept until below 7%").
- **Statements.** A fixed number whatever the host's finding count (`spec/requests/host_vulnerability_triage_spec.rb` compares 9 and 49 findings on four addresses; `debian_triage_views_spec.rb` 1 and 500): 54 on the default page of the 4,450-finding bench host, against 31 on `main`.
- **Measured** (`bin/benchmark explain --only "vulnerabilities tab"`, and in-process requests in development mode; a seed of 2,000 hosts with 100 package hosts and `--advisories-per-source 5`, about 3,560 to 4,450 open findings a host, its buckets rewritten to a realistic mix: 650 Fix available with 30 kernel, 50 Needs attention, about 1,600 Low risk, about 2,000 Ignorable). The data path is 28 statements and 33 ms of database time (`?rule=I2` with `?signal=network`: 31 and 43 ms); loading the sections 23 ms, of which the page's triage inputs 8 ms; work and progress 7 ms. The whole request, development mode on a shared 2-CPU container: 150 to 195 ms (main's tab: 114 ms), 200 KB of HTML. The planner's sequential scans are on near-empty tables (KEV, EPSS, tracker entries) that have indexes on their keys.
- **axe-core 4.14** (WCAG 2.1 A and AA, best practices) reports no violations on the default tab, `?rule=L2`, `?state=all`, and a host not triaged yet.
- **Package page (#283).** The package page (`GET /hosts/:id/vulnerabilities/package`) is paged: 50 findings a page (`HostPackageFindings`), as the tab's pages, keyset on worst severity, first seen, advisory id ("C" collation), and the finding's id, the order the tab draws a row's findings in; `?after=` and `?before=` hold the whole key, and a link that does not parse or has nothing left past it shows the first page with a notice, as #253's pages. A row's "N more" link carries the tab's filters (severity, signal, text, the Debian chip, `?fix=`), `state=open`, the row's architecture, and its section (`kernel`: K1 and K2; `fix`: F1 and F2; `rule` with `rule=`: one Low risk or Ignorable rule; `untriaged`: no bucket; `HostTriageSections.section_scope`, the tab's own conditions), plus the cursor of the last finding the row drew and `from=tab`, so it opens on exactly the findings the row counts, starting with the first one not drawn, and says it starts after the findings the tab shows (epic decision 36 as amended, decided by the owner 2026-11-23). The tab's `?bucket=` needs no parameter of its own: the section names the bucket. Every filter is checked against the tab's fixed lists (states, severities, signals, `no_dsa`, `available`, the four sections, Low risk and Ignorable rules), the architecture against the package's own architectures (its findings' and its installed ones'), the cursors against patterns, and the text is capped at 100 characters as on the tab; anything else is dropped, never echoed. The signal applies to every state, since the tab's resolved list keeps it under "All" (#303, decided by the owner 2026-11-24; until then the page dropped it with `state=resolved`), and the Debian chip, `?fix=`, and a section apply to the open list only. One difference follows: the tab's own `?state=resolved` still ignores `?signal=` (it draws no signal filter there), while the package page applies it, so only a hand-edited `state=resolved&signal=` URL filters; no link the tab or the page draws sends one. With no filter the page lists every finding of the package in every state, as before. A filtered page says how many of the package's findings match and which filters, all escaped, with a link to every finding. The summary counts stay the package's whole counts (one grouped query, which also gives the architectures, and the page's count when nothing is filtered); the per-finding fix notes are the page's (decided by the owner 2026-11-23). The freshness line is unchanged: it named KEV and EPSS already (#257); the page now reads their statuses once, for the line and the reasons. Each row shows its bucket and reason in a "Why this bucket" column, the tab's heading (not in the approved `host-vuln-package.html` mockup; decided by the owner 2026-11-23), from the tab's helpers (`triage_reason`, with the page's triage inputs, KEV dates, and EPSS scores); a resolved finding is in no bucket. With VT-OVERRIDES (#261) it shows the tab's decision tags too (`HostDecisions`): O1's reason with who recorded the control, until when, and "Change or end"; a Low risk finding's decision; and, since the page has no Decision column, a Needs attention finding's decision in force, past its last day, or suspended, with its link. The page reads a caught-up replica (#198, as #237 requires). Statements: a fixed number whatever the package's size (`spec/requests/host_package_findings_spec.rb` compares 3 and 60 findings on three addresses); 49 on `debian_triage_views_spec.rb`'s 500-finding host, unfiltered, and 50 filtered, before #261 (which adds 2: the host's decisions, and the controls in force read with the triage inputs) (33 before: +1 the counts by state and architecture, +1 the filtered count when a filter is set, +13 the triage inputs, +2 KEV dates and EPSS scores; the KEV and EPSS freshness, one statement, as before). Each path the counts depend on has a spec that fails without it (review of #297, S2: the architecture condition, the id and "C" collation in the key, the not-triaged condition, the signal, Debian, and fix filters on the link, and the KEV dates).
- **Details for the shown rows only (#302).** The tab and the package page count, group, and sort on the plain findings table, then add the details (a finding's verdict: source, installed version, ecosystem, backport fields) only to the rows they load, in the same statement (`VulnerabilityFinding.with_details_of`, given the page's host). The host's verdicts are read once and joined, so a page costs at most its host's verdicts, whatever the fleet's chunk variety. A page of resolved rows reads none (review of #315, N3). The statements that need a detail of every finding of the host (the text search and the Debian chip, which read the source; the chip's count; the related packages; Work remaining by source; the backports kept) read the host's findings and verdicts once each with no join (`with_host_details`: appended, with a window over the key carrying each key's verdict to its finding, review of #315, R1) instead of probing each finding's verdict through the advisory's verdicts across the fleet, so their plan does not depend on statistics. `with_details`, the per-finding probe, stays for lists that span hosts. Counts, orders, cursors, replica reads, and statement counts are unchanged; `spec/models/vulnerability_finding_details_spec.rb` checks that the three give the same columns and values, and `spec/requests/host_package_findings_spec.rb` that neither page probes a verdict per finding and that the rows show the verdict's version. Measured in process on `bin/benchmark seed` with one package of a 4,450-finding host inflated to 1,650 findings, the findings statements' EXPLAIN ANALYZE time (best of 5 each) went from 27 to 14 ms on the tab and from 27 to 13 ms on the package page (2,000 hosts, one package set), and from 231 to 46 ms and 389 to 22 ms on a large fleet (100,000 hosts, 1,000 with findings over 500 package sets, every chunk matched: 47,528 verdicts).
- **Resolved rows (#303).** The resolved list (`?state=resolved` and `?state=all`) draws at most 200 findings under a package row too (`NESTED_MAX`), in its own order (worst severity, then first seen, then the advisory id: the package page's), so a removed kernel image with about 1,650 resolved findings no longer draws them all. The row below them says how many more match and links to the package page with `state=resolved`, the row's architecture, the filters the tab applies to the resolved list (severity, text, and under "All" the signal), the cursor of the last finding drawn, and `from=tab`, so it lands on exactly the findings the row counts. It carries no section, the Debian chip, or `?fix=`: they narrow the open list only. The link is built from the rows already loaded: no statement is added, and the tab still reads the replica. Only the drawing was capped here: the groups' statement still loaded every finding of every row on the page, open and resolved alike, which the review of #317 measured at 202 ms and 107 KB with 1 removed image (1,650 findings loaded), 583 ms and 988 KB with 10 (16,500), and 1.5 s and 1.9 MB with 20 (33,000). #318 bounds the load (below). `spec/requests/host_package_findings_spec.rb` checks the link's filters and landing (with and without the signal) and that the statements are the same for 3 and 60 resolved findings. Measured in process (test environment, a host with a removed image's 1,650 resolved findings and 40 open, best of 5 on a shared container): `?state=resolved` went from 783 KB of HTML and 189 to 236 ms to 105 KB and 128 ms; `?state=all` from 792 KB and 210 to 255 ms to 113 KB and 120 ms. Statements (37 and 48) and their database time (about 22 and 27 ms) are unchanged.
- **Findings loaded a row (#318).** A package row loads at most 201 findings (`HostFindingGroups.load_max`: `NESTED_MAX` and one more, to tell that the row has more), open and resolved rows alike: the first in the order the row draws them (worst severity, first seen, advisory id, the package page's key), picked by `row_number()` over the page's package and architecture pairs inside the same statement, before `with_details_of` adds the details, so only those rows get them. A row with more takes its total, severities, fixes, states, resolutions, and first seen from its aggregated group (the groups' first statement, which now counts the states and resolutions too); a row with fewer counts the findings loaded, as before (review of #253, S2). The aggregated fix count is of active findings only, as `VulnerabilityFinding#fixable` (a resolved finding's kept fixed version is not a fix; the ranked lists are all active, so their order is unchanged). A Fix available package row's "Upgrade to" stays the highest fix of all its findings (re-check of #281, N3): past the 201 it also loads its witnesses, one finding of each stored fixed version and every finding with none (whose F2 version is read from Debian's tracker), which are explained but not drawn. Statements and their count are unchanged; every count, order, and "N more" link is the same (`spec/models/host_finding_groups_spec.rb`; `host_vulnerability_triage_spec.rb` for "Upgrade to"). The page's plans keep #315's shape (a scan, a sort, a window, then the materialized CTEs) with fresh, stale, and missing statistics.
