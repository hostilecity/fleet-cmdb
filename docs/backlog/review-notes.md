# Requirements review notes

Review of `docs/requirements.md` (the draft generated by another LLM), done before turning it into GitHub issues. The original text is preserved in `docs/backlog/_original-requirements.md` so you can diff against it:

```
diff -u docs/backlog/_original-requirements.md docs/requirements.md
```

Every change in the new `docs/requirements.md` is tagged `[R-nn]`, matching the notes below. Anything that needs your decision is a `DEC-nn` issue. When you have signed off, strip the tags and delete this file and `_original-requirements.md`.

**Verdict:** the draft's scope, phasing, and safety posture are sound, and the Phase 3 controls are stronger than most. The problems are not with the intent; they are places where the draft is internally inconsistent, silent about a mechanism that code depends on, or leaves a choice open that would be expensive to reverse later. None of the fixes changes the product.

Legend for *Handling*: **Edited** = requirement text changed (proposed wording, tagged); **Decision** = left open as a `DEC-nn` issue with options and a recommended default; **Task** = captured as an issue.

## Contradictions and inconsistencies

| ID | Finding | Handling |
|---|---|---|
| R-05 | FR-S.3 says audit entries are append-only; NFR-2 says snapshots **and audit entries** are retained 90 days and may be pruned; FR-1.1 says retiring a host keeps its audit trail. These cannot all be true if pruning touches audit entries. | **Edited + DEC-07.** Audit entries are never auto-pruned by default; snapshots and status history are pruned at 90 days. |
| R-06 | FR-3.3 mentions a "blocked" task and an "interrupted" task, but the state list in FR-3.2 has neither. Nothing handles a task that is never delivered. | **Edited.** No `blocked` state; interrupted is `failed` with a reason; added `expired`. |
| R-07 | FR-2.1 (Phase 2) lets the operator trigger collection on demand, but agents only pull and the task system arrives in Phase 3, which then lists "re-collect on demand" as a task. The Phase 2 feature has no delivery mechanism, and Phase 3 duplicates it. | **Edited + DEC-13.** A "report requested" directive on the heartbeat response; Phase 3's task reuses it. |
| R-08 | FR-S.1 stores the credential in a "root-readable-only" file, which presumes a root agent, while the principles demand least privilege. | **Edited + DEC-03.** "Readable only by the agent's service account"; the real choice is a decision. |

## Gaps in the shared foundations and Phase 1

| ID | Finding | Handling |
|---|---|---|
| R-09 | The enrollment flow is undefined. How does an agent prove it may join? What is a "pending" host? What does "approve an enrollment request" mean without an unauthenticated registration endpoint? How is re-enrollment triggered? Every API story depends on it. | **Edited + DEC-04.** Single-use expiring enrollment token; re-enrollment is a new token. |
| R-10 | Host lifecycle is a list of four states with no transitions. Does retiring revoke the credential? Can a retired host come back? What is the liveness of a pending host? What do the fleet counts include? | **Edited.** Added the transition table and rules (retire revokes; retired is terminal; only active hosts have liveness). |
| R-11 | "Materially changes" is undefined, and "re-sending the same report produces one snapshot" is ambiguous. Available memory, free disk, and uptime change every report, so naive snapshots would be written every 15 minutes per host. | **Edited + DEC-07.** Stable vs volatile fields; snapshot only on stable change; retry dedupe by report id. |
| R-12 | "Visible without a manual refresh of the underlying data" is ambiguous; no job cadence is given; liveness transitions are "recorded" without saying where (the audit log would be flooded). | **Edited.** 30-second live update target, evaluation at least every 60 seconds, a separate status history table, heartbeats and transitions kept out of the audit log. |
| R-13 | FR-S.2 says unknown fields are "rejected or ignored consistently" and defers the choice; NFR-5 needs a version-skew story; Phase 3 may poll "on the heartbeat path" but the heartbeat response has no room for that. | **Edited + DEC-08.** Ignore-and-log unknown fields; HTTP 426 for unsupported agents; extensible heartbeat response. |
| R-14 | The agent has no defined persistent state, yet Phase 3 requires it to "record the task id before execution" and Phase 1 needs the last boot id. Behaviour during outages (spool or drop?) is unspecified, and "appear within one heartbeat interval" needs a first heartbeat on start. | **Edited.** State directory; no spooling; immediate first heartbeat. |
| R-15 | NFR-1 requires certificate verification with no opt-out, but the agent config has no way to trust a private CA, which is what most homelabs use. | **Edited + DEC-05.** `ca_file` option. |
| R-16 | Operator authentication mechanism is unspecified. NFR-1 implies passwords; the owner's other project uses Google OAuth. No bootstrap or recovery story. A hijacked session in Phase 3 is remote execution. | **Edited + DEC-06.** Rails built-in auth proposed; CSP added; second factor before Phase 3. |
| R-17 | Stack not specified beyond "Rails" and "relational": no versions, database, job backend, UI approach, or test framework. The local system Ruby is 2.6.10, which cannot run current Rails. | **Edited + DEC-02.** Proposed stack matching the owner's `homealert` project. |
| R-18 | "Stores a hash of each credential" does not say how. Agent credentials are high-entropy, so a fast digest is right and bcrypt is wrong (and per-request bcrypt is slow); the Rails `has_secure_token` helper stores plaintext. | **Edited.** Digest with a non-secret key id for lookup. |
| R-19 | Nothing detects a cloned VM (a copied config file gives two machines one credential). | **Edited.** Machine id in inventory; mismatch raises a warning. Kept deliberately small. |
| R-20 | No CI, release process, or agent upgrade path. OTA is out of scope, but "upgrade" is in NFR-4. | **Edited + Task.** Agent self-update added to out of scope; upgrade is manual; CI and release issues added (`SETUP-04`, `SETUP-05`, `P1-A08`). |
| R-21 | NFR-5 requires cross-phase contract tests but there is no shared place for schemas and example payloads, so each side would test its own idea of the format. | **Edited + Task.** `docs/api/` with JSON Schemas and examples, consumed by both test suites (`SETUP-06`). |
| R-22 | "Heartbeat handling does not degrade" is not measurable. | **Edited.** p95 under 200 ms at 50 hosts (proposed figure, flagged). |
| R-23 | The backup requirement ignores that a restored database is useless without the Rails master key and any private CA material, and never requires a restore to be tested. | **Edited.** Both added. |
| R-24 | The repository is **public**, there is no license, no security policy, no `.gitignore` (`.idea/` is untracked), and the project will hold hostnames and credentials in fixtures. | **DEC-09.** |

## Gaps in Phase 2

| ID | Finding | Handling |
|---|---|---|
| R-25 | The package payload has "source (the operating system's package manager)", but distribution advisories are keyed on the **source package** name (Debian, Ubuntu, Alpine, Rocky), and epochs are part of the version. Without these, vulnerability matching cannot work reliably. | **Edited + DEC-11.** Added source package name and full version with epoch. |
| R-26 | Advisories are release-scoped (Debian 12 differs from 13) and distribution fixes include backports. The draft's "affected version range" ignores both. Verified against the OSV schema, which models exactly this. | **Edited + DEC-11.** Matching uses the host's distribution and release; OSV format recommended. |
| R-27 | CIS Benchmarks are published under CC BY-NC-SA 4.0 and CIS's terms for non-member products restrict derivative works, reposting, and claiming a compliance level. The draft asks for a CIS "starter set" in what is currently a public repository. (A flag to verify, not legal advice.) | **Edited + DEC-10.** Own wording with CIS references as pointers; "CIS-aligned", never "compliant". |
| R-28 | "The expected value or condition" is undefined, and not-applicable has no definition. Anything that evaluates code on operator- or VM-influenced data is dangerous. | **Edited + DEC-12.** Small declarative condition format; applicability selectors. |
| R-29 | "Editing a rule re-evaluates stored snapshots" conflicts with "result history so an operator can see a failure appear and clear": re-evaluating history under a new rule rewrites the past. | **Edited.** Rules are versioned and immutable; results record the version; re-evaluation applies to the latest snapshot; history stores changes. AC-2.2 reworded to match. |

## Ambiguities I resolved with an interpretation (please confirm)

- **Cancelling a running, non-interruptible task** (FR-3.2): "cancellation takes effect before the next task starts" is read as "the running task is not stopped; nothing further in the same batch starts". See `P3-S05`.
- **"Create or approve a host"** (FR-1.5): with the token flow there is nothing to approve, so the dashboard action is just "create a host" (`DEC-04`).
- **"Unreadable" versus "unsupported"** facts (FR-2.1): the draft only has unreadable. I added `unsupported` for facts an older agent has no reader for, so they are not mistaken for permission failures.

## Things I did not change

- The out-of-scope list, design principles, and the Phase 3 "no arbitrary shell" stance. They are the strongest part of the draft.
- Acceptance criteria wording, except AC-2.2 (R-29). Two new criteria (AC-3.8, AC-3.9) were added only for the new safety requirements.
- Section order and numbering, so a side-by-side diff stays readable.

## Not addressed (candidates for later)

- Clock-skew warnings, host groups beyond tags, notifications or alerting on status change, an operator-facing API, password reset by email, and SSO. None is in the draft; none is needed to meet the three phase goals.
- The importer was tested against a fake `gh`, not live GitHub; see `README.md` in this folder.
